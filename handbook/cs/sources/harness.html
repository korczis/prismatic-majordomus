Co je harness a čí je

Agent v terminálu jsou tři vrstvy. Model generuje text a volání nástrojů. Harness providera (Claude Code, Codex, Gemini CLI) z toho dělá smyčku: spouští nástroje, hlídá oprávnění, spravuje kontextové okno, komprimuje konverzaci a vystřeluje hooky. Třetí vrstva je repozitář sám: co v něm platí, co se v něm rozhodlo a co musí změna splnit, než ji někdo přijme.

Harness providera

  • smyčka model → nástroj → výsledek
  • oprávnění a sandbox pro shell a soubory
  • kontextové okno, compaction, paměť providera
  • hooky: SessionStart, UserPromptSubmit, PreCompact, SessionEnd
  • MCP klient
  • u každého providera jiný, mění se s jeho verzí

Harness repozitáře (Majordomus)

  • bootstrap soubory vyrenderované z jedné policy
  • co se stane na hranicích session, zapsané jako záznam
  • task se scope, profilem a závazky
  • finish contract: kdy je hotovo
  • git hooky a CI gates, které se ptají stejného soudce
  • sdílený MCP server: board, kdo na čem dělá

Harness providera rozhoduje, co agent může udělat. Harness repozitáře rozhoduje, co se z toho počítá: co projde commitem, pushem a merge a co se zapíše jako hotové. Druhý nenahrazuje první. Majordomus nespouští nástroje, nehlídá oprávnění a nevolá model.

Proč nestačí harness providera

Každý z následujících problémů se v repu Majordomusu skutečně stal. Harness providera ho nevyřeší, protože o repozitáři neví víc, než mu kdo napíše do instrukcí.

Jedna session krok za krokem

Takhle vypadá typická session v Claude Code nad supervizovaným repem. Kroky 1, 2 a 9 se dějí samy, ostatní dělá agent podle bootstrapu.

  1. Provider otevře session, hook vrátí briefing

    SessionStart otevře epizodu, zmrazí snímek kontextu a vypíše briefing. Provider ho vloží do kontextu dřív, než agent udělá první krok. Agent tak hned ví, kde je, co je rozdělané a kdo další pracuje v repu.

    ## Majordomus — what this repository already knows
Episode s-20261012095404-7216, on master at afbc259, working tree dirty.
Active task t-20261009182131-ef1f (active, profile implementation): ...
Shared server: ready http://0.0.0.0:58860 pid 12169 version 0.21.0
Mesh: active — 2 of 2 provider(s) running; 7 node(s) known, 7 trusted
Handover ...--master--afbc259--....md (same_worktree_same_branch, exact, fresh, 7h ago)
Its Next Action: ...
Knowledge candidates awaiting review on this branch: 3
Run `majordomus context` for the full briefing, `majordomus check` before claiming ...

    Skutečný výstup z 12. 10. 2026, zkrácený. Handover nese štítek exact: HEAD se od zápisu nepohnul, takže se mu dá věřit doslova.

  2. Každý prompt se archivuje

    UserPromptSubmit uloží prompt lokálně jako dva soubory pod jedním kmenem (YYYYMMDDHHMMSS-<slug>.json a .md). Archiv nikdy necestuje gitem a CI gate prompt-privacy hlídá, aby se žádný prompt nedostal do publikovaného výstupu.

  3. Agent si přečte plný kontext

    majordomus context dá briefing v pořadí autority: git, task a profil, blokery, autorské záznamy, historie. majordomus context resolve <cesta> řekne, které kontextové dokumenty platí pro cesty, na kterých bude pracovat.

  4. Ohlásí se ostatním

    majordomus_peers ukáže, kdo dalšího pracuje v repu a na čem. majordomus_announce přidá vlastní záměr a cesty. Pokud se scope s někým potká, odpověď to rovnou řekne.

  5. Založí task

    majordomus start "Opravit porovnání callback URI" \
    --scope apps/majordomus-cli/src/auth --requires tests,commit,push --profile debugging

    Od teď je jasné, kam smí psát, co dluží a jak hluboký obřad práce dostane.

  6. Pracuje a průběžně zapisuje

    Checkpoint v intervalu profilu (15 minut u debugging), rozhodnutí přes decision add --why, nejasnosti přes question add. Při compaction zapíše checkpoint hook sám.

  7. Ověří, než něco tvrdí

    majordomus check vypíše každý závazek, scope a stav gates. Až potom smí agent říct, že je něco hotové.

  8. Commit a push projdou git hooky

    pre-commit, commit-msg a pre-push se ptají stejného spustitelného souboru jako agent. Co by neprošlo, agent mohl vidět předem.

  9. Uzavře task nebo ho předá

    finish --outcome completed --verify-command "…" projde kontrakt. Když práce hotová není, poctivý výsledek (partial, blocked, failed…) s poznámkou, nebo handover pro další session.

  10. Provider zavře session, hook uklidí

    SessionEnd zapíše checkpoint, odvodí kandidáty znalostí z ledgeru, odvodí handover a zavře epizodu do neměnné obálky v .ai/repo/sessions/. Proběhne, i když agent na nic z toho nepomyslel.

Jedna policy, víc providerů

Každý provider čte svůj soubor: Claude Code CLAUDE.md, Codex AGENTS.md, Gemini GEMINI.md. Kdyby se psaly ručně, za týden by si odporovaly. V Majordomusu jsou to projekce: majordomus update je vyrenderuje z šablon v .ai/repo/providers/*.tmpl podle seznamu v policy a každou opatří razítkem s hashem policy a hashem vlastního obsahu.

# .ai/repo/policy.yaml
projections:
  - provider: agents
    target: AGENTS.md
    always_loaded: true
  - provider: claude-code
    target: CLAUDE.md
  - provider: gemini
    target: GEMINI.md
  - provider: bb
    target: .bb/AGENTS.md

Co v bootstrapu je a co ne

Je v něm

  • kde najít policy a pravidla (.ai/README.md)
  • jak rozlišit kontext pro cestu (context resolve)
  • jak se připojit k MCP serveru a ohlásit se
  • task lifecycle: start, check, finish
  • kde se dělá nová práce (worktree topologie)

Není v něm

  • korpus pravidel: dvě kopie pravidla jsou jedno pravidlo a jedna lež
  • nic specifického pro jednoho providera, co by mělo platit pro všechny
  • text delší než řádkový limit z policy
  • ruční úpravy: ty odhalí razítko

Razítko a drift

První řádek vygenerovaného souboru (nebo začátek vygenerovaného regionu mezi značkami majordomus:begin a majordomus:end) nese příkaz, který soubor regeneruje, hash policy a hash obsahu. Obsah, který nesedí na svůj hash, upravil někdo ručně. doctor to nahlásí a obyčejné update ruční úpravu nepřepíše. Oprava je majordomus update --diff <soubor>, přenést změnu do šablony nebo policy, a teprve pak --force.

Nový provider je šablona a jeden řádek v projections. Nic jiného ho neregistruje. Nativní vnořené soubory providera (třeba CLAUDE.md v podadresáři) jsou optimalizace. Co pro danou cestu platí, rozhoduje majordomus context resolve <cesta>.

Hooky providera: zapisovat, nikdy blokovat

Hranice session kreslí hooky, ne model. Model zapomene zapsat handover, když mu dojde kontext. Hook SessionEnd vystřelí vždycky. V Claude Code jsou čtyři hooky zapojené v .claude/settings.json:

{
  "hooks": {
    "SessionStart":     [{ "hooks": [{ "type": "command",
      "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/majordomus-session-start" }] }],
    "UserPromptSubmit": [{ "hooks": [{ "type": "command",
      "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/majordomus-capture" }] }],
    "PreCompact":       [{ "hooks": [{ "type": "command",
      "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/majordomus-session-compact" }] }],
    "SessionEnd":       [{ "hooks": [{ "type": "command",
      "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/majordomus-session-end" }] }]
  }
}

Každý hook je tenký shell, který jen najde spustitelný soubor a předá mu payload:

# .claude/hooks/majordomus-session-start
root=$(CDPATH= cd -- "$(dirname -- "$0")/../.." && pwd) || exit 0
for mj in "$root/bin/majordomus" "$root/.majordomus/bin/majordomus"; do
  [ -x "$mj" ] && break
  mj=
done
[ -n "$mj" ] || mj=$(command -v majordomus) || exit 0
exec "$mj" --repo "$root" capture session --provider claude-code --event start

Repozitář se odvozuje z cesty k hooku, ne z pracovního adresáře. Provider dosadí svůj projektový adresář do příkazu textově a pracovní adresář hooku není nijak smluvně daný.

Co který hook dělá

UdálostKroky
SessionStartotevře epizodu (při resume ji ponechá), zapíše snímek do .ai/local/session-contexts/, vypíše briefing na stdout, zajistí běžící sdílený server
UserPromptSubmitcapture prompt: jeden JSON payload na stdin, jeden záznam; text promptu se kopíruje jako syrový úsek payloadu, aby se při dekódování nic neztratilo
PreCompactcheckpoint --derive, knowledge derive
SessionEndcheckpoint --derive, knowledge derive, handover --derive --close, session close

Pravidla, která ty hooky drží

  • Nikdy nezablokují člověka. V UserPromptSubmit by exit 2 zahodil prompt, který člověk napsal. Hook proto vrací vždy úspěch nebo exit příkazu, který má smluvně zakázáno vrátit 2.
  • Selhání se nezamete. Každá událost se nejdřív zapíše jako provider.event.received, takže jde rozlišit „hook nevystřelil“ od „vystřelil a nic neudělal“. Chyba se zapíše jako provider.event.failed.
  • Ztracený prompt shodí doctor. Payload, který capture nepřečte, jde do vlastního logu a doctor selhává, dokud log není prázdný. Je to jediná pojistka pro případ, že provider přejmenuje pole, ve kterém prompt posílá. Hook by pořád běžel a self-test by pořád prošel, protože posílá payload ve formátu, který si nástroj sám vyrobil.
  • Hook nemá vlastní logiku. Rozhoduje spustitelný soubor. Hook se nemění, když se mění chování.
  • Běží, ať je task otevřený, nebo ne. Epizoda a task jsou dva různé záznamy.

Sdílený server a board

Každý provider spouští MCP server přes svou konfiguraci (.mcp.json, .gemini/settings.json, .codex/config.toml), všechny ukazují na bin/majordomus-mcp. První proces v checkoutu se stane serverem, každý další se k němu připojí. Claude, Codex a Gemini nad jedním checkoutem tak sdílejí jeden server a vidí se navzájem.

Board: kdo na čem pracuje

Peer je každý připojený klient, pojmenovaný podle toho, co poslal v initialize (claude-code, codex, gemini-cli), a očíslovaný p1, p2… Už odpověď na initialize mu řekne URL serveru, jeho vlastní id a všechny ostatní peery s tím, co ohlásili.

  • Ohlášení je jeden řádek záměru a cesty. Žije jen v paměti serveru. Patří spojení, takže po reconnectu je potřeba ohlásit se znovu.
  • Board patří repozitáři, ne checkoutu. Každý worktree má svůj server, majordomus_peers sesbírá boardy všech a u každého workera uvede worktree. Pole complete: false říká, že se některý checkout nepodařilo zeptat. Krátký board není důkaz, že tam nikdo není.
  • Board se dá přečíst i z příkazové řádky. majordomus peers je třetí projekce téže capability jako MCP tool majordomus_peers a GET /api/v1/peers, pro workera, kterému klient žádné majordomus_* tooly nedal. Vypíše každý checkout se stavem jeho serveru, pod ním jeho peery a pod každým jeho claimy s cestami; --format json vrátí odpověď capability beze změny. Když neodpovídá žádný server, žádný board není: příkaz to řekne a skončí kódem 12, ne nulou nad prázdným boardem, který nikdo nečetl.
  • Id peera je pozice, ne identita. p1 se po reconnectu přidělí znovu a jiný board ho používá taky. Trvalá polovina identity je checkout.
  • Překryv je informace, ne zámek. Dva scope se potkají, když jsou stejné, nebo jeden obsahuje druhý. start a check --overlap to hlásí. Výlučný claim napříč stroji je majordomus_mesh_claim a jeho odmítnutí jmenuje claim, na který narazilo.

Dva druhy scope

Slovo scope má v Majordomusu dva významy a je dobré je nemíchat.

Scope repozitáře: co se čte

.ai/repo/scope.yaml, deklarované jednou. Co je mimo, se neindexuje, neservíruje přes MCP, HTTP ani CLI a nenajde se v žádné projekci.

out vyhrává nad in. Cesta, která nesedí na nic v in, je mimo jako undeclared.

Scope tasku: kam se píše

start --scope <cesty>. check a finish --outcome completed selžou na změněném souboru mimo scope.

Ostatní výsledky soubory jen vyjmenují jako varování, aby worker, kterému scope vyšel úzký, nezůstal zaseknutý.

Projekce, které z té změny zapíše derive, do scope jmenovat nemusíš. Cestu, kterou git označuje atributem merge=derived, kontrola připustí, pokud task změnil i něco kanonického: soubor vrstvy nebo nederivovaný soubor uvnitř scope. Větev, která nese jen projekce, je odmítnuta jako dřív, a repozitář, který nic jako derivované nedeklaruje, nepřipustí nic.

# .ai/repo/scope.yaml (výřez)
in:
  - .ai/repo/**
  - apps/**/src/**
  - docs/**
out:                     # vyhrává nad in
  paths: [.git/, .ai/local/, '**/node_modules/', '**/target/', vendor/]
  binary: true           # NUL bajt v prvních 8 KiB
  max_bytes: 1048576
  generated:
    paths: [docs/generated/, site/data/generated/]
  secret:
    names: ['.env', '.env.*', '*.pem', '*.key', 'id_rsa*']
  fixtures:
    paths: ['**/fixtures/', '**/testdata/']
    max_bytes: 65536     # fixture nad limit jsou data, ne kontext

Výchozí scope.yaml nejmenuje žádný jazyk: jen vrstvu a místa, kam zdrojáky a dokumenty ukládá kdokoli (src/**, lib/**, test/**, docs/**). majordomus init k tomu přidá, co v repozitáři skutečně je: každou položku trackovanou v kořeni, na kterou výchozí seznam nedosáhne, adresář jako <jméno>/** a soubor jménem. Přidané řádky stojí pod komentářem, který říká, odkud jsou, a každý odhad vypíše. Vypíše i to, co pravidla out vyřadí, přestože je to trackované: commitnutý dist/ nebo soubory nad max_bytes, vždy s klíčem, který to mění. Existující scope.yaml nepřepíše nikdy.

Na každou cestu dá majordomus scope odpověď i s důvodem (secret, generated, over_limit, binary…). Trackovaný soubor se jménem tajemství je varování tracked_secret: nikdy se nečte ani neservíruje a v repu by neměl být.

Profily: kolik harness stojí

Ne každá změna potřebuje stejný obřad. Profil je jeden pracovní režim: kolik kontextu task dostane, jak silný model a jak hluboké přemýšlení si zaslouží, jak stručně worker reportuje a co musí vyprodukovat, než smí skončit. Task nese profil, se kterým začal. Výchozí je implementation.

  failing_output: false

  • Třída modelu, nikdy jméno modelu. fast až strongest jsou slova policy. Které modely jim odpovídají, říká deklarovaný katalog (models route, share/models.yaml). Profil tak přežije výměnu modelu. Katalog záměrně neobsahuje ceny ani hodnoty credentials, jen jméno proměnné prostředí a jestli je nastavená.
  • Effort a verbosity jsou dvě osy. Přemýšlet tak tvrdě, jak task potřebuje, a reportovat tak stručně, jak říká profil.
  • context.* zapíná sekce briefingu. Rutinní změna nedostane historii a poznámky k architektuře, které by jen zabraly místo.
  • output_contract je tvar závěrečné zprávy. Deep-work navíc dluží seznam rozhodnutí.
  • Klíče jsou uzavřené. Klíč, který nic nečte, je chyba, ne tichá no-op.

Závazky tasku: co worker dluží

Scope říká, kam smí worker psát. --requires říká, co dluží, než bude výsledek completed k dispozici. Jsou to dva různé sliby: změna může být dokonale uvnitř scope a pořád ležet nezacommitovaná na notebooku.

Závazek, který umí rozhodnout git nebo existující příkaz, se rozhoduje živě a zaznamenaný důkaz se vůbec nečte. U ostatních je důkaz zahašovaný přes vstupní soubory, takže změna kteréhokoli z nich ho udělá stale, ne jen starý. Kde nic rozhodnout nemůže, je to v souboru napsané v poli unestablished. Poctivá mezera je lepší než kontrola, která vždycky projde. Neznámý token odmítne už start.

Finish contract: kdy je hotovo

„Hotovo“ je nejdražší slovo, které agent řekne. Majordomus ho agentovi nebere, ale nedovolí mu ho zapsat, dokud neprojde každý řádek kontraktu.

majordomus start "<task>" --scope <cesty> [--requires tests,docs] [--profile debugging]
majordomus context              # co je teď potřeba vědět; na začátku každé session
   ... práce ...
majordomus checkpoint < note.md # průběžný stav podle intervalu profilu
majordomus check                # před jakýmkoli tvrzením, že je něco hotové
majordomus handover < note.md   # pokračuje jiná session, nebo:
majordomus finish --outcome completed --verify-command "cargo test -p majordomus-cli"

Řádky kontraktu (verification.finish_requires)

ŘádekCo ověřuje
scope_respectedžádný změněný soubor mimo scope tasku; počítá se z gitu
verification_ranověřovací příkaz doběhl a uspěl
state_updatedzáznamy tasku odpovídají práci
no_open_blockersžádná otevřená otázka nepatří tomuto tasku
note_presentzávěrečná poznámka existuje
obligations_metkaždý závazek z --requires je splněný
gates_passedgates, které změna vybrala, prošly; queued neprošel
publication_currentpublikovaný výstup odpovídá stromu

Když jakýkoli řádek selže, finish --outcome completed nezapíše nic a vypíše každý řádek s pass nebo fail. Ostatní výsledky jsou poctivé přiznání, že práce hotová není, a každý potřebuje poznámku: # Next Action (co dál), nebo # Reason (proč).

Výsledky

OutcomeZnamená
activetask běží

partialčást hotová, zbytek popsaný v dalším kroku

V transcriptu vypadají „hledali jsme a nic nenašli“ a „nešlo to prohledat“ stejně. Supervisor, který je nerozliší, neví, jestli zkusit znovu, eskalovat, nebo přijmout. Rozhoduje typované pole, ne próza. Outcome je jediné pole, které po start nějaký příkaz mění.

Identitu záznamu (repozitář, branch, HEAD, stav pracovního stromu, změněné soubory) agent nikdy nepíše. Počítá ji Majordomus z gitu a tělo, které se ji pokusí nastavit, je odmítnuto.

Nejistota a poradci

Když agent narazí na podstatnou technickou nejistotu, nerozhoduje ji potichu. majordomus reasoning z ní dělá záznam, který další session přečte, místo aby se ptala znovu.

  1. Důkaz první

    Agent sesbírá lokální důkazy a zapíše assessment: předmět, jak moc na tom záleží, hypotézu a důkazy.

  2. Plán rozhodne policy

    Triviální nebo nízká závažnost: rozhodnout lokálně. Podstatné bez vhodného poradce: strukturovaná lokální revize. Existující závěr na to odpovídá: použít ho. Podstatné a poradci jsou k dispozici: zeptat se jich.

  3. Poradci dodávají důkaz, ne verdikt

    Externí modely (jiný vendor, jiný nástroj) dávají hlubší revizi. Rozhodnutí patří agentovi, který pracuje. Neshoda se řeší experimentem, ne hlasováním.

  4. Závěr je typovaný záznam

    Rozhodnutí s důkazy, zamítnuté alternativy, zbývající rizika a plán ověření. Pak práce pokračuje.

majordomus reasoning check hlídá, aby ten návrh držel, a ne všechny jeho rodiny pravidel se týkají každého repozitáře. catalogue a records platí všude, kde nástroj běží. adapters, coupling, ci a claims jsou pravidla o domově návrhu a vážou jen repozitář, který sám píše katalog poradců (share/advisors.yaml). Workflow adoptéra, který jmenuje klíč k modelu, nebo jeho vlastní ADR o tom, že produkt vyžaduje lokální model, je jeho produkt a doctor na něm neselže. Odpověď jmenuje rodiny, které proběhly.

Chybějící poradce není chyba ani důvod zastavit se a ptát člověka. Checkout bez nainstalovaného poradce, bez klíče a bez sítě rozhoduje stejně a jen zapíše, že to bylo lokálně. Vendor není v logice nikde: protokol „zeptej se tohohle, pak tamtoho“ by se rozbil v den, kdy vyprší klíč.

Git hooky: jeden soudce, víc míst

Agent může příkaz Majordomusu přeskočit. Commit a push přeskočit nemůže. Git hooky jsou proto poslední místo, kde harness repozitáře vidí každou změnu bez ohledu na to, kdo ji udělal: člověk, Claude, Codex, nebo skript. Instalují se jednou: git config core.hooksPath .githooks.

# .githooks/pre-commit
bin/majordomus doctor || exit $?
bin/majordomus-cli worktree guard --quiet || exit $?   # feature branch jen z vlastního worktree
scripts/pages current || exit $?                     # odvozená data odpovídají stromu

# .githooks/commit-msg
STAGED="$(git diff --cached --name-only --diff-filter=ACMR | paste -sd, -)"
bin/majordomus-cli commit validate "$1" --paths "$STAGED" || exit $?

# .githooks/pre-push (zkráceno)
# push, který nese jen refs/majordomus/* (záznamy kontinuity), projde bez kontraktu
bin/majordomus finish --check || exit $?

pre-commit

  • doctor je jen pro čtení a spustí každou doktrínu, která je na něj navázaná. Podrobněji níže.
  • Worktree guard. Feature branch se commituje jen z jejího kanonického worktree <repo>-wt/<branch>, trunk jen z primárního checkoutu. Cesta se odvozuje z gitu, nikde se neregistruje.
  • pages current porovná zaznamenaný hash vstupů odvozených dat s hashem tohoto stromu za pětinu sekundy. Commit, který pohne kanonickým vstupem bez regenerace, by rozbil deploy tomu, kdo přistane jako další.

commit-msg

Hook běží v jediném okamžiku, kdy existuje celý důkaz: zpráva je napsaná a soubory jsou staged. fix bez testu se dá zachytit, dokud je levné test přidat.

KódÚroveňZnamená
commit.not_conventionalerrorhlavička není type(scope): subject
commit.subject_emptyerrorza dvojtečkou nic není
commit.subject_too_longerrordelší než subject_max_chars (100)
commit.subject_trailing_perioderrorsubject je titulek, ne věta
commit.unknown_scopepolicy (warning)scope, který historie nikdy nepoužila
commit.fix_without_testpolicy (warning)fix bez testu mezi soubory
commit.unresolved_referencepolicy (error)id záznamu, které vrstva nezná
commit.breaking_unexplainedpolicy (error)! bez těla a bez BREAKING CHANGE:

Limit 100 znaků je změřený, ne zvolený. Konvence gitu je 72. Medián subjectu v historii repa byl 73 znaků a 95. percentil 98. Limit, který porušuje polovina historie, není limit, ale šum, který učí lidi kontrolu ignorovat. Slovník scope se učí z historie, ne z ručně udržované tabulky cest.

Hook nemá vlastní pravidlo. commit-msg se ptá commit.validate. Stejného soudce čte scripts/ci/commit-policy přes historii v CI a stejného dostane agent přes MCP jako majordomus_commit_validate. Agent si tak může verdikt zjistit dřív, než commit zkusí, a nemůže dostat jiný.

pre-push

finish --check se ptá, jestli se práce tasku smí publikovat, a nic nezapíše. Výjimka je push, který nese jen refs/majordomus/*. To je úložiště kontinuity s podepsanými handovery a kontrakt by jinak odmítl handover právě pro task, který předává.

CI gates: co změna musí spustit

.ai/repo/ci/gates.yaml je celý model CI: které gates existují, který job je spouští a které třídy změněných cest je vybírají. scripts/ci-plan čte jen tenhle soubor. Workflow v .github/workflows/validate.yml je tenký adaptér nad plánem a nemá vlastní seznam cest. V repu Majordomusu je 74 gates ve 28 třídách cest.

# .ai/repo/ci/gates.yaml (výřez)
gates:
  - id: shell-lint
    job: structure
    always: true
    runs: scripts/ci/shell-lint
    summary: bash -n over every script, shellcheck over the tool, the scripts and the cases

  - id: prompt-privacy
    job: structure
    always: true
    runs: scripts/ci/prompt-privacy
    summary: no published or generated file is a prompt record, a rendering, or a copy of one

Pravidla plánovače

  • Gate s always: true běží v každém plánu.
  • Změněná cesta vybere gates každé třídy, na kterou sedí, ne jen první. Překryv může plán jen rozšířit.
  • Cesta, na kterou nesedí žádná třída, eskaluje na plný plán a plán ji jmenuje. Neznámá změna nikdy nespustí méně.
  • implies přidá gate k rodiči, requires přidá gate, bez kterého jiný neběží.
  • Push na master, plánovaný běh a PR s labelem ci:full spouští všechno.

Jak číst verdikt

Nulový exit code není verdikt. scripts/derive jednou skončil s nulou a přitom vypsal chybu: dva záznamy rozhodnutí sdílely identitu a oba vypadly z indexu. Všechno odvozené potom vzniklo bez nich. Odvozování teď běží pod --strict a chybová diagnostika běh ukončí.

Zelená historie není zelený strom. Master jednou nesl dvě vady, které shodily každou branch, jež ho mergovala. Jeho poslední dokončený běh předcházel commitu, který je zavedl, a všechny pozdější běhy stály ve frontě.

Gate, který neodpověděl, je queued, nikdy pass. Stejně tak test, který byl přeskočen.

Doctor a preflight

majordomus doctor: je harness zapojený?

  • vendorovaný balíček pravidel proti hashům v manifestu
  • řetěz každé doktríny od validátoru po CI
  • provider soubory proti jejich razítkům
  • zapojení každého vynucení, které policy jmenuje
  • schémata, layout, rozpočty, retence, graf pravidel, ADR, skills, prompty
  • log ztracených promptů je prázdný

Doctor detekuje, neopravuje. Regenerace je majordomus generate, nic se neopravuje na místě.

env preflight: co je tady dokázané?

Jedna typovaná hodnota o checkoutu: verdikt pro git, epizodu, briefing, task, handover, policy, pravidla, ADR, sdílený server, peery, zaznamenané testy, vynucení pravidel, projekce, generovanou dokumentaci a deploy.

Každý verdikt nese důkaz, na kterém stojí. Renderuje ji terminál při vstupu do adresáře, HTTP, MCP i Cockpit. Žádné rozhraní si stav nepočítá samo.

Verdikty preflightu:

verifiedactivefreshstaledegradedunavailablefailedunknownnot_applicable

První tři nejdou vyrobit bez důkazu. Kontrola, která nemá co ukázat, nemůže vrátit verified, jen unknown.

Důkaz je vztah ke stromu, ne časové razítko

Každý zaznamenaný běh testu nese runner, výsledek, commit, stav pracovního stromu a digest. Jestli je důkaz pořád platný, se počítá při čtení:

StavZnamená

inputs_unchangedněco se změnilo, ale ne vstupy tohoto testu

not_runtest existuje a neběžel

Pravidlo musí něco volat

Nejčastější vada harness není špatné pravidlo, ale pravidlo, které nic nespouští. V repu Majordomusu se našlo 17 nezávislých případů kontroly, která byla zdokumentovaná jako blokující, ležela na disku, šla spustit, a nic ji nevolalo. Proto se u každého pravidla způsob vynucení odvozuje z toho, co jeho blok x-majordomus skutečně jmenuje. Deklarovat se nedá.

RežimZnamená
dispatchedvalidátor, který spouští příkaz (check, finish, hook)
gatedtesty, které spouští CI gate
reviewedjen uvedený důvod, proč to stroj neumí ověřit; vynucuje člověk
declarativenic; pravidlo je jen text

majordomus doctor pro každou doktrínu projde řetěz a nahlásí první přerušený článek:

principle → doctrine → validator → enforcement point → exit code → test → CI → claim

Čte přitom zdrojový kód, ne popis, který o sobě registr dává. Gate rule-proof navíc vyžaduje, aby každé blokující pravidlo jmenovalo validátor, test nebo důvod lidské kontroly. Pravidla bez důkazu jsou v ratchetu, který se smí jen zmenšovat. Řeší se zapojením vynucení, nikdy přeřazením pravidla do poradní třídy. Podrobněji ve stránce o paměti a pravidlech.

Co harness stojí a co šetří

Harness přidává kontext, kroky a kontroly. Jestli se to vyplatí, je otázka měření, ne přesvědčení. Majordomus neuvádí žádné procento úspory, které nezměřil, a číslo o tokenech napsané do prózy odmítne majordomus economics check.

  • Jednotka: tokeny na úspěšně dokončený task. Běh, který ušetří tokeny tím, že selže, není úspora. Pár běhů se počítá jen tehdy, když oba prošly všemi branami úspěchu.
  • Kontrola a treatment: stejný task, stejný stav repa, stejný model, stejné nástroje, stejné akceptační testy, jednou s Majordomusem a jednou bez něj.
  • Dvě různá měření: celková úspora tokenů z živých párových běhů (jediné číslo, které může podpořit tvrzení o úspoře) a poměr výběru kontextu (co kontextový kompilátor vybral z toho, co považoval za relevantní). Druhé není celková úspora a každé rozhraní to říká.
Třída číslaZnamená
observedvrátil ho provider nebo jeho harness za běhu, zapsané beze změny
countedspočítané deterministicky z bajtů na disku pojmenovaným, připnutým tokenizérem
derivedaritmetika nad observed nebo counted
estimatedčíslo za něco, co nikdo nezměřil; nikdy se neporovnává ani nepublikuje
counterfactualco by mechanismus ušetřil, modelované, ne pozorované; nikdy úspora

Číslo spočítané z několika vstupů není nikdy silnější než nejslabší z nich.

Co Majordomus jako harness nedělá

Dělá

  • renderuje bootstrap pro každého providera z jedné policy
  • zapisuje hranice session do typovaných záznamů
  • drží scope, profil a závazky tasku
  • odmítá „hotovo“ bez splněného kontraktu
  • dává hookům, CI a agentovi stejného soudce
  • ukazuje, kdo na čem dělá
  • říká, co je dokázané a na jakém důkazu

Nedělá

  • nevolá model, nedrží SDK, nečte hodnoty credentials
  • nespouští nástroje agenta a nehlídá jeho oprávnění
  • nemá agenty, persony, role ani katalog workerů
  • neukládá transcripty a nic neshrnuje modelem
  • nemá embeddingy ani vektorové úložiště
  • nezamyká cesty: ohlášený scope je claim, ne zámek
  • neuvádí úsporu, kterou nezměřil

Jediný aktér, kterého Majordomus zná, je owner, volný řetězec v záznamu tasku. Supervizní nástroj, který přidává podstatná jména, se stává tím, co supervizuje.

Z toho plynou i limity. Je stavěný pro jeden repozitář, jednoho vlastníka a jednotky souběžných sessions. Nemá SSO, role ani oprávnění typu „tým X smí měnit pravidla Y“, neřeší sdílení pravidel napříč stovkami repozitářů a neumí ne-kódové artefakty, jako jsou HW specifikace nebo výsledky měření. Při devíti souběžných sessions na jednom stroji už je úzkým hrdlem stroj sám: disk, odvozování a fronta CI.

Co se dá přenést i bez Majordomusu

Na Majordomusu nezáleží tolik jako na tvaru řešení. Tohle funguje s jakýmkoli providerem, jakýmkoli CI a bez jediného řádku jeho kódu. Pořadí je zhruba podle poměru přínosu a ceny.

  1. Jeden zdroj instrukcí, generované projekce

    CLAUDE.md, AGENTS.md a GEMINI.md se generují z jedné šablony a CI hlídá, že nikdo neupravil výstup ručně. Bootstrap jen odkazuje, pravidla v něm nejsou.

  2. Gate, který neodpověděl, neprošel

    Chybějící verdikt je vlastní stav, ne pass. Stejně tak nulový exit code s chybou ve výstupu a přeskočený test. Stojí to málo a chytá to nejdražší omyly.

  3. Hook se ptá stejného soudce jako CI a agent

    Žádná logika v shellu hooku. Jedna kontrola, tři místa volání. Agent si verdikt může zjistit předem přes MCP nebo CLI.

  4. Hooky na hranicích session zapisují stav, nikdy neblokují

    Na konci session a před compaction se zapíše krátký stav: cíl, kde to je, další krok. Na začátku session ho dostane další worker. Selhání hooku se loguje, nezametá.

  5. „Hotovo“ je kontrakt, ne věta

    Seznam řádků, které musí projít: scope, ověřovací příkaz, závazky, gates. Selhání jednoho znamená, že se nic nezapíše. Výsledky jsou typované, no_match není failed.

  6. Každé pravidlo jmenuje, co ho spouští

    Pravidlo bez validátoru, testu nebo uvedeného důvodu lidské kontroly je text. Počet takových pravidel se smí jen snižovat.

  7. Repo říká, co agent nikdy nečte

    Tajemství, vygenerované soubory, velké fixtures a binárky jsou vyjmenované jednou a mimo dosah všech rozhraní, ne zakázané v instrukcích.

  8. Práce se ohlašuje dřív, než se staví

    Ať je to board, issue tracker nebo kanál: kdo na čem pracuje a jaké cesty se chystá měnit. Kolize objevená při merge je nejdražší možná.
