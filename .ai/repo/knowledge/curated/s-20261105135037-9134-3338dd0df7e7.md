# A Claude Code shell opened in the primary checkout carries its direnv exports (MAJORDOMUS_ROOT, MAJORDOMUS_SHARE, MAJORDOMUS_URL) into every worktree it works in; scripts/pages current then ran generate --check against the primary's tree and reported docs/generated/artifacts.* as differing right after a clean derive, while majordomus generate rewrote nothing. Every majordomus call, git commit and git push in a worktree needed env -u MAJORDOMUS_SHARE -u MAJORDOMUS_ROOT -u MAJORDOMUS_URL in front.

Observed as friction about bin/majordomus-cli in episode s-20261105135037-9134.

# Evidence

- `.envrc` is an adapter: `PATH_add bin`, and `majordomus env enter` exports what a shell needs; `bin/majordomus-env` line 29 exports `MAJORDOMUS_SHARE`; `lib/rust_bin.sh`, `mj_rust_share` (lines 287-294), answers `MAJORDOMUS_SHARE` when it is set and the tree's own `share/` only when it is not; `bin/majordomus-cli` exports that answer before it execs the executable. A shell opened in the primary checkout keeps the primary's values in every linked worktree it enters, so `generate --check` there judges the primary's tree.
- Curated note s-20261028215857-d010-fefd412fb59b met the same in the commit hook (MAJORDOMUS_SHARE naming the primary checkout's share in a worktree); on 2026-11-06 `scripts/pages current` reported `docs/generated/artifacts.*` as differing right after a clean derive for the same reason, and the #2845 repair met it at `git commit`.
- This run unset `MAJORDOMUS_ROOT`, `MAJORDOMUS_SHARE`, `MAJORDOMUS_URL` and `MAJORDOMUS_COMPLETION_BIN` before every command in the worktree and put the worktree's `bin/` first; no stale-artifact reading followed.
