Plán: milníky, issues a vlny

Plán řeší tři selhání: práce se vybírá z paměti, „hotovo“ se tvrdí místo dokazuje a plán žije na několika místech, která si odporují. Proto je v repu a status se do něj nikdy nepíše.

Milník: specifikace výsledku

  • problém, výsledek, současný a cílový stav
  • scope a ne-scope, kritéria, validace, požadované důkazy
  • jeden YAML v .ai/repo/project/milestones/
  • milník svoje issues nevyjmenovává, issue jmenuje svůj milník

Issue: ohraničený kontrakt provedení

  • cíl, proč, scope, depends_on, akceptační kritéria, validační příkazy
  • evidence_required a časová razítka started_at, verified_at, completed_at
  • volitelně serves: kterému kritériu intentu slouží
  • jeden soubor v .ai/repo/project/issues/

Ani jeden záznam nemá pole status. Kdo ho napíše, dostane chybu neznámého klíče. Stav se počítá při každém čtení z razítek, závislostí a důkazů. V repu Majordomusu je 35 milníků a 328 issues.

Odvozený stav issue

StavKdy platí
CANCELLEDcancelled: true
DONEcompleted_at je nastavené a každý token z evidence_required má důkaz
VERIFYimplementace je prohlášená za hotovou, důkazy ještě nestačí
ACTIVEstarted_at je nastavené a nic dalšího
BLOCKEDněkterá závislost není DONE
READYnic z předchozího

Razítko platí jen se svou pečetí (started_event, verified_event, completed_event, SHA-256). Ručně dopsané datum bez pečeti je chyba stamp_without_event. plan done odmítne issue, které není ACTIVE nebo VERIFY, a odmítne ho i tehdy, když chybí důkaz k některému požadovanému tokenu.

Vlny: co může běžet souběžně

Vlna je Kahnova vrstva issue v grafu závislostí. Vlna nula jsou issues bez závislostí, každé další je o vrstvu za svou nejhlubší závislostí. Vlny se počítají při každém čtení a nikde se neukládají. Závislosti říkají, co by mohlo běžet spolu. Scope říká, co bezpečně může.

majordomus plan validate           # schémata, reference, graf, konzistence stavu
majordomus plan status             # postup milníků a další proveditelné issue
majordomus plan ready              # issues se splněnými závislostmi
majordomus plan blocked            # issues, které čekají, a na co
majordomus plan waves              # topologické vlny
majordomus plan graph              # graf jako Mermaid
majordomus plan next               # jedno issue, které vzít teď
majordomus plan start <id>         # odmítnuto, pokud není READY
majordomus plan evidence <id> --covers tests --type test --command "…" --result "…"
majordomus plan done <id>          # odmítnuto, dokud chybí požadovaný důkaz

Projekce plánu na GitHub issues měla detektor driftu, který někdo napsal a nikdo nevolal. Projekce se za pět dní rozpadla na desetinu modelu a každý build byl zelený. Od té doby ji hlídá gate github-check a pravidlo project.github-projection-gated.

Intents: k čemu práce slouží

Otázka „kterému výsledku tahle změna slouží“ se dřív zodpovídala z promptu, který nepřežil svou session. Intent je typovaný záznam nad milníky: tvrzení, které má začít platit, invarianty, milníky, které ho realizují, a kritéria splnění. V repu jsou čtyři.

StupeňKdy platí
declaredněkterý jmenovaný milník neexistuje
plannedvšechny milníky existují
executingněkterý milník je ACTIVE, VERIFY nebo DONE
verifyingkaždý nezrušený milník je DONE
satisfiedverifying a každé kritérium je splněné
  • Kritérium splní jen aktuální důkaz. Průchozí běh, jehož commit je v této historii, na čistém stromu, s nezměněným hashem testu a bez změny čehokoli, co kritérium jmenuje. Průchod na špinavém stromu je stale, selhaný běh failing.
  • Uzavřená práce nepřebíjí důkaz. Issue označené za hotové, kterému důkaz odporuje, se nahlásí.
  • Issue se váže na kritérium polem serves: - <intent>#<kritérium>. Pokrytí kritéria je covered, weak, observed nebo uncovered.
  • Kritéria typu command a deployment zatím splnit nejdou (not_derivable). Je to napsané, ne zamlčené.

Vazba tasku na intent

Policy klíčem intent.binding určuje, co stojí odmítnutá vazba při start:

HodnotaChování
off nebo chybíptá se, jen když dostane --issue, --intent nebo --exempt
advisoryptá se vždy; odmítnutí ohlásí a task začne (nastavení repa Majordomusu)
requiredodmítnutá nebo nečitelná vazba task nezačne a plan start issue neaktivuje

Výjimka je třída deklarovaná v policy, uvedená s důvodem: --exempt maintenance --because "…". Třídy v repu jsou maintenance, emergency, integration a exploration. Chybějící intent sám o sobě výjimkou není.

majordomus intent list                 # každý intent s odvozeným stupněm
majordomus intent validate             # všechny nálezy, exit 10 při selhání
majordomus intent coverage             # která práce nese které kritérium
majordomus intent preflight --issue <id>   # smí práce začít
majordomus intent realization          # která práce realizuje který intent
majordomus intent explain <id>         # proč stojí tam, kde stojí

Worktrees: jedna větev, jedno místo

V den rozhodnutí (7. 9. 2026) mělo repo 53 registrovaných worktrees na nekonzistentních místech, z toho 16 dočasných od sessions. Pravidlo project.worktree-topology to nahradilo jednou větou: jméno branche je relativní cesta.

Šest postavení worktree

primarycanonicalmisplaceddetachedephemeralmissing

Pre-commit hook volá worktree guard. Ten odmítne (exit 10) commit feature branche odjinud než z jejího kanonického worktree, commit v primárním checkoutu na jiné než trunk větvi a commit z dočasného scratch checkoutu. Odpojené (detached) worktrees jsou vyňaté.

majordomus worktree                      # branch, postavení, kanonická cesta, neuložená práce
majordomus worktree create <branch>      # cesta se odvodí, nikdy nezadává
cd "$(majordomus worktree path <branch>)"
majordomus worktree migrate --plan       # co by se přesunulo; nic nemění
majordomus worktree migrate              # git worktree move, ověřený otiskem před a po
majordomus worktree topology             # celý obraz: kontejner, trunk, worktrees, diagnostika
majordomus worktree cleanup              # vypíše sloučené branche s čistým worktree; nic nemaže
majordomus worktree cleanup --remove     # odstraní je po opětovném změření každého

Migrace je bezeztrátová, nebo to není migrace: nikdy neresetuje, nestashuje, nečistí a nepřepisuje. cleanup --remove odmítne branch před svým remote, bez upstreamu, s neuloženou prací nebo s procesem, který má pracovní adresář uvnitř. Branche se nemažou nikdy.

Proč na tom záleží při víc agentech

  • Agenti se nesrazí na cestě. Session, branch a worktree se mapují předvídatelně a obnovená session odvodí worktree z branche místo důvěry v zapsanou cestu.
  • Jeden server a jeden board na worktree. Sdílený server patří checkoutu, board repozitáře se skládá ze všech.
  • Aktivní task je lokální. Claim v jednom worktree nepokrývá ostatní, proto existuje překryv a mesh.
  • Build: mezivýsledky kompilace se sdílejí, hotové artefakty zůstávají v target každého worktree. Sdílený CARGO_TARGET_DIR je zakázaný, protože by jeden build nahradil binárku, kterou jiný worktree právě spouští.

Osmnáct hodin po zavedení (8. 9. 2026) drželo 15 worktrees 104 GB build výstupu a na 926GiB disku zbylo 124 MiB. Tři subsystémy přitom nehlásily plný disk, ale špatný obsah. Studený target/ má 2,45 GiB na worktree. Od té doby se build odmítne pod 5 120 MB volného místa a build výstup sloučených worktrees se měří a uvolňuje.

Prostředí repozitáře: co platí při vstupu

Vstup do adresáře má za dobu jednoho cd odpovědět, jestli tu Majordomus opravdu platí, v jakém kontextu pracuju a co běží. Odpověď je jedna typovaná hodnota a banner v shellu je jen jeden z jejích rendererů. Stejnou hodnotu vrací majordomus env, GET /api/v1/environment a MCP resource majordomus://environment.

  • Každé pole má původ. Soubor, příkaz nebo konstanta, která ho rozhodla, a jestli se četlo teď, z cache, nebo se nepodařilo. Ukáže to env explain [POLE].
  • Dvě rozlišení. Plné (env, explain) staví index a píše cache. Rychlé (banner, export, enter) čte cache. Stav vrstvy je resolved, cached nebo unavailable.
  • env enter nikdy nebuilduje, nečeká a vždy skončí nulou. Vypíše přiřazení proměnných, banner na stderr a zajistí sdílený server. Změřená cena vstupu: 185 až 217 ms studená, 134 až 218 ms teplá při zátěži stroje 136.

Nové worktrees převezmou schválení direnv z primárního checkoutu jen tehdy, když je jejich .envrc bajt po bajtu stejný. Důvod: 9. 9. 2026 bylo 36 z 37 worktrees s .envrc zablokovaných direnvem.

Důkazy: co se opravdu spustilo

Cesta k testu je deklarace, že někde existuje důkaz. Není to důkaz. Důkaz je zaznamenaný běh se svým commitem. Ledger .ai/repo/evidence/ledger.json je trackovaný JSON, který drží poslední běh každého testu, bez historie a bez zachyceného výstupu.

Pole běhuObsah
test, runneridentita odvozená z cesty: test/cases/X.sh je suite:X, tests/X.rs je crate:X
outcomepass, fail, skip, timeout, error; dokazuje jen pass, neznámé slovo je error
commit, working_treeplné jméno objektu a clean, dirty nebo unknown
digestsha256: zdrojáku testu
origin, at, commandlocal, ci nebo release; čas v UTC; příkaz
 
MJ_TEST_REPORT=suite.tsv bash test/run.sh
majordomus evidence stamp --producer suite --report suite.tsv --out suite.provenance.json
majordomus evidence record --suite suite.tsv --provenance suite.provenance.json
git add .ai/repo/evidence/ledger.json   # nezacommitovaný záznam je lokální názor

majordomus evidence show [--state stale] [--check]
majordomus evidence claim <id>          # stav jedné garance
majordomus evidence proves <test>       # které garance test dokazuje

Jak se stav důkazu odvozuje

Jedna funkce, první vyhovující řádek vyhrává. Vstupy jsou přesně tři cesty: zdroj garance, její implementace a zdroj testu. „Změněno“ je diff od commitu běhu k posuzované revizi bez řádku ledgeru samotného.

PodmínkaStav
garance nejmenuje testno_test
cestu neumí spustit žádný runnerunrunnable
nic nezaznamenáno, nebo běh byl skipnot_run
fail, timeout nebo errorfailing
pass, ale commit běhu není v posuzované historii, git neumí porovnat, test má jiný hash, nebo se změnil vstupstale
pass, nic se nezměnilo a oba stromy jsou čistéproven
pass, nic se nezměnilo, ale některý strom je špinavý nebo neznámýinputs_unchanged
pass, něco se změnilo, ale žádný ze vstupůinputs_unchanged

Selhávající část udělá selhávajícím celek. Jinak rozhoduje nejslabší část, která může nést důkaz. proven a inputs_unchanged se nikdy neslévají do jednoho stavu.

Doktrína důkazů

  • Přeskočený případ není důkaz. Případ, který odmítne běžet, se zaznamená jako skip, nikdy jako průchod. Předtím desítky přeskočených případů končily nulou a zapisovaly se jako ok.
  • Binárka, která nespustila nic, neprošla. Nula testů nebo filtrovaná podmnožina je skip. Chybějící řádek s výsledkem je chyba.
  • Selhání má přednost před absencí.
  • Strom měří běh, ne člověk. Nezměřený strom je unknown a nikdy není proven.
  • Částečný běh zachová zbytek. Záznam jednoho testu nikdy nesmaže ostatní.
  • Lokální záznam zůstává lokální. --ledger local nepohne žádným verdiktem.

Ledger není odolný proti podvrhu a netvrdí to. Co poctivě přiznává dokumentace: stale se dřív počítalo jako podpora, dokud se nezměřilo, že na něm stojí 14 garancí proti nule skutečně proven. A první návrh dělal proven nedosažitelným, protože sám zápis do ledgeru strom zašpinil. Proto se řádek ledgeru z diffu vyjímá.

Garance a use cases

Garance je veřejné tvrzení o tom, co nástroj dělá: jedna věta se zdrojem, implementací, testem a statusem. Žijí v docs/CLAIMS.yaml, každá má stránku na webu a na ní se generuje i docs/SITE_CLAIMS.md. Soubor jim říká claims, web garance, aby se nepletly s claimy v meshi.

244garancí v CLAIMS.yaml
226ve stavu guaranteed
48use cases se scénářem
83 %spodní mez řádkového pokrytí

Zbylé garance jsou 10 plánovaných, 6 poradních a 2 zamítnuté. Dva gates běží v každém plánu:

  • claim-proof: test, který garance ve stavu guaranteed jmenuje, musí obsahovat id té garance. Baseline výjimek je prázdný.
  • evidence-check: posuzuje jen guaranteed. Podpořená znamená proven nebo inputs_unchanged. Dnes je to ratchet, který odmítá jen zhoršení. Baseline na origin/master nese 158 nepodpořených garancí a žádnou podpořenou, protože záznam důkazů z CI do trackovaného ledgeru ještě není zapojený. Dokumentace to říká otevřeně.

Use case: úkol, který nástroj předvede sám na sobě

Use case je úkol, který člověk s nástrojem dělá, jako jeden objekt: příkazy, pravidla, garance a scénář. Každý krok scénáře je skutečné volání bin/majordomus v jednorázovém repozitáři. Zralost nikdo nepíše, pozoruje se z důkazů:

draftdescribedexecutableverifiedguaranteed

guaranteed znamená ověřený scénář, kde je každá jmenovaná garance zaručená a každá jmenovaná doktrína vynucená. Repo vyžaduje, aby každý veřejný příkaz měl use case.

majordomus usecase run [id] [--live]     # spustí scénář; --live jen čte nad aktuálním repem
majordomus usecase coverage --check      # má každý veřejný příkaz use case?
majordomus usecase impact --base master  # které scénáře změna zavazuje spustit
majordomus usecase scaffold --missing    # kostry pro nepokryté příkazy

Pokrytí kódu

Jedno měření (cargo llvm-cov, bez testovacího kódu) pro řádky, funkce a regiony. Dvě spodní meze fungují jako ratchet: 83 % pro celý crate a 95 % pro doménu session a kontinuity. Diferenciální gate coverage-differential jde dál: každý řádek, funkce a region, který změna přidá nebo se ho dotkne, musí být pokrytý. Invariant je new_debt == 0 a starý dluh nesmí růst. Výsledky jsou PASS, FAIL, UNKNOWN a BLOCKED a jen první je zelený: spadlé měření nikdy není průchod.

Verze a vydání

Verze je napsaná na jednom místě: [package] version v apps/majordomus-cli/Cargo.toml. Jediný, kdo ji mění, je majordomus release bump. Shellový nástroj žádnou verzi nezná a čte vygenerovaný share/version.txt. Ručně psaný changelog neexistuje: skládá se ze záznamů vydání, datovaných ADR a git log.

Verze se měří, netvrdí

release analyze nečte slova v commitech. Porovná veřejný povrch capabilities posledního vydání (docs/generated/registry.json: id, druhy, vazby na MCP, HTTP a CLI, obě schémata) se stromem.

Změna povrchuCo dluží

něco přibylo nebo se rozšířilominor
povrch stejný, commity nesou změnypatch

Vstupy a výstupy se posuzují opačnými směry: rozšířený vstup je kompatibilní, rozšířený výstup taky, zúžení kteréhokoli ne. Konvenční commity jsou jen podpůrný důkaz. --level a --exact smí jít jen výš, než kolik měření vyžaduje.

Od tagu k vydání

  1. 1

    Bump a tag

    release bump, odvození projekcí, PR, merge na zeleném ci, release-verdict --commit HEAD, pak git tag a push tagu.

  2. 2

    Plán

    Tag se musí rovnat verzi v manifestu a ci otagovaného commitu muselo skončit úspěchem. Selhání je exit 10, nečitelný nebo běžící stav exit 12. Špatně napsaný tag stojí třicet sekund místo publikovaného vydání.

  3. 3

    Build

    Jeden archiv na podporovaný cíl, ověřený tam, kde vznikl. Šest platforem (macOS a Linux, ARM64 a x86_64, glibc i musl). Windows je uvedený jako nedostupný, s důvodem.

  4. 4

    Publikace

    Otisky, GitHub release, attestace, záznam vydání zapsaný z nahraných souborů, metadata na web a PR se záznamem. Jen tenhle job smí zapisovat do repa.

  5. 5

    Smoke

    Publikovaný instalátor nainstaluje právě vydanou verzi a ověří ji.

Co ověřuje instalátor

  • jen HTTPS; SHA-256 a velikost před rozbalením, nesoulad je fatální
  • URL artefaktu musí nést vlastní prefix vydání projektu
  • položky archivu s absolutní cestou, .., odkazy nebo zařízeními jsou odmítnuté
  • rozbalený nástroj se jednou spustí a musí ohlásit očekávanou verzi; instaluje se přejmenováním, bez sudo
  • provenance (GitHub attestace) se kontroluje, když je přihlášené gh; fatální je jen s MAJORDOMUS_REQUIRE_PROVENANCE=1

Co dokumentace výslovně neslibuje: podpis nad metadaty a bitově identické rebuildy.

Web

Po merge do masteru scripts/pages build vyrenderuje commitnuté projekce (starý hash zdroje odmítne a nic nepřegenerovává), site-deploy pushne výsledek na gh-pages a pages verify --commit SHA se ptá veřejného /build.json, dokud neservíruje právě ten commit. pages current je rychlá verze téže otázky pro pre-commit hook.

Verze v0.3.1, v0.5.0, v0.6.0 a v0.7.0 vyšly z commitů, jejichž ci selhalo. Nic to nekontrolovalo. Od té doby je release-verdict součástí plánu vydání.

Poučení z provozu

Každé pravidlo, gate a příkaz v Majordomusu má za sebou konkrétní incident. Tady je sedmnáct zdokumentovaných, s čísly a s tím, co se po nich změnilo. Vzorec je pořád stejný: něco bylo deklarované, nikdo to nevolal a nikdo se nedíval.

Vyzkoušej si · časová osa incidentů

    Registr capabilities zblízka

    Kapitola Jeden fakt, mnoho rozhraní říká proč. Tady je jak. Deklarace je makro capability!, jeden modul na soubor v apps/majordomus-cli/src/capability/builtin/. Na origin/master je 191 deklarací v 55 modulech: 183 má MCP nástroj, 187 HTTP routu a 105 cestu v CLI. Server k nim přidává každý objekt vrstvy .ai/ jako resource, proto hlásí přes dva tisíce capabilities.

    Autor deklaruje

    • id, kind (Query, Command, Resource), titulek, popis
    • typy vstupu a výstupu v Rustu, ze kterých vznikne JSON Schema
    • stability a exposure: jméno MCP nástroje, HTTP metodu a cestu, slova CLI
    • handler; volitelně .writes_repository() a .cancellable()

    Nástroj odvodí sám

    • modul, původ, dostupnost, viditelnost
    • efekt (read, process_state, repository_mutation) a z něj MCP anotace
    • benchmarkové případy z typu vstupu
    • příklady v OpenAPI
    • Kompilátor hlídá první vrstvu. Vstup bez benchmarkových případů se nezkompiluje. Handler s jinou signaturou, než deklarují typy, taky ne.
    • Registr hlídá druhou. Při sestavení sbírá všechny chyby najednou: duplicitní id, jméno nástroje, URI, routa nebo cesta CLI; routa mimo /api/v1/; command s jinou metodou než POST. capabilities validate skončí s exit 10 a seznamem.
    • Jeden executor. Každý transport volá Context::execute, takže odmítnutí je stejné v CLI, HTTP i MCP.
    • CLI se negeneruje. Strom příkazů je psaný ručně a kontroluje se proti registru oběma směry. Je to „kontrolovaná druhá deklarace“, ne projekce. Obecné majordomus run <id> dosáhne na jakoukoli capability.

    Přidání capability krok za krokem

    1. Napsat doménovou logiku a přidat blok capability! (nový modul navíc zaregistrovat).

    2. HTTP, OpenAPI, Swagger UI, MCP a formulář v Cockpitu se objeví bez dalšího kódu.

    3. Pokud má mít příkaz v CLI: varianta v clap, dispatch přes ctx.execute, textový renderer a spustitelný příklad. Dokud nesouhlasí, selže capabilities validate, test projekcí i gate projection-check.

    4. Spustit just derive a commitnout. Samotné majordomus generate nepřepíše data webu a pre-commit hook zastaralá data odmítne.

    5. Rozšířit pin test modulu a přidat behaviorální test. Pokud je to veřejná garance, přidat ji do CLAIMS.yaml s důkazem.

    6. Verze: release analyze změří, co změna povrchu dluží.

    Cockpit a UI: stejný model v prohlížeči

    Cockpit běží na stejném sdíleném serveru jako MCP, na /cockpit. Stránky renderuje server v Rustu bez šablonovacího enginu a každá je kompletní HTML dřív, než se spustí jakýkoli skript. JavaScript je jen vylepšení: paleta příkazů, spouštěč capabilities, grafy, živý proud událostí. Zabezpečení: přísné CSP bez vzdáleného originu, výchozí loopback, stránky jen na GET.

    majordomus ui: povrch pro člověka

    ADR 0135 (přijaté 11. 10. 2026) dělá z /ui primární povrch ve slovníku dodávky: issues, pull requesty, roadmapa, dodávka, nasazení, důkazy, governance. Cockpit zůstává technickou vrstvou pod ním. Obojí je stejný server a stejný executor, bez vlastního úložiště. Starší servery /ui neznají a vrátí 404.

    Executions: volání, které jde sledovat

    Execution je volání capability, kterému proces dal identitu, aby se dalo sledovat místo čekání. Má životní cyklus, vstup tak, jak byl uložen, typované události a výstup nebo chybu. Nepřežije proces, který ji přijal: žádná trvalá fronta, opakování ani plánovač.

    Každá událost má obálku s verzí protokolu, hustou sekvencí od jedné, časem, typem a daty. Klient musí neznámé typy ignorovat.

    execution.created.queued.started.progress.step.started.step.completed.log.diagnostic.cancelling.cancelled.completed.failed
    majordomus run <id> [--input JSON]        # spustí capability jako execution
majordomus executions list
majordomus executions events <id> --after N
majordomus executions cancel <id>

POST /api/v1/executions/start    GET /api/v1/executions/events
GET  /events?execution=<id>&after=<seq>   # WebSocket, heartbeat 20 s

    Limity jsou napsané: 200 zapamatovaných executions, 2 000 událostí každá, 4 běžící současně, 64 živých kanálů. Citlivé vstupy se podle schématu redigují.
