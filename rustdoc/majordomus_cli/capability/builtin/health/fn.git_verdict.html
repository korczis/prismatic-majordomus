Expand description

The git check: the checkout git describes, or — for a deployed build with no checkout to ask — the commit the executable was built from.

A hosted deployment receives a tree assembled from the deployment object, never a clone, so git there has nothing to answer and the check read unknown for a process whose commit is known exactly: the build identity names it, and /api/v1/live already serves it. Only a process that reads its layer from the filesystem (the deployed command lines pass --discovery filesystem) and was built from a named commit falls back to that identity; a version-control checkout git cannot read stays unknown, because there the build commit says nothing about the tree being served. A dirty build is a warning, as a dirty working tree is.

use majordomus_cli::capability::builtin::health::git_verdict;
use majordomus_cli::capability::builtin::health::HealthStatus;
use majordomus_cli::git::GitState;

let none = GitState::Unavailable { reason: "git: not a git repository".into() };
let (s, d, by) = git_verdict(&none, "filesystem", "0123456789abcdef0123", Some(false));
assert_eq!(s, HealthStatus::Ok);
assert!(d.contains("0123456789ab") && by.contains("build identity"), "{d} / {by}");

// a checkout git cannot read is still not known, whatever the executable was built from
let (s, _, _) = git_verdict(&none, "vcs", "0123456789abcdef0123", Some(false));
assert_eq!(s, HealthStatus::Unknown);
