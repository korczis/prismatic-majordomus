Nasadit web ručně

Publikujte web na GitHub Pages z terminálu, jediným skriptem, který spouští workflow Pages, když čekání na frontu Actions není přijatelné.

majordomus://skill/deploy-site •aktivní verze 1webdeployevidence

pracovník potřebuje

  • commit k publikaci, checkoutnutý s čistým stromem a obsažený v origin/master
  • zola, node_modules (npm ci) and, for the full gate, cargo; or, without cargo, the rustdoc, ui-snapshot and cockpit-snapshot artifacts of the same commit's Pages run
  • slovo operátora v této relaci, že web má jít nyní živě

zanechá postup

  • commit v gh-pages pojmenovávající zdrojový commit, nebo odmítnutí pojmenovávající kontrolu, která jej zastavila
  • kontrolní bod zaznamenávající nasazení a commit, který publikovalo

Účel

Dostat web živě hned, ne po frontě Actions, aniž by vznikl druhý způsob publikace. Jeden příkaz, ten samý, který spouští workflow Pages, a nasazení je poté vidět: commit gh-pages i patička webu uvádějí zdrojový commit.

Kdy použít

Operátor to řekne, slovy, v této relaci. Merge do masteru už nasazuje přes workflow; ruční nasazení je pro případy, kdy je to příliš pomalé, nebo je workflow červené z důvodu, který není web (benchmark runner, job pro macOS), a web sám je zelený. Nikdy nenasazujte proto, aby červená kontrola vypadala zeleně.

Postup

1. Předpoklady

  • Stojíte na commitu k publikaci, s čistým stromem, a origin/master jej obsahuje. Náhled nesloučené práce je možný pomocí --any-ref; patička pak jmenuje onen commit, takže si ho nikdo nespletl s masterem. Řekněte to, když to děláte.
  • zola, node_modules (npm ci) a pro plnou kontrolu cargo jsou přítomny; skript říká, co přeskakuje.
  • GitHub Pages poskytuje větev gh-pages. Jednou na repozitář: scripts/site-deploy --configure-pages (vyžaduje gh); poté nastavení zůstává.

2. Nasazení

scripts/site-deploy --dry-run      # gate, build, check; shows the gh-pages commit it would push
scripts/site-deploy                # the same, then pushes gh-pages
scripts/site-deploy --probe        # add the browser probe (every route at 320, 390, 1280 px)

just site-deploy je tentýž příkaz. Kontrola je: odvozená data synchronní, generované projekce synchronní (majordomus generate --check), site-build, site-check. Selhání kdekoli zastaví před pushem, s důvodem; opravte zdroj, nikdy výstup.

Build webu neskládá snapshot UI (ADR 0141): workflow pages jej zapisuje v samostatném jobu a jeho deploy job jej umístí. Deploy z terminálu takový job nemá, takže skript odmítne postavený web, kterému chybí snapshot, jejž model publikace deklaruje (scripts/pages snapshots je vypisuje), nebo který nese snapshot přečtený při jiném commitu, a vypíše příkazy, které jej umístí (project.the-published-ui-is-the-trunks). Po tomto odmítnutí je web už postaven a zkontrolován, proto zapište snapshot při tomto commitu, zkopírujte jej na jeho mount a publikujte, co tam je:

majordomus web report ui-snapshot
mkdir -p site/public/ui && cp -R target/web/ui-snapshot/. site/public/ui/
scripts/site-deploy --skip-build

3. Without cargo: the artifacts of the commit's Pages run

The parts of a deploy that need cargo are the crate's reference and the two snapshots, and the Pages run of the commit already built them as the artifacts rustdoc, ui-snapshot and cockpit-snapshot. When that run produced them but did not publish (a step bound killed its deploy job, or the queue is too slow), do the deploy job's steps by hand with them instead of building from source. The operator's word is still the precondition, and so are these:

  • A fresh clone at the commit, with full history and tags, because the link check decides commit and tag links (scripts/pages checkout --verify says whether it can), and npm ci in that clone: a node_modules borrowed from another checkout can lack a package the build loads.
  • A case-sensitive volume for the clone and for TMPDIR, while the UI snapshot holds two paths that differ only in case (I3447): on the default case-insensitive APFS of macOS the artifact does not extract whole. A sparse image formatted Case-sensitive APFS with hdiutil create serves.
sha="$(git rev-parse HEAD)"
run="$(gh run list --workflow pages.yml --commit "$sha" --limit 1 \
  --json databaseId --jq '.[0].databaseId')"
for a in rustdoc ui-snapshot cockpit-snapshot; do
  gh run download "$run" -n "$a" -D "target/web/$a"
done
npm ci
scripts/pages evidence --commit "$sha"     # site/data/evidence.json, as the deploy job writes it
scripts/pages build                        # reads target/web/rustdoc; no generation, no cargo
scripts/pages check
scripts/pages snapshots | while IFS="$(printf '\t')" read -r id mount artifact _; do
  [ -n "$id" ] || continue
  mkdir -p "site/public$mount" && cp -R "$artifact/." "site/public$mount/"
done
scripts/site-deploy --skip-build

Order matters: the reference is in place before the build reads it, and the snapshots are placed after the check, which judges the site's own pages. scripts/site-deploy still refuses a snapshot read at another commit, so an artifact of an older run cannot go live under this one's name. Verify the UI and the Cockpit as well as the site (step 4).

4. Ověřte

GitHub servíruje novou hlavu branche za zhruba minutu. Nasazení je skutečné, když živý web pojmenovává commit, který jste publikovali:

curl -s https://majordomus.dev/ | grep -c "/commit/$(git rev-parse HEAD)"   # 1

scripts/pages verify-ui --commit "$(git rev-parse HEAD)" asks the same of the UI at /ui/: its snapshot names that commit and every page it lists answers; scripts/pages verify-ui --surface cockpit --commit "$(git rev-parse HEAD)" asks it of the Cockpit.

Pak otevřete stránku, kterou jste změnili.

Pro čtení z druhé strany — díváš se na živý web a chceš vědět, co to je — git log -1 --format='%an %s' origin/gh-pages pojmenuje zdrojový commit a řekne, kdo jej publikoval: github-actions[bot] pro push do masteru, člověk pro ruční nasazení. Náhled publikovaný přes --any-ref zůstává živý, dokud jej další push do masteru nepřepíše, takže živý web, který není master, je očekávaný, ne chybný.

5. Nedělejte

  • Cokoli pod site/public/ nebo na gh-pages upravovat ručně: obojí jsou výstupy. Chybná stránka se opraví ve svém zdroji a znovu nasadí.
  • Nasadit ze špinavého stromu s --allow-dirty, „jen se podívat“: patička by jmenovala commit, který neobsahuje to, co je živé.
  • Obejít odmítnutou kontrolu. Řádky REFUSE jsou důvody, proč by nasazení uvádělo v omyl; skript skončí s kódem 10 a nic nepushne.

Výstup

Commit, který je nyní živý, pojmenovaný, a větev, do níž byl pushnut; nebo, když kontrola odmítla, řádek REFUSE, který ho zastavil, a zdroj, který je třeba opravit. Zaznamenejte deploy tam, kde úloha drží své poznámky (majordomus checkpoint), se zdrojovým commitem, aby se na to, co je živé, dalo později odpovědět bez dotazu na GitHub.
