## 148. Markdown is drawn by one renderer in the executable, and every drawing on a served surface can be acted on

### Context

Most of what the layer holds is Markdown: rules, decisions, prompts, skills, use cases. So is
most of what a forge says about a pull request, an issue or a release. The served surfaces
showed all of it as the file it is — a `<pre>` of the source — and the short prose a record
carries in a field was drawn by a hand-written scanner in `ui/prose.rs` that knew backticks,
double asterisks and links and nothing else. The owner asked, on 2026-10-12, for Markdown to
be rendered in place, with one look, wherever it is read — what the repository holds and what
is pulled from the forge alike — with diagrams drawn, and then for every graph, chart and
visualisation to be interactive and clickable, enforced so that it "can never happen" that
one is not.

Two things were true of the surfaces that day:

- **Two ways to draw prose, and neither was Markdown.** The scanner drew four constructs; the
  object page drew none. A third would have arrived with the first forge body.
- **Two kinds of drawing, and nothing said which a new one had to be.** The relationship
  graphs of the UI and the Cockpit and the train graph take a press on a node to its record.
  The overview's activity field and the 3-D topology draw the same records and bind nothing.

The surfaces serve a strict content policy: scripts from the origin only, no inline script, no
network request to a third party. They are also published as a static snapshot (ADR 0141), so
whatever is drawn has to be drawn in the HTML the server writes, not by a script at reading
time.

### Decision

#### One renderer, in the executable

`markdown::render` draws a body and `markdown::inline` draws a line. Both parse with
`pulldown-cmark` (default features off: no HTML writer, no SIMD, no `getopts`) and draw the
parser's events through the element builder every page already uses, so there is one escaping
routine on the surfaces and this module is not it.

What the renderer refuses is part of the decision:

- **Raw HTML is text.** A body is data. An element a body wrote is shown as the characters
  it is; a comment is dropped.
- **An address is followed only when it is known.** A web address is a link. A path to
  another file of the layer is a link to that object's own page, resolved by the caller
  through the capability the page already asks. Anything else — `javascript:`, a path that
  resolves to nothing — is the text, marked as not linked, and never an `href`.
- **An image is named, not fetched.** The policy would refuse it, and a body that makes a
  reader's browser ask a third party for something is a body that reports the reader.
- **A word is a link when the caller says it is a record.** The inline form takes a resolver
  for bare words, which is how an issue or milestone id in a sentence becomes a link without
  the renderer knowing what a plan is.

The typography is one set of `.mj-md` classes in `share/design/primitives.css`, which the
Cockpit, the UI and the published site import. A body has one look wherever it is read.

A client-side renderer was the alternative and was refused: it would draw nothing in the
published snapshot, would be a second escaping routine in a second language, and would need
either an inline script or a body smuggled through an attribute.

#### A diagram is drawn from the source, which stays

A fenced `mermaid` block is written by the server as its source, marked, with the links the
caller resolved for the names in it (`data-mj-links`). A script draws the figure when the
vendored library is there, wraps each named node in the anchor the server gave it, and leaves
a control that shows the source again. Without the library, or without script, the source is
what is read. Mermaid is vendored and lazy like every other drawing library, and runs at
`securityLevel: 'strict'`.

#### A drawing is acted on, or it is a named debt

`project.a-visualisation-is-interactive` states it; `scripts/ci/visualisation-check` holds it
in every plan. A served script that loads a vendored library at run time must bind a way from
its marks to somewhere. The two drawings that bind nothing are listed in
`.ai/repo/visualisation-baseline.txt`, which is a ratchet: an unlisted picture fails, and so
does a listed one that became interactive or is gone, until the line is removed.

The gate is deliberately a reading of the scripts and not a browser run. It costs
milliseconds, so it can be in every plan; the browser half — that a press on a node of each
drawn graph arrives at the record — belongs to the UI audit, which already drives every page.

### Consequences

- A rule, a decision, a prompt or a skill is read on its own page as the document it is, with
  its links leading to the objects they name.
- A forge body — a pull request's description, a release's notes — has one function to go
  through, and it is safe to give it to: nothing a body contains is executed, fetched or
  followed without being known.
- `ui/prose.rs` no longer parses anything. It only says which words are records.
- The executable gains one dependency (`pulldown-cmark`, with `unicase`) and no feature of it
  that writes HTML.
- A new chart or graph cannot arrive as a picture. Its author binds a way through, or adds a
  line to a list a reviewer reads.
- Two drawings are a named debt. Paying it — the activity field's cells and the topology's
  nodes leading to their records — removes both lines.

### What this does not decide

Which charting library draws quantities, and the sortable tables, are the next slices; this
decision only fixes what any of them must do to be on a surface at all. Highlighting of code
blocks is not done: a highlighter in the executable is a dependency several times the size of
the parser, and one in a script is a second renderer.
