# an evolve run on 2026-11-17 was told to take numbers with majordomus plan allocate and to announce them with majordomus_announce, but the command line has no plan allocate (the form is mesh allocate <kind> --session <s>, and the MCP tool majordomus_plan_allocate), and its provider's MCP server had not connected, so both had to be spoken to the worktree's own server over MCP's HTTP transport (initialize, then tools/call with the Mcp-Session-Id), POST /api/v1/peers/announce being refused without a caller; the skill (v6, step 3) now says so

Observed as friction about .ai/repo/skills/evolve/SKILL.md in episode s-20261117224745-7fdd.

- `file:.ai/repo/skills/evolve/SKILL.md`
- `file:docs/MCP.md`

# Evidence

- `majordomus plan allocate` on this checkout's executable (1.1.0, master's crate): `error: unrecognized subcommand 'allocate'`; `majordomus mesh allocate --help`: `Usage: majordomus mesh allocate [OPTIONS] --session <SESSION> <KIND>`. The MCP tool `majordomus_plan_allocate` (`plan.allocate`) answered I4653, I4654 and I4655 with `at_least` 4635, each with its `id:issue/<n>` claim.
- The session's provider reported its majordomus MCP server as failed to connect. `docs/MCP.md`: `POST /api/v1/peers/announce` is refused (422) over plain HTTP, having no caller. `initialize` over `POST http://127.0.0.1:<port>/mcp` answered an `Mcp-Session-Id`, and `tools/call` of `majordomus_announce` with it put the run's ids and paths on the board.
- This change: the evolve skill, version 6, step 3, names the allocator and its command-line form and says how to announce and allocate when the MCP server did not connect. The cases that name the skill (`grep -l 'majordomus-skill:.*evolve' test/cases/*.sh`) were run before the commit.
