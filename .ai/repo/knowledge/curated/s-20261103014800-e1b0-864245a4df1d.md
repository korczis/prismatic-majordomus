# a train top composed by hand with git commit over a hand-written MERGE_HEAD lost its base parent: git reduces redundant parents unless MERGE_MODE says no-ff, and master was dropped because a member already contained it, so the top's first parent was a member instead of master

Observed as friction about .ai/repo/skills/integrator/SKILL.md in episode s-20261103014800-e1b0.

# Evidence

- `file:.ai/repo/skills/integrator/SKILL.md`

# Evidence

Reproduced with git 2.43.0 in a scratch repository: commit A, branch m with commit B on A, back on A,
B written to .git/MERGE_HEAD, then `git commit --no-edit`:

    without MERGE_MODE:                       parents B           (A dropped: reduce_heads)
    MERGE_MODE written with echo (newline):   parents B           (the file must be exactly "no-ff")
    MERGE_MODE written with printf no-ff:     parents A B

Met on 2026-11-02 when train 22b's first top, composed by chained merge-tree on master c98e5d3f81f
and committed over MERGE_HEAD, came out with the three member heads as parents and no master,
because member #2906's head already contained c98e5d3f81f. The recomposition on 5bc72353c8d kept
master as first parent only because no member contained it.
