Declare once, derive every interface

A capability is written in one place, and the command line, the HTTP API, the OpenAPI document, MCP, the Cockpit, the reference and this website are projections of it.

What it does

An executable capability is one capability! block in its module's file, with a typed input, a typed output and a handler. A declarative object — a rule, a skill, a decision, a use case, an operational moment, a feature like this one — is one file under .ai/ whose kind and schema the tool distribution declares. The registry is built from both on every start, validated and fingerprinted, and everything a person or a program reaches is a reading of it: the MCP tools and resources, the routes under /api/v1/, the OpenAPI document and the Swagger UI over it, the words after majordomus, the benchmark targets, the Cockpit's pages, the generated reference under docs/generated/, and the datasets this website is rendered from.

majordomus generate writes every committed projection from one plan; majordomus generate --check refuses a tree in which any of them differs from what the sources produce, and CI refuses to merge or deploy such a tree. The feature you are reading is itself one file under the layer, and the surfaces listed beside it were derived from that file rather than typed onto this page.

What it does not do

It does not discover a capability nobody declared: a handler without a capability! block is not exposed anywhere, by design. It does not infer a relation from a name or a substring; every reference a file makes is typed and resolved against the thing it names, and one that resolves to nothing fails validation rather than becoming a link to nothing.

  • ○declared status: guaranteed ○recorded evidence: not run Every generated artifact declares the document it projects, the encoding it is written in, the schema its content satisfies and its source, and a structured document is written in every encoding it is committed in from one value test/cases/52_generated_artifact_typing.sh
  • ○declared status: guaranteed ○recorded evidence: not run The committed projections, the OpenAPI document, the capability reference and the allow-lists, are regenerated from the registry and the schemas, and generate --check refuses a stale one test/cases/76_capabilities_projections.sh
  • ○declared status: guaranteed ○recorded evidence: not run What the tool knows about itself is written once and derived everywhere else, and a second copy is a test failure test/cases/28_no_hardcoded_values.sh
  • ○declared status: guaranteed ○recorded evidence: not run A commit whose derived data is behind its canonical inputs is refused before it exists, and a repository that unwires that gate is a doctor failure test/cases/56_derived_current_gate.sh
  • ○declared status: guaranteed ○recorded evidence: not run Every committed derived artifact of the repository is regenerated by one command in dependency order and checked by one read-only command that names every stale artifact, a second regeneration on a clean tree changes nothing, and no derived file records the commit it lands in test/cases/400_derivation_is_one_graph.sh

The rules that hold it

  • ✕blocking One canonical declaration; modules compose capabilities; the root composes modulesproject.rust-canonical-declaration
  • ✕blocking Derived files are regenerated, never editedproject.derived-files-regenerated
  • ✕blocking A generated artifact declares its document, its encoding, its contract and its sourceproject.generated-artifacts-are-typed
  • !advisory Derived state is computed once per state versionproject.derived-once

The decisions behind it

  • adr-0002A canonical capability registry, with MCP, HTTP, OpenAPI, Swagger UI, the CLI and the reference as projections accepted
  • adr-0004One canonical declaration, composed modules, derived projections, and performance as evidence accepted
  • adr-0005One projection plan over the canonical inputs, named owners for every truth, and the site as a view of the registry accepted
  • adr-0023Product features are objects of the layer, and the landing page is a projection of them accepted

Using it

The commands that run it

  • majordomus update setup

    Regenerate every provider instruction file from the one policy, deterministically.

  • majordomus doctor inspect · read-only

    Is Majordomus itself healthy, and is every enforcement it declares actually wired here?

From the executable's command line

The synopsis of each, as the executable's own help prints it.

  • majordomus capabilities list [OPTIONS]

    Every capability, one line each, with its projections

  • majordomus capabilities describe [OPTIONS] <ID>

    One capability by canonical id: schemas, provenance, every projection

  • majordomus capabilities projections [OPTIONS]

    Where each capability is projected, and every claim its surface does not answer

  • majordomus product list [OPTIONS]

    Every feature, narrowed by any filter, with the surfaces derived for each

  • majordomus product show [OPTIONS] <ID>

    One feature in full: what it is made of, resolved, and everything derived from that

  • majordomus product domains [OPTIONS]

    The domains of the product, each with the stable features that name it and what they add up to

  • majordomus product matrix [OPTIONS]

    Every feature against every interface, and every module, command and kind against the features that name it

  • majordomus product providers [OPTIONS]

    Every provider the tool has an adapter for, with what this repository does with it

  • majordomus product validate [OPTIONS]

    Every finding over the model; exit 10 when any is an error

  • majordomus quality report [OPTIONS]

    Measure the crate and report every finding, with the rule it breaks and what to do about it

  • majordomus quality rustdoc [OPTIONS]

    Judge the crate's rustdoc tree against the crate: every page present, HEAD's, nothing broken or leaked
