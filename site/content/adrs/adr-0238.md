## 238. The plan is reconciled with merged work through plan.transition, and an issue authored or executed twice is refused where it collides

### Context

ADR 0166 made delivery a fact, inferred from git and the forge, and kept stamps as acts. A merge
is not acceptance, so inference never writes a stamp. `plan.drift` names each disagreement
between the two, with the command that settles it. One adopter repository showed, on
2026-11-25, what that leaves to a worker. The repository is a fork with an `upstream` remote,
several concurrent agent sessions, and a commit grammar with no room for an id in the subject.

- **Merged work stayed unrecorded.**
  - Drift reported seven `merged_not_recorded` issues, and a milestone read 0/13 while its work
    had merged.
  - Two agents settled the issues by hand, one `plan start|verify|evidence|done` at a time, over
    hours.
  - Their pull request carried a table: each issue, the merge that delivered it, and the
    verification that each one still had to run.
- **Merged was not accepted.** Every one of those issues still needed a run of its declared
  validation before `done`. One criterion was covered by no CI job.
- **The forge source read the parent repository.**
  - `gh repo view` without an argument resolves a fork with an `upstream` remote to the parent,
    and `gh pr list` resolves the same way. So `plan drift` reported "174 open pull requests" of
    the parent and judged every `pr_open` against it.
  - The fork's own pull requests were never read.
  - Every `repos/{repository}` call that follows (`GhForge::observe`) inherits the parent too.
- **One delivered issue had no edge.**
  - A commit inside another pull request delivered it. No subject, title, branch or slug named
    it. Subjects of the form `Keyword: [Component] details` never carry an id.
  - Delivery reads a commit's subject and never its body (ADR 0166). That is right for prose. But
    it leaves a repository with such a grammar no edge that it can write on purpose.
- **Issue ids collided.**
  - Board reservations did not stop peers taking an id, and the remedy was "check master, renumber
    yours, re-stamp".
  - `plan.allocate` (I3040) prevents a collision only for a caller that uses it. Across linked
    runtimes, two claims made before they sync are both admitted. Nothing detects a collision that
    has already happened.
- **One issue was executed twice.**
  - The second session's picker ran before the first session's pull request existed.
  - Only I4356 refuses a `start --issue` on an exclusively claimed issue, and only for a mesh
    claim. A branch or an open pull request is not one.
  - I3971 makes `plan next` pass such an issue over. Nothing tells `start`, a push or a pull
    request.
- **A VERIFY issue was not a finding.** A VERIFY issue whose merge landed and whose evidence is
  missing is no drift class (`drift.rs`, the `match` in `judge`). "A merged pull request claims
  it but its acceptance is unmet" was invisible.

The owner asked for these lessons as generic Majordomus work. The question and answer are
recorded verbatim in
`.ai/repo/knowledge/curated/owner-answers-2026-11-25-generic-lessons-of-an-adopter-session.md`.

### Decision

#### 1. The forge is read for the trunk remote's repository (I4777)

- **Resolve the repository from git.** `GhForge` derives `owner/name` from the URL of the remote
  that the trunk tracks (`origin` unless the trunk names another). It accepts the
  `git@github.com:o/n(.git)`, `ssh://git@github.com/o/n` and `https://github.com/o/n(.git)` forms.
- **Pass it explicitly.** It calls `gh repo view <owner/name>` and runs every other call with
  `GH_REPO=<owner/name>`, so `gh pr list` and every `repos/{repository}` call read the same
  repository. An inherited `GH_REPO` is overridden. The same pin applies to the drain, the
  deployment observation, the proof and the monitor, the other places that run `gh`.
- **Fall back openly.** A remote URL that names no GitHub repository keeps gh's own resolution,
  and the source says so.
- **Check the cache.** The recorded observation already carries `repository`. Delivery reads a
  recorded observation only when that field equals the trunk remote's repository. Any other
  observation is `unread`, with both names, never a reading of the wrong repository.

#### 2. `Delivers:` trailers are an edge (I4773)

- **What counts.** A commit names an issue when the final trailer block of its message, the
  `git interpret-trailers` form, holds `Delivers: <id>[, <id>...]`, and when that id is a
  declared issue.
- **Recorded as a claim.** The edge is `via: trailer`. It is an author's explicit claim, shown as
  such.
- **Prose stays unread.** The body is still never read as prose. A trailer is a field, not a
  mention.
- **Planning rule.** The planning-only rule (I2749) applies to it as to a subject: a commit that
  changes only plan records delivers nothing.

#### 3. `plan.reconcile` proposes the moves a merge supports and applies them only through `plan.transition` (I4773)

**What it reads.** A read-only capability, a view over the delivery report that `plan.drift`
reads, not a second inference. It considers every issue whose stage is `merged`, `released` or
`deployed` and whose status is READY, BLOCKED, ACTIVE or VERIFY.

**What it answers.** For each such issue:
- `proof`: the merge, pull request, `via` and age, from delivery.
- `moves`: the `plan.transition` calls the plan admits now, in order. Each is judged by
  `plan::check` against the plan as the previous moves leave it:
  - READY → `start`. A merge proves that execution began, and nothing more.
  - `done` only where the issue's `evidence_required` tokens are covered by evidence the record
    holds, and where every covering entry was recorded at or after the newest merge that names
    the issue. Evidence older than the delivery is not evidence of it. The done guard decides
    completeness; reconcile adds only this freshness condition.
  - `verify` is never proposed. It is a worker's attestation that the implementation is
    complete. A merge can be one slice of a split issue, and nothing in git says otherwise.
- `refused`: the move the plan does not admit, with the guard's own reason:
  - a BLOCKED issue's `start` names what it waits on;
  - a `done` short of evidence names the tokens.
- `evidence`: each required token, covered or missing, and the issue's declared `validation`
  commands. These are what a worker runs to cover a missing token.
- `acceptance`: each criterion, as `unjudged`. Reconcile never judges prose, and it never reads a
  merge as a criterion met.
- `class`:
  - `recordable`: `start` is proposed and `done` is not;
  - `acceptable`: `done` is admitted;
  - `held`: BLOCKED, with no move;
  - `unaccepted`: merged, ACTIVE or VERIFY (or proposed to start), evidence missing or older than
    the merge;
  - `pending_pr`: another open pull request still names the issue. The work is still landing, so
    nothing is proposed.

**Preconditions.** A proposal over a forge that was not read, or a cached observation of another
repository, is listed but marked `unsettled`. `--apply` refuses it (exit 12), because "no open
pull request names it" cannot be established.

**`--apply`.** It performs the proposed `start` moves, one `plan.transition` per move, and
`--done` adds the admitted `done` moves. It re-reads the plan between moves, because a stamp
written by the previous move is the next one's guard. A `start` is stamped at the time of the
run, not of the merge, and the output says so; the proof stays in the report.
- A refused move stops that issue and not the batch.
- It writes no evidence, edits no field, and passes no `--covers`.
- It is idempotent: a second run finds nothing to move.
- Exit codes: 0 when every move was written, 10 when one was refused, 12 when the proposal was
  unsettled.
- Dry run is the default.

#### 4. `merged_unaccepted` is a drift class that reports and never refuses (I4773)

A VERIFY issue whose delivery is merged or later and whose evidence is incomplete is
`merged_unaccepted`. Its remedy is `majordomus plan evidence <id> --covers <token>` for each
missing token. It is `Reported` under every gate. Nothing else that drift decides changes.

#### 5. `plan.collisions` refuses an issue authored or executed twice (I4775)

**The answer.** A read-only capability over git refs, the recorded forge observation and the mesh
board. Each finding names its holder: the ref, the pull request, its head branch, and the mesh
session when there is one.

**Class `id_reused`** (refused).
- What it detects: an issue record that the head adds, relative to its merge-base with the trunk,
  that another line of history also added after that merge-base with different content. The
  other line may be the trunk or any local or remote-tracking branch.
- Why it is not noisy: a record inherited from the trunk is present at the merge-base and is
  never a finding. A record with the same blob on two refs is the same record carried twice, and
  is not one either.
- Remedy: `majordomus mesh allocate issue`, then renumber the head's record.

**Class `claimed_elsewhere`.** The head executes an issue only when its branch names it (the
I1405 rule or the slug), or when the caller names it (`--issue`).
- Changing a record's stamps is recording, not execution. A plan-records pull request, and
  `reconcile --apply` itself, executes nothing.
- A head whose change is planning-only (the I2749 rule) executes nothing.

The holders, and what each one does:

<div class="overflow-x-auto" tabindex="0">

| holder | verdict |
|---|---|
| another open pull request whose head branch names the issue, or whose title names it among at most three ids | refused, unless this head's pull request says `Supersedes #N` or the other says `Superseded by` it (`declared_supersessions`); a pull request that supersedes this head's still refuses it |
| a live mesh claim of another session naming the issue | refused (I4356's refusal, generalised from exclusive claims to the advisory claim `start --issue` already makes) |
| another branch only, with no pull request | warned; a branch is cheap and not a claim |

</div>


A title that names more than three ids is a combined top (a train), and claims none of them.

**Cost of `id_reused`.** The candidates are the records the head adds since the merge-base: one
diff. A single `git log --all --diff-filter=A` over the candidate paths alone finds every commit
that added them on any ref. An adding commit that is an ancestor of the head is the head's own.
Any other is compared by the record's `title` at that commit, not by blob, because stamps
change a blob without changing whose record it is. The refs that hold it are named with one
`for-each-ref --contains`. The cost scales with the head's added records, not with the number of
refs. A record whose path the base already holds, and whose `title` the head changes, is
`retitled`: a warning, because it can be the hidden form of a collision after a rebase.

**Freshness.**
- An observation older than `collisions.max_age` (`.ai/repo/ci/plan.yaml`, seconds) is `stale`.
- A stale or unread forge never proves "no other pull request". The finding says
  `unread: forge`.
- A gate on a pull request refreshes the observation first. If it still cannot read the forge,
  it is unjudged (exit 12).

**Where it runs.**
- `majordomus start --issue <id>` asks it for that issue after the binding and before the task is
  written. It refuses (exit 15) on a refused finding, naming the holder and the command to
  inspect it.
  - `--alongside "<reason>"` starts anyway and records the reason in the task. Two sessions may
    legitimately split one issue.
  - An unread forge is a warning at start: the session is not blocked by a forge it cannot reach.
- The pre-push hook runs `--gate push` over the recorded observation, with the running task's
  session as its own. A stale or unread forge only warns there, and a fresh conflicting reading
  refuses, so an offline push is never refused for a forge it could not read.
- `--gate pr` is the pull-request reading: there an unread forge cannot be judged (exit 12).
  It is not yet a gate of this repository's CI. The CI jobs read no forge today (I2750 settles
  that for the trunk), and a gate that is always unjudged would turn every head red. Until
  then, the existing `collision-gate` refuses a new path, an issue record included, that two
  branches add with different bytes.

**Relation to work in flight.**
- I4753 (planned in #3131, the same day) makes `start` and `plan start` take an *exclusive* mesh
  claim on the issue.
- `plan.collisions` is the read half that composes with it. It reads every live claim that names
  the issue, advisory or exclusive, beside the forge and the branches, and names the holder;
  I4753's exclusive claim is the write half.
- I3971 makes `plan next` pass such an issue over.
- `scripts/collision-check` and `collision-gate` are this repository's own path-level detector.
  `id_reused` is the same question asked of an issue record by its title, from the executable
  every adopter installs.
- On the trunk the gate judges nothing. The trunk is where the first author landed.

### Consequences

- The hours spent settling drift by hand become `majordomus plan reconcile`, a dry run that names
  the moves and the evidence still owed. `--apply` then writes exactly the moves the guard
  admits.
- DONE is never written on a merge alone. Where `--apply` writes DONE, the record already carried
  the evidence the issue requires.
- In a fork, delivery, drift, flight and reconcile read the fork's own pull requests. A cached
  observation of another repository is reported unread instead of being judged.
- A repository whose commit grammar has no room for an id can still name what a commit delivers.
- An id authored twice is refused on the second pull request, before either one lands. An issue
  that is executed twice is refused at the second `start`. A late start (the picker ran before the
  pull request existed) is still refused at that session's push and its pull request.
- New surfaces: `plan.reconcile` and `plan.collisions`, generated onto the CLI, MCP and HTTP
  projections. There are new options for `start` (`--alongside`), one new drift class and one
  key (`collisions.max_age`).
- A pull-request gate over `plan.collisions` waits for the CI jobs to read the forge.

### Alternatives rejected

- **Document the manual procedure.** This is what cost hours, and it scales with the number of
  merges.
- **Let `--apply` write VERIFY from a merge.** This was the first draft. Both second-round
  reviewers refuted it: VERIFY is a worker's attestation, and a merge can be one slice of an
  issue.
- **Let `--apply` stop before DONE always.** The done guard already decides completeness from the
  evidence the record holds, and a second rule of acceptance would drift from it. `--done` stays
  explicit, and it adds only the freshness condition.
- **Read commit bodies or the paths a commit touched as edges.** Bodies mention the issues around
  the work as readily as the one they realise (ADR 0166). Path overlap with an issue's scope is
  inference about intent, not a claim by anyone.
- **Make collisions drift classes.** Drift judges stamps against delivery on the trunk's plan.
  Collisions judge a head against the other heads, and they run at `start` and at push, where
  drift's history walk is too expensive.

### Review

The owner ordered several passes with other models (the answer recorded above).
- **Pass 1** was a written design.
- **Pass 2.** Two independent reviewers were given the problem, the evidence and the code, not the
  design: Codex (`codex exec --sandbox read-only`) and a Claude Sonnet subagent with no context.
  The reasoning plan's selected advisors, Gemini CLI and ChatGPT, both failed authentication, and
  their consultations are recorded as `auth_failed`. Ollama has no model on the machine.
- **Pass 3.** Both reviewers critiqued the revised design. This decision is the third revision.

#### Round 1 (independent designs)

- **Both:** `GhForge::observe` reads the parent of a fork (`gh repo view`, and `gh pr list`
  without `--repo`), and the cached observation is used without checking its repository.
  *Taken* (decision 1). Sonnet: every `repos/{repository}` call inherits the wrong repository.
  *Taken.*
- **Both:** `--apply` writes only through `plan.transition`, and done only when the existing guard
  passes; it never synthesises evidence. *Taken.* Sonnet: BLOCKED is never touched, a refusal
  stops the issue and not the batch, and the run is idempotent. *Taken.*
- **Both:** VERIFY with a merge and missing evidence needs its own finding. *Taken* (decision 4).
- **Both:** an unread or stale forge is unknown, never "no open pull request". *Taken*, with one
  deviation: `start` and a push warn on an unread forge instead of refusing, so that a session
  without network can still work. The pull-request gate refuses.
- **Both:** a trailer is a sound edge when it comes from the final trailer block, on non-planning
  commits, and names a declared id. Body prose and path-touch inference are not sound. *Taken*
  (decision 2). The trailer is named `Delivers:` (Codex's proposal) over `Plan-Issue:` (Sonnet's),
  because it says what the commit did.
- **Codex:** `transition` writes the record before the ledger event. *Taken* as a reporting duty:
  `--apply` stops that issue and reports the write error. The ordering is ADR 0097's.
- **Sonnet:** join acceptance criteria against CI jobs. *Rejected:* matching prose to jobs is the
  judgement reconcile refuses to make. I3255's receipt is the route.
- **Sonnet:** a `plan renumber` command. *Deferred.* It rewrites references across the tree, and
  is its own issue.

#### Round 2 (critique of the revision)

- **Both:** writing VERIFY from a merge is unsound. *Taken:* reconcile never proposes `verify`.
- **Sonnet:** evidence recorded before the merge must not admit `done`. *Taken:* the freshness
  condition.
- **Both:** stamp changes and plan-records heads must not count as execution, and a train must not
  claim every issue it names. *Taken:* execution is the branch or `--issue` only; planning-only
  heads are exempt; a title with more than three ids claims none.
- **Codex:** a stale forge must not refuse an offline push. *Taken.*
- **Both:** `id_reused` must not walk every ref per record. Compare by a stable field, not by blob,
  because stamps change blobs. *Taken:* candidate-scoped `log --all --diff-filter=A`, compared by
  title.
- **Sonnet:** a rebase can hide a collision behind a path that the base already holds. *Taken:*
  `retitled`, a warning.
- **Codex:** an inherited `GH_REPO` must be overridden too. *Taken.*
- **Sonnet:** in a fork whose trunk tracks `upstream`, the trunk's remote is the parent. *Kept as
  designed:* in that workflow the pull requests are the parent's, and delivery reads that trunk's
  merges. A policy override is left out until an adopter needs one.
- **Sonnet:** exit 15 at `start` collides with the code for an active task. *Kept:* every refusal
  of `start` (an active task, a refused binding) is `MJ_EX_REFUSED`, and the message says which.
- **Sonnet:** cut the acceptance list and the five classes. *Rejected:* the owner asked for each
  criterion with how it is met or not, and `unjudged` is the truthful answer for prose.
