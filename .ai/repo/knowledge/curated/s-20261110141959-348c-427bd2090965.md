# after the shared server died and serve ensure started another, the MCP plan.allocate tool refused 'not_active: a number is reserved by the mesh of the server holding this checkout's lease' because the client stayed attached to a server that no longer held the lease; the CLI mesh allocate --session worked once the session was re-opened

Observed as friction about capability:plan.allocate in episode s-20261110141959-348c.

# Evidence

- `file:apps/majordomus-cli/src/capability/builtin/allocate.rs`
- `file:docs/MCP.md`

# Evidence

- On 2026-11-10 the shared server of the primary checkout died; `majordomus serve ensure` started another (port 54334). The MCP `plan.allocate` tool of an already-attached client then answered "refused: not_active: a number is reserved by the mesh of the server holding this checkout's lease; ask it (majordomus mesh allocate), or start one with a mesh declaration".
- `majordomus mesh allocate --session <id> --at-least <n> issue` answered once the mesh session was re-opened with `majordomus mesh session open` (I3798 covers re-opening on a successor). apps/majordomus-cli/src/capability/builtin/allocate.rs is where the refusal is made; docs/MCP.md describes re-announcing after a reconnect but not re-attaching to a successor server.
