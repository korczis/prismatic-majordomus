# a caller that took the derive lock by hand (mkdir and an owner line without a pid) and then ran scripts/derive waited on itself for over 30 minutes on 2026-11-17: scripts/derive takes the lock itself, an owner line without a pid can be neither checked nor recognised as an ancestor, and the wait said only that such an owner cannot be checked; the wait now names this case and its remedy (scripts/derive --locked -- <command>, or the caller's pid at the end of the owner line), and case 1018 holds the message

Observed as friction about lib/machine_lock.sh in episode s-20261117224745-7fdd.

# Evidence

- `file:lib/machine_lock.sh`
- `test:test/cases/1018_one_derive_at_a_time_and_no_orphans.sh`

# Evidence

- `lib/machine_lock.sh` at ae13be1bd13, mj_lock_acquire: an owner line with no numeric pid gives an empty `pid`, so `mj_lock_is_ancestor` cannot recognise the caller, the dead-owner reclaim does not apply, and the wait printed only `waiting: <lock> is held by an owner that names no pid, so it cannot be checked: <line>`; the header of `scripts/derive` says every stage runs under the machine's derive lock and that `scripts/derive --locked -- <command>` runs a command under it.
- 2026-11-17: a caller that made the lock directory and wrote an owner line without a pid, then ran `scripts/derive`, waited on itself for more than 30 minutes with that line.
- This change: the wait adds `If this derive's own caller took the lock, it is waiting on itself: scripts/derive takes the lock itself, so a caller never takes it; run a command under it with scripts/derive --locked -- <command>, or end the owner line with the caller's pid`. `bash test/run.sh 1018_one_derive_at_a_time_and_no_orphans` passes (1 passed), and with the added line removed from lib/machine_lock.sh it fails with `expected /If this derive's own caller took the lock, it is waiting on itself/`.
