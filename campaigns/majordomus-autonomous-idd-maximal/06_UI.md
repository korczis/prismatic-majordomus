# PHASE 06 — `majordomus ui` AS AN INTERACTIVE, DERIVED CONTROL PLANE

Inspect actual `docs/UI.md`, `docs/COCKPIT.md`, `docs/DESIGN_SYSTEM.md`, `docs/COCKPIT_IDE_AUDIT.md`, site/UI rules, templates, rendering/caching and current `majordomus ui` behavior. Do NOT guess that a frontend framework is in use or replace the Rust server. Extend existing UI projections and design conventions. Respect intended high-level project-centered Majordomus UI vs lower-level Cockpit/debugger. Do not ship a parallel single-page state engine. Use Flowbite/Alpine.js/Cytoscape/ECharts only where already compatible with build, CSP, license and performance requirements; avoid new large runtime dependencies for cosmetic polish.

Navigation information architecture (derived from canonical publication/router/capability metadata): Project overview; Intents; Milestones; Work queue/Issues; Mesh/Peers; Executions; PRs/Integration; Releases/Deployments; Evidence/Audit; Governance/Diagnostics. Preserve access to Cockpit detailed views and stable entity deep links. New domain entities automatically enter the correct category through typed metadata; no hardcoded backend+frontend inventories. Clearly distinguish local vs mesh-global and last-updated/staleness/incompleteness.

Core user journey:
1. Project selector/repo status with latency-safe shell and server connectivity.
2. Intent composer with editable statement, criteria, invariants and target/deploy policy. Show source and context; propose plan without unauthorized side effects.
3. Plan review: criterion coverage, dependency graph, risk, estimated bounded cost, alternatives, critique, provenance, missing approvals; approve/start with explicit effect scope.
4. Live intent overview: stage, satisfaction criteria matrix, evidence, milestones, issues, queue and blockers; deep links.
5. Milestone graph: Cytoscape only when useful; selectable nodes, dependency edge detail, filters, search, keyboard accessible equivalent list, context actions. No enormous graph on initial paint; lazy load neighbors.
6. Mesh: peer cards/list, trust/health, lease/claims, worktrees, active attempts, reconnect status; actions only if authorized; stream progress/logs with bounded tail and redaction.
7. Execution detail: live timeline, event cursor, worker, provider, selected context fingerprint, resources, attempt history, retries, cancel/reassign/pause/resume gated by policy.
8. PR integration: review and CI status, priority, merge readiness, blockers, actions, linking to intent and worker.
9. Release/deploy: version, artifact SHA, target, promotion approval, smoke state, rollback capability if available, evidence links.
10. Final intent evidence explorer: criterion -> issue/commit/PR -> CI -> artifact -> deploy -> observed health. Explain every green indicator.

Interaction architecture: server-authoritative snapshot plus resumable delta stream; request IDs, ETags/revisions, optimistic concurrency; reconnection with backoff, catch-up on lost event cursor; stale badges when disconnected; no fake progress. UI commands are invocations of canonical capabilities and render receipts and policy denials. Never have a click mutate local-only state and pretend the domain operation completed. Use standard HTML forms/actions where sensible, progressive enhancement and non-JS fallback for important reads. Per-control loading/success/error states from actual host response.

Performance (measure baseline and enforce): initial high-level overview should render quickly with skeleton/partial projection, avoid loading historical logs on initial page, limit first-page list size, lazy load graph details, cache immutable/static generated metadata, conditional HTTP cache dynamic snapshots, properly invalidate on events, no N+1 lookups, prefetched canonical links and stable pagination. Establish numeric p50/p95 render and interaction budgets using current performance doctrine rather than claiming unverified universal thresholds. Record benchmarks under realistic sample datasets including 500 issues, 100 PRs, 30 peers, 100k events.

UX/accessibility: mobile-first (320px upward), usable drawers, no horizontal overflow, high contrast, keyboard operation, focus restoration, ARIA live events where appropriate, accessible tabular alternatives to charts/graphs, reduced-motion, visual difference between WAITING/BLOCKED/FAILED/SATISFIED, capability-based action visibility plus server-side auth. Every node clickable to stable entity detail; browser history/back/forward and URL-driven filters work. Avoid duplicate stale local route definitions.

Required UI tests: state transition component tests; click canonical action then rehydrate true state; reconnect; stale revision conflict; denied unauthorized operation; 320/375/768/1440 screenshots; keyboard, focus, overflow, drawers; pagination; accessible graph alternative; long labels; missing remote peer; log redaction; cache invalidation; deep link refresh; stream burst under backpressure; unknown backend capability fallback.

Acceptance: user creates an intent, approves plan, launches it, observes live progress across mesh/PR/deploy, intervenes through supported controls and checks evidence without leaving `majordomus ui`. Record a screen walkthrough and runnable UI smoke test if test framework allows.
