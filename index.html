0.18.0· A supervisory control layer for AI-assisted work

AI coding agents do the work. Your repository decides whether it is done.

Majordomus keeps the context, the paths each agent may touch, the rules and the definition of done in the repository instead of a chat window, and it refuses to record work as finished until the repository's own checks pass. It runs beside whichever coding agent you use, and it never calls a model.

01the problem

Where AI-assisted work breaks down

None of these are model problems. They are operations problems, and the repository is where operations belong.

  • Context Agents forget. What one session learned dies with its conversation, and the next one starts over.
  • Coordination Agents collide. Parallel workers edit the same paths, or build the same thing twice, without knowing about each other.
  • Completion Done is cheap. A worker can report success before the repository's own checks hold.

Majordomus turns each of them into repository state, a contract a machine checks and a record of what happened.

03how it works

One task, from start to finish

A worker claims a task and the paths it may touch, reads what the repository knows, records progress, is checked against policy, leaves a handover, and asks to finish. The repository answers each step.

  1. 1 start begin a scoped task under a profile
  2. 2 context what the next worker needs to know now, within budget
  3. 3 checkpoint record compact progress inside the active task
  4. 4 check is the current task consistent with policy, scope, state?
  5. 5 handover write an append-only continuation record (body on stdin)
  6. 6 finish evaluate the finish contract; refuse if unmet

Nothing here asks a model to behave. check reports what does not hold against the task's scope and policy, and finish refuses to record the work while any line of the contract fails.

Inspect the recorded runs behind every step

Recorded runs, not a mockup: each panel is the stdout of a scenario this site executed while it was being generated, with the machine and the clock redacted and nothing else touched.

04the proof

A worker's word is not proof

A worker strays outside its scope, says it is done, and is refused; fixes the scope and is refused again, because the repository's own test still fails; and is accepted only when every line of the contract passes. A recorded run of the real tool, stepped through.

  1. worker The worker makes the change it was asked for, and also edits a note under docs, which the task never claimed.
  2. ✕refused check names the file outside the claimed scope and exits non-zero. It is a failure, not a warning.
  3. ✕refused The worker reports the task finished. finish evaluates the contract instead of believing it, and refuses.
  4. worker The stray edit is taken back.
  5. ✕refused Scope is clean now, but the repository's own test still fails. finish runs it and refuses again.
  6. worker The worker does what the handover said was left.
  7. ✓accepted Every line of the contract passes, so the outcome is recorded, with the verification that proved it.

This is the difference between a tool that tells a worker what to do and one that decides whether what it did counts. A worker can always say it is finished; here that sentence is a claim the repository evaluates, line by line, and nothing is recorded while any line fails.

Built: the intent record and its judgment. Not built: what acts on it

An intent is a typed record and the repository judges it: what is built is listed below from the claims that name the test proving each, and what is not from the claims still planned, so neither list is written here. Beyond them, nothing derives a plan from a desired outcome, finishing a task does not ask whether an intent is satisfied, and Majordomus does not run the opposition pass: a worker writes the critique, and intent validation fails work that started without one. Every sentence on this page written in the conditional is one of these, and this section will shrink as each one lands.

guaranteed

  • An intent's stage is derived from the milestones that realise it and each criterion from the evidence ledger, and it is satisfied only while every criterion has a current passing run
  • An intent whose criterion names evidence that resolves to nothing is refused by name
  • Once work exists under an intent, a criterion no issue serves, an issue under its milestones that serves nothing and a link to a criterion that does not exist are each refused by name
  • A gap that leaves a criterion unanswered is refused, and an issue serving an intent that started without a critique or while a blocking finding is open fails intent validation
  • The work realising an intent is joined across sessions, providers and handovers, and an intent whose milestones are all closed while a criterion's evidence fails is refused naming that criterion
  • Asked before work on an issue, `intent preflight` names the intents the issue serves with the governance that applies, or refuses naming the cause
  • The Cockpit shows every intent with its derived stage at /cockpit/intents, and one intent's criteria, evidence, serving issues and realising work at /cockpit/intents/<id>
  • A task that names the issue or the intent it serves is briefed with what that intent asks of the work, and a handover tells the next worker when the intent moved
  • Where the policy requires binding, starting an issue or a task that serves an intent with no critique, or with a blocking finding open, is refused when it is started rather than reported afterwards

planned

  • A milestone will be closed on GitHub only once the intents it realises are satisfied
  • A criterion settled by a command or by a deployment will be met by recorded evidence

07get started

Try it on a repository you already have

What init creates is the layer this site is generated from: one directory, tracked, readable without the tool.

install · one command

Install majordomus in one command

No git, no Rust, no Node, no root. One archive for your machine, its digest verified before anything is unpacked, into $HOME/.local/bin.

1 · paste into a terminal 
curl -fsSL https://majordomus.dev/install.sh | sh

2 · in the repository you want supervised

majordomus init

Writes .ai/ — the policy, the profiles, the rules, the prompts, the workflows — and nothing else.

3 · point your agents at it

majordomus update

Generates CLAUDE.md, AGENTS.md and the other bootstraps from the policy; every worker reads the same contract. Platforms, pinning a version, the security model →
