# MASTER PROMPT — Majordomus Mesh Fabric (MMF)

## Mission
Replace board-polling-as-chat with **real secure peer message exchange** while preserving existing peer announcements, durable knowledge, task ownership and governance. Deliver an integrated, provider-neutral, dynamic, inferred, data-driven and fault-tolerant mesh communication fabric. The first non-negotiable outcome is two actual live supported peer runtimes completing a request/reply without polling the peer board. A synthetic echo handler is useful as a transport test but does NOT satisfy the AI-runtime E2E criterion.

## Operating algorithm
A. Discover reality: git/worktrees/branches/PRs/issues; effective `.ai/**`; peer registry, sessions, task graph, bus/synth/monitors, event vocabulary, existing storage, auth, transport, schemas, telemetry, CLI/MCP/HTTP/Cockpit, CI/release. Produce a source-linked graph of actual owners, dependencies, gaps and reusable components. Categorize every statement observed/inferred/proposed.
B. Select ONE canonical owner for messaging and ONE canonical event/outbox persistence path, or extend their existing equivalents. Write the narrow ADR only if current policy demands it. Explicitly document rejected options: UDP broadcast as message plane, unauthenticated datagrams, polling as chat, dual source of truth, fabricated exactly-once, compulsory relay, premature custom consensus.
C. Define typed versioned MMP envelope: message_id, sender principal, recipient address or topic, message kind, schema/type, correlation and causation, deadline, TTL, delivery class, priority, intent/task/session references, schema-validated payload or content-addressed artifact ref, provenance, policy revision, optional trace context. Validate size, schema, ACL, replay protection, clock skew and version negotiation. Do not trust caller-supplied identity fields without binding to authenticated transport/session principal.
D. Build transport-independent API and handlers: send, ask/reply, stream/cancel, publish/subscribe, receipt/status and replay where justified. Declare semantics precisely (accepted vs persisted vs delivered vs processed; timeout vs cancellation; duplicate vs rejected; ordering scope). Request/reply routing must reach a running agent adapter, not a passive board row.
E. Prioritize UDS or existing faster local IPC for same-host peers. Support connection lifecycle, reconnect, authenticated local identity (peer credentials or bound session auth), bounded buffers, deadlines, graceful shutdown, fair scheduling and cancellation. Cross-host secure QUIC/TLS and fallback after evidence-based need; do not block first local milestone on NAT traversal.
F. Durability: transactional outbox/inbox or equivalent existing append-only store, idempotency, ACKs at distinct stages, retry with bounded backoff/jitter, dead-letter diagnostics, crash/restart replay, expired-message cleanup, ordered processing only where promised. No exactly-once network delivery claim. External side effects require explicit idempotency keys or compensation; do not infer safety from dedup alone.
G. Security: peer identity, scope/task authorization, capabilities and current policy at both sender and receiver/execution boundaries, secure transport, cross-repo isolation, resource quotas, payload scrubbing, audit, safe remote execution prevention. Any generated agent plugin or hooks must use vendor-supported integration seams, preserve user control and be feature gated.
H. Routing: derive reachability/capabilities from authenticated handshakes and registry snapshots, honor trust/policy, prefer UDS locally, choose QUIC for remote with TCP/TLS or relay fallback as justified. UDP multicast/mDNS only optional LAN discovery; never authorize by discovery claims. Implement deterministic route selection first, metrics-based adaptive weights later; ensure hysteresis and safe rollback.
I. Integration: link message causality to intents, milestones, issues, tasks, sessions, board, KB/ADRs, reviews, claims and evidence without duplicating their canonical stores. Thin adapters for Claude Code, Codex and others only where their current supported interfaces genuinely allow it. A client that cannot receive unsolicited work must report capability unavailable rather than pretend to be reachable.
J. Derived surfaces: extend canonical capability declarations and generate CLI, MCP, HTTP/OpenAPI, Cockpit/LiveView streaming, docs, GH Pages and examples as actually supported. UI should show peer topology, route, queue/delivery status and traces, not invented timings. Derive all inventories; never edit generated outputs directly.
K. Verification: unit, property, model/state-machine tests where sensible; real multiprocess UDS; two live runtimes E2E; fault injection for disconnect, process kill, duplicate, reorder, timeout, saturated queue, stale lease, unauthorized peer, malformed envelope, schema evolution, replay, multi-repo isolation, CI gate/registry drift, cross-surface consistency. Benchmark p50/p95/p99 roundtrip excluding and including model inference, CPU/memory, queue wait, delivery success and fallback; compare with current board coordination using same workload. Report actual evidence, not aspirational multipliers.
L. Delivery: use current project workflow to materialize dependencies as intent/milestones/issues only where necessary; minimize PRs and batch dependencies sensibly. Integrate incrementally to master with all required gates, version and docs; repair related legacy and remove dead adapters. No silent stubs or 'done' until end-to-end tested.

## Invariants
- Centralized governance, decentralized transport, durable evidence.
- No mandatory board polling for request/reply. Board remains a discoverable/status projection.
- No separate peer inventory / event vocabulary / bus created for MMF if existing canonical owner can be extended.
- Policy and scope are evaluated for each message/operation; transport bypass cannot bypass authorization.
- Offline durable delivery is at-least-once with idempotent processing only where proven; asynchronous delivery may be pending, rejected, expired or dead-lettered with explicit reason.
- Every external API/schema/surface is inferred/generated from typed canonical declarations where current architecture supports it.
- No remote code execution by virtue of receiving a mesh message.
- Distinguish transport ACK, durable ACK, application ACK, and execution outcome.
- No false agent reachability or fabricated peer capability.
- No cross-worktree confusion; define whether identity is process, client, repo, session or agent and model relationship explicitly.
- Capacity ceilings and admission control are required before enabling fan-out.
