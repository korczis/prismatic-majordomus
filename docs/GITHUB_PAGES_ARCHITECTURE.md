# GitHub Pages architecture

The public site at <https://korczis.github.io/prismatic-majordomus> is **derived**. It has
no content of its own beyond a small, budgeted promotional file. The repository is the
source of truth; the site is a presentation layer over it.

This document exists so that the next person to change the site knows where content
lives, and so that nobody creates a second documentation universe by accident.

```
canonical Markdown / YAML  (README.md, AGENTS.md, docs/**, share/skeleton/**)
        |
        |  scripts/generate-pages
        v
semantic HTML in _site/    (Tailwind utilities + Flowbite components, no custom CSS)
        |
        |  Tailwind CLI scans _site/ and node_modules/flowbite
        v
_site/assets/app.css
        |
        |  .github/workflows/pages.yml
        v
GitHub Pages
```

## Content ownership

Every sentence on the site comes from exactly one of these. Nothing is duplicated.

| Canonical source | Owns |
|---|---|
| `README.md` | the homepage narrative: the problem and its magnitudes, the responsibility table, the mental-model diagram, the core principles, what it is not, the limitations, the quick start, the example workflow |
| `docs/CLAIMS.yaml` | **every capability claim on the site**, with its status, source, implementation, and test |
| `share/skeleton/profiles/*.yaml` | the profiles page and the profile tabs: every axis value |
| `share/skeleton/policy.yaml` | the default profile and the default checkpoint interval |
| `bin/majordomus` | the version shown in the navbar, hero badge, and footer |
| `docs/DESIGN.md`, `CLI.md`, `SCHEMAS.md`, `CONCEPTS.md`, `ADOPTION.md`, `ECONOMICS.md`, `EXTRACTION_REPORT.md` | one rendered documentation page each |
| `AGENTS.md` | the repository-contract page, itself generated by `majordomus update` |
| `assets/logo.svg`, `assets/logo-mark.svg`, `assets/social-card.png` | the mark, wordmark, and social card, shared with the README |
| `site/promo/copy.yaml` | **the only hand-written prose on the site**: the site name, URLs, meta descriptions, button labels, and one lead sentence per homepage section |

`site/promo/copy.yaml` is deliberately constrained. It may not contain a capability claim
or a number, it has a line budget, and `--check` enforces both. If a paragraph wants to
live there, it almost certainly belongs in `README.md` instead.

## The generator

`scripts/generate-pages`, portable shell, matching the rest of the repository: bash 3.2
and BSD userland are the floor. It sources `lib/common.sh`, so the site is parsed by the
same restricted-YAML reader the tool itself uses — a policy file the tool would reject
is a policy file the site cannot render.

| File | Role |
|---|---|
| `scripts/generate-pages` | the generator: page composition, validation, manifest |
| `scripts/lib/md2html.awk` | the Markdown subset used in this repository, rendered to semantic HTML with no presentation classes |
| `scripts/lib/section.awk` | extracts one Markdown section by heading text; **exits non-zero when the heading is absent** |
| `scripts/lib/codeblock.awk` | extracts the Nth fenced code block |
| `site/tailwind.css` | the Tailwind and Flowbite entry point |

It reads canonical content in three ways, in decreasing order of robustness:

1. **Whole file.** A documentation page renders one Markdown file entirely. Nothing to break.
2. **By heading text.** The homepage takes the body of a named level-2 heading. If the
   heading is renamed, `section.awk` exits non-zero and the build **fails loudly** rather
   than emitting an empty section. `--check` verifies every heading the generator reads
   before generating anything.
3. **By fenced-block ordinal.** Two diagrams are taken from `README.md` by position.
   This is the fragile one: inserting a code block before them silently shifts the
   content. `--check` verifies the blocks exist but cannot verify they are the right
   ones, so **reordering README code blocks requires re-checking the homepage.**

Headings and blocks the generator currently depends on are listed in `check_sources`.

## Output

Generated into `_site/`, which is gitignored. **The generated site is never committed.**
It is built in CI and uploaded as a Pages artifact, so there is no possibility of a
committed build going stale against the sources it came from.

Routes are directories with an `index.html`, so a plain static server resolves them
exactly as GitHub Pages does, with no configuration.

```
/                       homepage
/getting-started/       install, first task, adoption
/profiles/              every axis of every profile, from YAML
/guarantees/            the claims matrix: guaranteed, advisory, planned, rejected
/docs/                  documentation index
/docs/<name>/           one canonical document each
/site-manifest.json     what this build was made from
/sitemap.xml  /robots.txt  /.nojekyll
```

## Drift prevention

A derived site has one failure mode a hand-written site does not: the deployed output can
silently lag behind the sources. Three mechanisms address it.

**`site-manifest.json`** records the version, the source commit, the generator version,
and a SHA-256 of every canonical input plus one `input_sha256` over all of them. The hash
is order-stable and independent of timestamps, so two checkouts with identical content
produce the same value. `--check` recomputes it and fails if the manifest disagrees with
the files on disk.

**Deploy on push.** `.github/workflows/pages.yml` runs on every push to `master`, so the
deployed site is never more than one push behind. It runs `test/run.sh` and
`bin/majordomus doctor` *before* generating: the site claims the tests pass, and
deploying from a tree whose tests fail would publish a claim the tree does not support.

**A regression test for the architecture itself.** `test/cases/11_site_derives_from_source.sh`
copies the repository, changes a profile description, the version, a policy value, and a
claim, regenerates, and asserts that all four changes appear in the output and that the
stale text is gone. If editing canonical content does not change the site, that test
fails — which is the only real proof that the site is derived rather than a copy.

## Validation

`scripts/generate-pages --check` generates and then validates. It is the single command
CI runs, and it exits non-zero on any failure.

Sources, before anything is generated:

- every file declared in `SOURCES` exists
- every heading and fenced block the generator reads is present
- every claim in `docs/CLAIMS.yaml` has a valid status and an existing source; every
  `guaranteed` claim names an existing implementation **and an existing test**
- no duplicate claim ids
- every `docs/*.md` is rendered by some route, so a new document fails the build until
  the site links it
- `site/promo/copy.yaml` is within its line budget and contains no hardcoded count

Output, after generating:

- every route exists and carries a title, meta description, canonical link, Open Graph
  and Twitter metadata, a `<main>` landmark, a skip link, and exactly one `<h1>`
- the Flowbite mobile navbar toggle and its `aria-controls` are present on every page
- no unresolved `{{PLACEHOLDER}}`, no unexpanded `$SHELL_VARIABLE`, no empty attribute
  (the scan runs with code blocks stripped, so a `$HOME` inside a shell example is content)
- no inline `style=` attribute anywhere
- no remotely fetched asset: script, stylesheet, and image sources must be same-origin
- required homepage sections are present, and the guaranteed, advisory and planned
  badges actually rendered
- values that exist only in canonical sources reached the pages that should carry them
- every internal link resolves to a generated route or asset
- no credential pattern, no private email address, no local filesystem path or internal
  hostname
- `input_sha256` matches the sources on disk
- `app.css` is within a plausible size band, contains the classes the HTML uses, and uses
  class-based dark mode; no second stylesheet exists

## UI stack

Tailwind CSS v4 and Flowbite v3, both pinned in `package.json`. Node is needed **only**
to compile the stylesheet; the `majordomus` command itself has no runtime dependencies
and `--no-css` generates the whole site without Node.

**Custom CSS: none.** Presentation is Tailwind utilities and Flowbite component classes.
`site/tailwind.css` contains only `@import`, `@plugin`, `@source`, and one
`@custom-variant` for class-based dark mode; it defines no rules of its own. `--check`
fails if a second stylesheet appears in `assets/`, and fails on any inline `style=`
attribute. If a rule ever genuinely has to exist, justify it here, in this section.

Interactive behaviour is Flowbite data attributes — `data-collapse-toggle` for the mobile
navbar, `data-tabs-toggle` for the profile tabs — initialised by the bundled
`flowbite.min.js`, which is copied from `node_modules` and served from the same origin.
The only JavaScript the site adds is `assets/theme.js`, the documented Flowbite dark-mode
switcher. **Every page is fully readable with JavaScript disabled**: without it the mobile
menu is collapsed but every link is in the footer, and the profile tabs simply show the
first profile while the other panels stay hidden, with the same content available in full
on `/profiles/`.

Markdown is rendered into a Flowbite Typography container
(`format lg:format-lg dark:format-invert`), so headings, paragraphs, tables, lists, code
and blockquotes inherit one typography treatment. `md2html.awk` emits no presentation
classes; its one exception is an `overflow-x-auto` wrapper around `<pre>` and `<table>`,
so a long code line or wide table scrolls in its own container instead of widening the
page.

## Local preview

```bash
npm ci                              # once: Tailwind, Flowbite, Flowbite Typography
scripts/generate-pages              # generate _site/ and compile the stylesheet
scripts/generate-pages --serve      # the same, then serve on http://localhost:8080
scripts/generate-pages --check      # what CI runs
scripts/generate-pages --no-css     # HTML only, no Node needed
scripts/generate-pages --out DIR    # write somewhere else
```

Site tests, which run as part of `bash test/run.sh`:

```bash
bash test/run.sh 10_site_generates              # routes, metadata, determinism
bash test/run.sh 11_site_derives_from_source.sh # the derived-content regression
```

## Changing content correctly

| To change | Edit | Not |
|---|---|---|
| any capability claim, or its status | `docs/CLAIMS.yaml` | the HTML |
| a problem, principle, or responsibility on the homepage | `README.md` | `site/` |
| a profile axis | `share/skeleton/profiles/<name>.yaml` | the profiles page |
| a documentation page's text | the `docs/*.md` file | the generated page |
| the layout, or a Flowbite component | `scripts/generate-pages` | a stylesheet |
| a meta description or button label | `site/promo/copy.yaml` | anywhere else |
| the mark or social card | `assets/` | `site/` |

Adding a documentation page: add the `docs/*.md` file, then add a line to `DOCPAGES` in
the generator. Until you do, `--check` fails — deliberately, so the site cannot quietly
omit documentation.

Adding a capability: add the row to `docs/CLAIMS.yaml` with its source, implementation and
test. A `guaranteed` row without a test fails the build, which is the same rule the
repository contract applies to `README.md`.
