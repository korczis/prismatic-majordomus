Getting started

From nothing to a supervised repository. Every command below exists in the CLI reference; nothing here is a target.

Majordomus is a directory in your repository plus a portable-shell CLI. There is no server to run and no account to create. The steps below are the ones the tool's own tests exercise.

  1. 1 Install the CLI

    One archive for your machine, its digest verified before anything is unpacked, into $HOME/.local/bin. Pinning a version, choosing where it goes, and the security model →

  2. 2 Add it to a repository

    init writes .ai/ and refuses to overwrite one that exists. update generates AGENTS.md, CLAUDE.md, GEMINI.md from the policy. doctor prints the 2 hook lines still missing; add them and run it again until it reports zero failures.

  3. 3 Start a scoped task

    Scope is the set of paths the worker may touch. Profile defaults to implementation. Identity fields are computed from git; a worker never writes them.

  4. 4 Work, checkpoint, check

    A file outside the scope is a failure, not a warning. A stale checkpoint is a warning and never blocks.

  5. 5 Hand over or finish

    Required handover sections: # Objective, # Current State, # Next Action. finish evaluates scope_respected, verification_ran, state_updated, no_open_blockers, note_present and writes nothing when any line fails.

commands

  • start — begin a scoped task under a profile
  • check — is the current task consistent with policy, scope, state? read-only
  • finish — evaluate the finish contract; refuse if unmet
  • session — open, inspect and close one execution episode
  • context — what the next worker needs to know now, within budget read-only
  • checkpoint — record compact progress inside the active task
  • evidence — record that one obligation the task declared has been discharged
  • handover — write an append-only continuation record (body on stdin)
  • history — read the append-only ledger back read-only
  • decision — record or read durable decisions
  • question — open, resolve and list questions that block acceptance
  • prompt — list, show and render repository-local prompt assets read-only
  • skills — the repository's skills: list, show and check them read-only
  • capture — record the person's raw prompts from a provider hook, and prove it
  • search — find durable records without reading all of them read-only
  • knowledge — the compiled index over what this repository states read-only
  • adr — the repository's architecture decisions: list, show, propose, check
  • rules — the effective rule set: vendored baseline plus project rules (read-only, except vendor update) read-only
  • usecase — the executable use cases: list, show, validate, run, coverage, impact, scaffold
  • plan — the milestone and issue model: validate, read, and move an issue
  • init — create the .ai/ layer in this repository (refuses to overwrite)
  • migrate — move pre-.ai project data from .majordomus/ into .ai/ (explicit, backed up)
  • recover — bring this checkout's record stores back to what the contract describes
  • update — regenerate provider projections from policy
  • doctor — is Majordomus itself healthy and actually wired here? read-only
  • doctrine — what rules are enforced, by what, and whether they are wired read-only
  • watch — what has drifted: state, policy, projections, retention read-only
  • version — print the version
  • bench — time every public command, cold and warm, against the baseline
  • archive — a snapshot of the tracked tree, for reading or checking elsewhere

exit codes

  • 0 ok
  • 2 usage
  • 10 contract unmet
  • 11 drift found
  • 12 missing artifact
  • 13 internal error
  • 15 refused

There is no "warn and continue" code.
