Vykresleno z docs/WORKTREES.md — téhož Markdownu, který ukazuje GitHub.

Kam patří každý linked git worktree tohoto repozitáře, jak se to rozhoduje a co nástroj dělá s tím, který je jinde. Chování tak, jak je implementováno a testováno; kde se tento dokument a spustitelný soubor rozcházejí, je chybný dokument a mění se ve stejném commitu. Rozhodnutí je ADR 21; pravidlo je project.worktree-topology.

~/dev/prismatic-majordomus                    the primary checkout: hosts the trunk, never moves
~/dev/prismatic-majordomus-wt/                the container: the checkout's sibling, name + "-wt"
~/dev/prismatic-majordomus-wt/feature/x       the one worktree of branch feature/x
~/dev/prismatic-majordomus-wt/fix/a/b         the one worktree of branch fix/a/b — hierarchy kept

Název větve je relativní cesta. Nic se neplošťuje (feature-x), nehashuje (feature-x-a93f) ani nečísluje (worktree-1) a nic se nikde neregistruje: pro daný repozitář a větev existuje právě jedna cesta a každý povrch ji odvozuje stejně.

Proč

Na jednom repozitáři pracuje současně několik relací — lidí i agentů — a každá potřebuje vlastní checkout. Mechanismem je linked worktree gitu a git bere cíl jako argument, takže o jeho umístění rozhoduje každý volající. Třiapadesát z nich se zde rozhodlo jinak: ploché sourozenecké adresáře pojmenované po ničem, scratch adresáře relací, jeden uvnitř primárního checkoutu, jeden zabírající vlastní cestu kontejneru. Cenou nebyla neuklizenost. Bylo to, že „kde je větev X“ a „kam patří nový“ nemělo odpověď, která by nezahrnovala hledání, hádání nebo vymýšlení, a relace, která musí cestu vymyslet, nechá svou práci tam, kde ji další relace hledat nebude.

Topologie dává odpověď jednou: izolace funkcí bez rozhodování, paralelní agenti, kteří nemohou kolidovat na cestě, předvídatelné mapování relace → větev → worktree, které předávka umí pojmenovat a obnovená relace se podle něj umí vrátit, úklid, který je odvozený seznam, ne archeologie, a topologie, kterou může ukázat každý povrch, protože ji každý počítá stejně.

Jak se cesta odvozuje

git rev-parse --git-common-dir             which repository this is, from any directory of any worktree
git worktree list --porcelain              its worktrees; the first record is the primary checkout
parent(primary) / name(primary) + "-wt"    the container
container / branch name                    the worktree, one directory per component

Druhý řádek je ten, který se snadno pokazí. git rev-parse --show-toplevel odpovídá na aktuální worktree, takže odvození kontejneru z něj uvnitř linked worktree by vytvořilo …-wt/feature/x-wt, kontejner pro každý worktree, zanořující se donekonečna. Primární checkout se proto čte ze sdílených metadat gitu, takže odpověď je stejná z primárního checkoutu, z jeho podadresáře, z linked worktree i ze čtyř adresářů hluboko uvnitř něj.

Název větve je vstup odvozený ze souborového systému a zachází se s ním tak: název se validuje podle vlastních pravidel gitu pro reference (žádné .., žádná komponenta začínající ., žádná končící .lock, žádné řídicí znaky, žádný z ~ ^ : ? * [ \, žádné @{, žádné počáteční -), každá komponenta platného názvu je běžný název adresáře a odvozená cesta se při každém volání dokazuje jako striktně pod kontejnerem. Komponenty v Unicode jsou běžné názvy adresářů. Dva názvy lišící se jen velikostí písmen se ohlásí (worktree.case_collision), protože na souborovém systému nerozlišujícím velikost je obě obsahuje jeden adresář.

Trunk se objevuje, nikdy není napevno zadán: HEAD vzdáleného repozitáře (refs/remotes/origin/HEAD), pak init.defaultBranch, když ta větev existuje, pak kterákoli z main a master existuje sama, pak vlastní větev primárního checkoutu. Hlásí se, která rozhodla.

-wt se píše jednou, jako CONTAINER_SUFFIX v apps/majordomus-cli/src/worktree/path.rs. Žádná konfigurace neexistuje: kontejner, který lze konfigurovat, je kontejner, o kterém by se dva checkouty jednoho repozitáře mohly rozejít.

Business logika existuje jednou, v apps/majordomus-cli/src/worktree/. Každý povrch je adaptér, který vykresluje nebo promítá, co služba odpověděla; žádný neodvozuje cestu, nerozhoduje o postavení ani neposuzuje, zda je tah bezpečný. Pět otázek jen pro čtení jsou schopnosti registru (worktree.topology, worktree.status, worktree.inspect, worktree.migration_plan, worktree.uncommitted), což je staví na MCP, HTTP, OpenAPI, Swagger UI, do Cockpitu a vygenerované reference, aniž by kterýkoli z nich nesl vlastní trasu nebo schéma. Vytváření, migrace, oprava a odebírání jsou operace téže služby na příkazové řádce. Schopnost, která zapisuje do repozitáře, musí deklarovat efekt repository_mutation, být příkazem a být dosažena přes POST — unit test jejich množinu připíná, takže přidání další je viditelné rozhodnutí — a přesouvání worktrees na disku není něco, co sdílený server MCP přebírá; Cockpit jmenuje přesný příkaz pro každý z nich.

Topologie je platná, pokud nestojí žádná diagnostika na úrovni chyby. Odpojené a efemérní worktree ji neznehodnocují; guard přesto odmítne commit z efemérního.

Které adresáře činí checkout efemérním, jsou data, ne seznam ve spustitelném souboru: share/providers.yaml deklaruje vlastní scratch kořeny nástroje (dočasný adresář) a kořeny každého providera — <primary>/.claude/worktrees pro Claude Code a pro bb, orchestrátor, který drží worktree na vlákno, ${BB_DATA_DIR:-~/.bb}/plugins/environment-git-worktree/host-data/worktrees. Kořen se rozbalí vůči primárnímu checkoutu a prostředí; kořen, pod nímž žije sám primární checkout, se přeskočí, takže fixture testu v dočasném adresáři má běžné sourozence. Diagnostika jmenuje providera, jehož kořen odpovídal. Cizí checkout se nikdy nemigruje bez vyžádání a nástroj jej nikdy neuklízí: náprava, kterou guard nabízí, je pokračovat v kanonickém worktree (ADR 0024).

Kde nová větev začíná

Primární checkout hostí trunk a nic jej neposouvá: 2026-10-16 byl jeho lokální master o 779 commitů za origin/master. Větev z něj odříznutá nenesla nic z té práce, report říkal (new, from master), jako by to bylo aktuální, a každý pracovník resetoval nový worktree na origin/master ručně. Větev, která existovala jen na remote, byla horší: začala se znovu z toho zastaralého master místo aby se převzala.

Proto create a ensure, pro větev, která zde neexistuje, se ptají vzdáleného úložiště trunku — vzdáleného, jehož HEAD pojmenovává trunk, jinak toho, které pojmenovává branch.<trunk>.remote — dvěma tichými, omezenými fetchi (--no-tags, bez promptu, zabité po 60 sekundách) trunku a větve do jejich remote-tracking refů. Lokální trunk se nikdy nepřesouvá.

remotevětev začínáreport
má větevkde stojí větev vzdáleného repozitáře, sledující jibranch fix/x (from origin/fix/x at <sha>, tracking it)
odpovídá, takovou větev nemána trunku vzdáleného serveru tak, jak byl právě stažen, bez sledování čehokoli do prvního pushebranch feature/x (new, from origin/master at <sha>)
nelze přečístna lokálním trunku, nebo na větvi remote, jak byla naposledy stažena, pokud je známastejný řádek z master a řádek warning jmenující remote, důvod gitu, o kolik commitů je lokální trunk za trunkem remote podle posledního fetche a reset, který spustit, až odpoví
žádný nenína lokálním trunku; nic se nestahuje a nic se neříkábranch feature/x (new, from master at <sha>)

--base REF se bere tak, jak je zadáno, a nikdy se nestahuje. JSON nese rozhodnutí jako start (from: remote_trunk, remote_branch, local_trunk, given, head, se vzdáleným repozitářem, důvodem a vzdáleností) a commit přečtený zpět z nového worktree jako start_commit. Je to jediné místo, kde příkaz worktree sahá do sítě; každé jiné čtení a rozhodnutí funguje offline.

.envrc nové cesty

direnv schvaluje .envrc podle cesty a obsahu, takže vlastní .envrc repozitáře na cestě, která před chvílí neexistovala, je pro direnv soubor, který nikdy neviděl, a první cd do nového worktree byl zodpovězen direnv: error .envrc is blocked. Naměřeno 2026-09-09: z 37 worktree, které nesly .envrc, jich bylo 36 zablokováno a jediný schválený byl primární checkout. create, ensure a každý přesunutý krok migrate proto přenášejí schválení primárního checkoutu na novou cestu — direnv allow na .envrc worktree v okamžiku, kdy cesta existuje — a hlásí, co se stalo, na řádku envrc a v poli envrc JSON.

Přenášeno, ne uděleno: .envrc worktree musí být bajt po bajtu shodné s primárním checkoutem a primární checkout musí být sám schválen, jinak není schváleno nic a report říká které (differs, not_approved_in_primary). Větev s vlastním .envrc je soubor, který člověk nečetl, a schvalovat ho za něj je jediná věc, které má direnv allow zabránit. Bez direnv v PATH je výsledek direnv_absent a nic není blokováno, protože by soubor nic nenačetlo.

Strojově lokální .envrc.local primárního checkoutu se sdílí ve stejném okamžiku. .envrc repozitáře načítá .envrc.local z adresáře, do kterého se vstoupí, a pravidlo adaptéru drží tento soubor bez programu, který by vyhledání primárního checkoutu potřebovalo. Nový worktree proto dostane symlink na .envrc.local primárního checkoutu a vlastní exporty člověka, včetně tajemství uložených v keychainu, jako je OPENAI_API_KEY, se tam načtou také, z jednoho souboru. Odkaz se vytvoří jen tam, kde git název ignoruje (jinak not_ignored), a worktree s vlastním .envrc.local si ho ponechá (own_kept).

Hooky jeho vlastního stromu

Repozitář, který sleduje své háčky (.githooks/, jmenované v core.hooksPath), chce, aby se každý commit posuzoval háčky stromu, ve kterém vzniká. core.hooksPath žije v konfiguraci, kterou sdílí každý worktree, takže jakmile obsahuje absolutní cestu — <primary>/.githooks, jako tady —, každý propojený worktree spouští háčky primárního checkoutu. Dne 2026-10-14 byl primární checkout o tři dny pozadu a doctor, které jeho háčky spouštěly, odmítlo každý commit aktuálního masteru v každém worktree (FAIL wiring ssh-permissions-on-commit … not invoked by <primary>/.githooks/pre-commit); I2718.

Každý propojený worktree má proto vlastní cestu k hookům. create, ensure, každý přesunutý krok migrate a repair čtou politiku repozitáře z efektivního core.hooksPath primárního checkoutu, najdou adresář, který uvádí, uvnitř worktree, a když by git spustil hooky jiného checkoutu, svážou worktree s jeho vlastními přes konfiguraci gitu pro jednotlivé worktree:

git config core.repositoryformatversion 1          # only when it was 0
git config extensions.worktreeConfig true          # only when it was off
git -C <worktree> config --worktree core.hooksPath <worktree>/.githooks

Hodnota je absolutní, takže přesunuté worktree se znovu naváže na své nové umístění. Zpráva říká, co se stalo, na řádku hooks a v poli hooks JSON (set, own, not_configured, shared, untracked, failed). Nic se nevymýšlí: repozitář bez core.hooksPath ponechává vlastní adresář hooků gitu, adresář hooků mimo primární checkout je sdílen záměrně a ponechán beze změny a strom, který adresář nenese, si ponechá primární místo žádného. Relativní .githooks git už řeší proti vrcholu každého worktree a hlásí se jako own. Primární checkout se nikdy nemění.

doctor, spuštěné v linked worktree, které git posílá do hooků jiného checkoutu, selže s wiring hooks-path a přesným příkazem, který to opraví, a posuzuje zapojení vlastního adresáře worktree — co bude spouštět po opravě — ne to zastaralé.

Poslední krok je ten, za kterým žádný mechanismus nestojí. Vytvořit worktree je jeden příkaz; odstranit ho je rozhodnutí, k němuž nikoho nic nenutí, a cleanup záměrně nic nemaže — jmenuje, co je sloučeno a čisté, a akt nechává na člověku, protože nástroj, který by odstranil worktree na základě sloučené větve, by nakonec odstranil práci, kterou někdo nedokončil. Cena je skutečná a zaplatila se tu 2026-09-08, osmnáct hodin poté, co topologie přistála: patnáct worktree mezi sebou drželo 104 GB adresářů Rustu target/, devět z nich s větvemi už sloučenými do trunku, a svazek klesl na 124 MiB volného místa. Nic v topologii nic neuvolňuje a pro kontejner není deklarován žádný rozpočet, takže „stůj“ říká disk — a říká to slovníkem, který zrovna použije další selhávající subsystém. Tři řekly, že jejich obsah je špatně. Proč je mechanismus nepřítomný, a ne chybějící, viz ADR 0021.

Pokud držíte worktree, jehož větev přistála, worktree cleanup vám to řekne; git worktree remove <path> a git branch -d <branch> jsou ty dva příkazy a adresář target/ uvnitř je obvykle většinou toho, co stojí.

Migrace

worktree migrate --plan uvádí každý špatně umístěný worktree s větví: kde je, kam patří, jak by se přesunul, nepotvrzenou práci, která se přesune s ním, a co mu brání. Obyvatel kontejneru, pokud nějaký je, je první — každý jiný cíl leží uvnitř kontejneru, a dokud worktree kontejnerem je, vznikly by tyto cíle uvnitř tohoto worktree. Výjimky — odpojené worktree, zastaralé registrace, dočasné pracovní checkouty, primární checkout mimo trunk — jsou uvedeny s tím, co s každou z nich udělat.

worktree migrate přepočítá plán pod zámkem repozitáře a pro každý pohyblivý krok:

  1. pořídí otisk worktree: větev, HEAD, index (každá sledovaná cesta s režimem, blobem a stagem), staged diff, unstaged diff, každý nesledovaný soubor s velikostí a hashem obsahu, každá ignorovaná položka s cestou a velikostí;
  2. požádá git o přesun — git worktree move, jedno přejmenování, včetně špinavého stavu; obsah kontejneru se vyvede do pracovní cesty a pak dovnitř; přesun mezi souborovými systémy se odmítne, pokud není --allow-copy, a pak se provede kopií, git worktree repair, ověřením proti manifestu každé položky stromu a teprve potom odstraněním originálu;
  3. znovu vezme otisk v cíli, ověří, že jej tam git registruje, a krok hlásí jako moved jen když se oba otisky rovnají — jinak failed, s tím, co se liší, a nic dalšího se nedotkne;
  4. pojmenovává relativní symbolické odkazy, které se z nové cesty už nerozřeší (node_modules -> ../sibling/node_modules), které přesun nezměnil a nepřepisuje.

Nic se neresetuje, nestashuje, nečistí, nečekautuje ani nemaže. Zamčený worktree je blokován, dokud není odemčen. Cíl, který existuje — registrovaný worktree jiné větve, cizí git checkout, adresář prázdný či nikoli, soubor, odkaz — je konflikt pojmenovaný druhem a nikdy se nepřepíše. Pokud byl příkaz spuštěn z worktree, který se přesunul, report říká, kam cd.

Výkon

Vracení

majordomus worktree cleanup vypíše, co je nadbytečné: každou větev slitou do trunku, jejíž worktree je čistý nebo chybí. --remove odstraní tyto worktrees a nic jiného — větve se nikdy nemažou, protože dochází disk a větev je jediné trvalé jméno, které práce má.

Výpis a odstranění jsou dva okamžiky a vše, co činí worktree bezpečným k odstranění, se mezi nimi může změnit, takže výpis jen nominuje: --remove čte postavení větve vůči jejímu remote, zda uvnitř něco běží a zda je strom opět čistý, u každého kandidáta bezprostředně před jeho odstraněním a jmenuje, co odmítá:

odmítnutíproč to nepokrývá „sloučeno a čisto“
před svým remote, bez upstreamu, nebo upstream zmizelsloučená historie větve je na vzdáleném serveru; commit nad ní je na jednom disku a to, že je větev sloučena, o tom nic neříká
proces má uvnitř svůj pracovní adresářmtime lže: dva worktrees uklizené 2026-09-15 vypadaly od 12. nedotčené a měly v sobě živé procesy
necommitnutá prácepřečteno znovu v okamžiku odstranění, nevzato z výpisu
lsof chybí, nebo git nemohl porovnat s upstreamemnevědět není totéž co nic tam není

test/cases/611_the_reclaim_refuses_what_it_cannot_prove.sh nasází fixture s vlastním remote: volný worktree, který odejde, a větev před svým remote, jednu nikdy nepushnutou, jednu, jejíž vzdálená větev byla smazána, jednu s procesem uvnitř a jednu špinavou před výpisem, které zůstanou. Zahrnuje kombinaci, kvůli které zamítnutí existují: větev mergnutá do trunku a nesoucí commit, který její remote nikdy neviděl. Co se změní po výpisu — commit, smazaná vzdálená větev, zapsaný soubor — nasázejí unit testy reclaimu v apps/majordomus-cli/src/commands/worktree.rs. Chybějící lsof se nenasazuje nikde.

Checkout a jeho vzdálenost od trunku

Dne 2026-10-16 byl primární checkout o 779 commitů za origin/master, s necommitnutými změnami, které nikdo nedokázal přiřadit. Jeho sdílený server odpovídal na plánovací otázky každé relace z toho stromu a jeho místní master byl základem, z něhož se dělaly nové větve. Každé čtení říkalo, že server je připraven; žádné neříkalo, že strom, který servíroval, není trunk. project.a-checkout-serves-the-current-trunk z té vzdálenosti dělá čtení.

worktree::trunk::measure počítá pro HEAD checkoutu i pro lokální větev trunku commity vzdáleně sledovaného trunku, které každému chybí (behind), a commity, které každý má a trunku chybí (ahead). Vzdálený trunk je upstream trunku, jinak remote, jehož HEAD trunk jmenuje, jinak první remote s větví tohoto jména. Nic se nestahuje: odpověď platí k poslednímu fetchi a fetched_at (čas FETCH_HEAD) říká, kdy to bylo. Za probíhajícího merge se jeho příchozí commity počítají jako přítomné, takže merge, který větev aktualizuje, se nikdy neposuzuje podle stromu, který nahrazuje.

Prahy jsou prahy politiky (.ai/repo/policy.yaml, checkout.trunk_distance) a nic nečte výchozí hodnotu, když chybějí. Stav checkoutu je to, co servíruje jeho server; stav lokálního trunku (local_trunk_standing) je to, z čeho začíná větev z něj vytvořená. V propojeném worktree je lokální trunk věcí posunu jiného checkoutu, takže doctor ho hlásí jako WARN clone local-trunk a nikdy kvůli němu neselže commity tohoto worktree.

Totéž čtení se objeví všude, kde se strom poskytuje:

  • majordomus worktree trunk (worktree.trunk, majordomus_worktree_trunk, GET /api/v1/worktrees/trunk) na to odpovídá sám a končí kódem 10, když je checkout zastaralý;
  • majordomus worktree status vytiskne řádek currency a vrátí trunk_distance;
  • server.status (majordomus serve status, majordomus_server, GET /api/v1/server) jej nese jako trunk pro checkout, který server obsluhuje;
  • instrukce MCP initialize přidají jednu větu — „Tento server servíruje strom o N commitů za origin/master“ — když je vzdálenost zaostávající, zastaralá nebo neposouzená;
  • majordomus doctor to vykresluje pod clone.

Náprava, kterou každé čtení jmenuje, uvede checkout do aktuálního stavu: fast-forward checkoutu trunku, merge vzdáleného trunku do feature větve (pushnutá větev se nikdy nepřepisuje) a fast-forward lokálního trunku tam, kde je checkoutnut. Necommitnutá práce se nejprve zachrání — git stash create, git update-ref refs/rescue/<checkout>-<timestamp> s tím commitem, nesledované soubory zkopírované vedle. Typovaná majordomus worktree update, která dělá přesně toto a odmítá, dokud v checkoutu stojí proces, je dalším řezem pravidla. test/cases/3176_a_checkout_serves_the_current_trunk.sh drží vzdálenosti, postavení, verdikty doctoru a případ rozpracovaného mergu proti fixture remote.

Necommitnutá práce, kterou nikdo nedrží

Větev, jejíž commity nedosáhnou žádného remote, jmenuje doctor (clone unpushed). Práce, která nedosáhla žádného commitu, jmenována nebyla: 2026-10-07 polovina oprav bezpečnosti integrace o důvěře v nahrazení ležela jako 45 nezacommitovaných souborů ve worktree skončené relace a 2026-10-08 doktrína dokončení ležela jako 21 připravených souborů v jiném. Obojí se našlo, protože někdo náhodou četl ty adresáře, a pushlo se jako větve rescue/...; téhož večera mělo datové úložiště volných 125 MiB (I1995).

Práh je session.stranded_after z politiky, ticho, po jehož uplynutí se klient epizody považuje za odešlého. Odpovídá na obě zde položené otázky — drží otevřená epizoda stále práci a čekala práce, kterou nic nedrží, dost dlouho na to, aby byla opuštěná — takže neexistuje druhé číslo, které by se od něj rozcházelo; --older-than jmenuje jiné pro jedno čtení. Politika, která žádné nedeklaruje, nepovažuje nic za opuštěné a říká to.

majordomus doctor vykreslí odečet: jedno WARN clone <path> na opuštěný worktree s jeho počtem a stářím a příkaz rescue jako nápravu; držená a nedávná práce se počítá v jednom OK. Odečet vyžaduje jedno git status na propojený worktree, asi 15 s na tři sta z nich, proto .githooks/pre-commit spouští doctor jako MAJORDOMUS_DOCTOR_CONTEXT=commit bin/majordomus doctor: v tomto kontextu, jediném, který doctor přijímá, se odečet vynechá a řádek INFO clone uncommitted to řekne a jmenuje majordomus worktree uncommitted. Ani odečet, ani doctor nic nezapisuje: každé git status běží pod GIT_OPTIONAL_LOCKS=0, takže se neobnovuje žádný index a .ai/local/ jiného worktree se čte, nikdy nezapisuje. test/cases/3025_abandoned_work_in_a_worktree_is_named.sh zasadí opuštěný worktree, držený a nedávný a drží git status každého worktree bajt po bajtu shodné napříč odečtem, nástrojem MCP a doctorem.

Nečinné inkrementální relace ve sdíleném build adresáři

rustc drží inkrementální stav cratu jako adresáře relací pod <build-dir>/<profile>/incremental/<crate>-<hash>/ a dokončenou odstraní jen pozdější kompilace téhož cratu. Crate, který se přestane kompilovat, zanechá poslední relaci a v build adresáři sdíleném každým worktree to znamená zbytky každého worktree. Zastaralé artefakty crate a žádný úklid pod běžícím sestavením

Každý build majordomus-cli zapíše svou knihovnu, spustitelný soubor, každou testovací a bench binárku a na macOS jeden objektový soubor na codegen unit do <build-dir>/<profile>/deps pod názvem <target>-<hash>. The bound, while builds run

The sweeps above remove what is old and ask nothing about the size of what remains. On 2026-10-23 the shared build directory held 102 GB against its 6144MB bound (MAJORDOMUS_SHARED_BUILD_CAP_MB, ADR 0139), and at 16:30Z its debug/deps held 51 GB in eleven generations of this crate, every one of them younger than the deps sweep's 120 minutes. scripts/reap-orphans reduced it only as a whole and only when no cargo or rustc ran anywhere on the machine, which with nine sessions building was never.

So the bound is applied between builds, by the builds: mj_rust_bound_build_dir in lib/rust_bin.sh runs after the sweeps above before a build, after a bounded build has finished (mj_rust_bound_after_build, at most once every two minutes per build directory), and from scripts/reap-orphans when a build is running. While the directory is over its bound it evicts whole stale units, oldest first, until it is under it:

jednotkawhen it is stalepořadí
a coverage run's llvm-cov-targetno file in it written within MAJORDOMUS_SHARED_BUILD_EVICT_IDLE_MIN minutes (default 60)první
a dependency's generation (its deps files, fingerprint and build-script output, by unit hash)its crate version, read from the generation's dep-info, is named by no worktree's Cargo.lock, and it is idle as aboveprvní
a finished incremental sessionidle as aboveby age
a generation of this crate's own unitsidle as aboveby age

Each profile's units are evicted only inside cargo's own lock on that profile. A unit is asked again inside it: one written since, one with a file some process holds open, and every unit of a profile some process names (a test binary, a doctest) are kept, and each is said. The pass before a build takes only a lock that is free. Measured on 2026-10-23 with four cargo processes running, the shared debug profile's lock was held at 40 of 40 probes in a minute, so the pass after a build, when the directory is over its bound, waits for each profile's lock in the background, bounded by MAJORDOMUS_SHARED_BUILD_EVICT_LOCK_WAIT seconds (default 900; 0 waits for none). There is one waiter per build directory, and its log and pid are kept under ~/.cache/majordomus/bound-<cksum>.{log,pid}. The build that finished does not wait.

What it cannot evict it says: a bound smaller than one generation cannot hold the newest generations of the trees building now, and a dependency some Cargo.lock names is never a candidate. scripts/reap-orphans --targets while a build runs is the dry run: it lists every unit it would evict, with its size, idle minutes and whether its profile is locked now. MAJORDOMUS_SHARED_BUILD_EVICT_IDLE_MIN=0 evicts nothing. test/cases/3959_the_shared_build_dir_stays_under_its_bound.sh proves each row.

Soukromé adresáře sestavení

Build, který čeká MAJORDOMUS_BUILD_LOCK_WAIT sekund za zámkem jiného worktree, se znovu buildí v ~/.cargo/build-private/<cksum of the tree's root> (mj_cargo_private_dir; nic v ~/.cargo/config.toml je nevytváří — dělá to mj_cargo_bounded exportem CARGO_BUILD_BUILD_DIR). Každý je studený build všech závislostí, několik GiB, a na stroji, kde buildí mnoho relací, většina buildů čeká tak dlouho, takže skoro každý worktree, který kdy buildil, jeden zanechal. Dne 2026-10-17 držely 178 GiB v 35 adresářích, z nichž 25 bylo nečinných déle než dvě hodiny, a svazek dosáhl 3.9 GiB.

All three sweeps and the bound's eviction are off in the test suite (test/run.sh sets MAJORDOMUS_INCREMENTAL_IDLE_MIN, MAJORDOMUS_DEPS_IDLE_MIN, MAJORDOMUS_PRIVATE_BUILD_IDLE_MIN and MAJORDOMUS_SHARED_BUILD_EVICT_IDLE_MIN to 0): a case must not act on the machine it measures. scripts/ci/backlog-check refuses a tree in which a build no longer sweeps before it starts, a sweep no longer takes cargo's lock or asks the process table, or the runner leaves them on (rule project.accumulation-is-measured).

What the sweeps do not see

The floor, its refusal and the three sweeps measure build output only. On 2026-10-19 the volume fell to 17 GiB free while the worktrees' build directories were small: one session's scratch directory held 12 GB, $TMPDIR 9.6 GB and swap 5 GB. When the floor refuses and the five directories it names do not add up to what is missing, measure the rest before removing anything: du -sh "$TMPDIR", each agent session's scratch directory, and sysctl vm.swapusage. A session's scratch directory is that session's: it is emptied by the session or after the session has ended, never under a live one. Swap shrinks only as memory is given back. Teaching the floor's refusal to name these is a tool change of its own.

Path crate, který sestavil jiný worktree

Sdílení adresáře buildu sdílí každou jednotku, kterou cargo pojmenuje cestou relativní k workspace, takže tentýž path crate zkompilovaný ze dvou worktrees je jeden slot. Build skript majordomus-cli se znovu spouští při MAJORDOMUS_BUILD_TREE (.cargo/config.toml), čímž jeho slot zastarává v každém stromu kromě toho, který ho zapsal. Path crate bez toho build skriptu to nedostane: 2026-10-17 build dávky 71b znovu použil majordomus-core, který jiný worktree zkompiloval proti jiným verzím závislostí, a selhal s „multiple different versions of crate serde_json“. Dotek src/lib.rs toho crate vynutil přestavbu. Každý path crate workspace potřebuje totéž cargo:rerun-if-env-changed=MAJORDOMUS_BUILD_TREE ve vlastním build skriptu.
