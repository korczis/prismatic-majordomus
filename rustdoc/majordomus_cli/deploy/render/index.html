Module render 

Source
Expand description

The provider artifacts, rendered from the canonical deployment object: the container image definition, the ignore file that bounds its build context, and the provider configuration.

None of the three is authoritative and none is written by hand. Each carries a header naming the object it came from and the command that regenerates it, and majordomus generate --check refuses a tree where one of them was edited. That is the whole point of the kind: the port, the routes, the resources, the machine count and the build inputs are stated once, and these files are views of that one statement.

Constants§

APP_DIR
Where the layer and the tool distribution live inside the image.
COMMIT_ARG
The build argument that carries the commit into the builder stage. It is the variable the crate’s build script reads, so an image built with it answers the commit on its health routes and one built without it answers unknown.
DIRTY_ARG
The build argument that says whether that commit’s tree was dirty (true/false).
DOCKERFILE
Where the image definition goes.
DOCKERIGNORE
Where the build context’s ignore file goes. Docker reads it from the context root, so it lives at the repository root whatever the image definition’s own path is.
FLY_TOML
Where the provider configuration goes. Fly reads fly.toml from the working directory.
RUNTIME_IMAGE
The runtime base, pinned for the same reason.
RUN_USER
The unprivileged user the deployed process runs as.
RUST_IMAGE
The Rust toolchain the builder stage pins. A floating tag would make the image a different thing on different days, which is the opposite of what a deployment is for.

Functions§

artifacts
The three artifacts of one deployment.
dockerfile
The container image, as a multi-stage build: a builder that holds the toolchain and a runtime that holds the binary, the layer and nothing else. The runtime carries no compiler, no cargo registry, no repository history and no shell history — what is not copied in cannot leak out.
dockerignore
The build context: nothing but the declared inputs. Everything is excluded and each input is let back in, so a file that appears in the repository tomorrow does not appear in the image tomorrow.
fly_toml
The provider configuration. Every value here is read from the object; nothing is stated twice, and the [build] section points at the generated image definition.
