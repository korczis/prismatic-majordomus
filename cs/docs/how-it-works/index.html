Vykresleno z docs/HOW_IT_WORKS.md — stejného Markdownu, který zobrazuje GitHub.

Majordomus lze snadno špatně pochopit jako nástroj příkazové řádky, HTTP API, server MCP, dashboard a složku pravidel v Markdownu, které se náhodou dodávají společně. Tento dokument vysvětluje, proč je toto čtení chybné a kde je přesto správné. Sleduje fakt od souboru, kde je zapsán, přes index a typovaný registr, které jej drží, přes kontroly, které rozhodují, zda je pravdivý, až ke každému rozhraní, které jej ukazuje — a pojmenovává každé místo, kde repozitář tomuto tvaru zatím nedostává.

Každé tvrzení zde bylo ověřeno proti kódu v commitu, který tento soubor naposledy změnil, a po jednom tvrzení auditováno druhou relací. Kde se kód a návrhový záznam rozcházejí, vítězí kód a rozpor je uveden pod Architecture debt. Čísla se do tohoto dokumentu nepíší: každé je uvedeno jako příkaz, který je měří, protože číslo zkopírované do prózy je zastaralé den po napsání (project.no-counts-in-prose).

Teze

Majordomus by měl fakt jednou objevit a zmodelovat a pak z této kanonické reprezentace odvodit každé relevantní rozhraní.

Ta věta není preferencí opětovného použití kódu. Je to mechanismus proti driftu. Repozitář, na kterém současně pracuje několik lidí a několik AI pracovníků, hromadí popisy sebe sama: seznam příkazů v README, další v textu nápovědy, třetí ve schématu API, čtvrtý v dashboardu, pátý v seznamu nástrojů agenta. Každý je správný v den, kdy vznikl, a každý udržuje ten, kdo si na něj vzpomene. Víc pracovníků a víc rozhraní kopie násobí a agentní vývoj způsobuje, že se kopie rozcházejí rychleji.

Majordomus jde opačným směrem: jeden model, mnoho projekcí. Projekce smí fakt vykreslit jinak, filtrovat ho nebo spojit s jinými. Nesmí o něm mít druhý názor.

Čtěte od shora. Lidé a pracovníci píší malou sadu kanonických souborů. Objevování je nachází přes deklarace místo ručně vedených seznamů, index dává každému typovanou identitu a registr schopností drží každou operaci, kterou spustitelný soubor umí. Každý povrch se ptá stejného executoru. Odvozený stav — zda je pravidlo prokázáno, jaký je stav úkolu, jaké je prostředí checkoutu — se počítá z kanonických a pozorovaných vstupů; kde se drží kopie (commitnuté projekce, cache prostředí), kontroluje se proti těmto vstupům nebo se z nich znovu staví a nikdy se nepovažuje za zdroj. Generované soubory dole jsou commitnuté a kontrolované, takže rozpor mezi modelem a jeho projekcemi shodí build, místo aby se dostal ke čtenáři.

Většinu váhy nesou dvě rozlišení.

Objevování není odvozování. Objevování znamená, že informace už někde autoritativně existuje a Majordomus ji najde: soubor pravidla odpovídající pathspecu, modul pojmenovaný v kompozici, worktree uvedený gitem. Odvozování znamená, že Majordomus navrhne pravděpodobný výklad. Jediné odvozování v kompilátoru kontextu je relevance podle klíčových slov a je omezeno pod přímou deklaraci — drží to test an_inference_is_never_as_confident_as_a_declaration — ne však pod každý vztah dosažený slabými nebo vícekrokovými hranami (viz Kontext pro relaci).

Pozorované není kanonické. To, že je peer online, není deklarace, kterou někdo učinil; je to současná realita a vyprší. Nic z nástěnky peerů ani z registru meshe se neukládá, jako by to byl fakt o repozitáři.

Schémata

Existují dva řetězce schémat, jeden pro každý druh věci, a žádný se nepíše dvakrát.

Spustitelné operace. Vstup a výstup schopnosti jsou běžné typy Rustu, které odvozují schemars::JsonSchema. CanonicalSchema::of::<T> převede typ na jednu hodnotu JSON Schema 2020-12 (apps/majordomus-cli/src/capability/schema.rs) a ta se vykresluje čtyřmi způsoby: inline pro MCP (for_mcp), jako komponenty OpenAPI (for_openapi), jako formulář runneru Cockpitu a do docs/generated/registry.json. Parametry dotazu HTTP se převádějí přes totéž schéma. Žádné schéma schopnosti není ručně udržovaný dokument — není tu rozhraní TypeScript ani samostatná definice Swagger — přestože jeden typ Rustu, design::Ordered<T> (seřazená mapa), implementuje JsonSchema ručně, ne derivací.

flowchart LR
  d2_T["Rust type with derive JsonSchema"] --> d2_S["CanonicalSchema"]
  d2_S --> d2_M["MCP inputSchema and outputSchema"]
  d2_S --> d2_O["OpenAPI components"]
  d2_S --> d2_F["Cockpit runner form"]
  d2_S --> d2_J["docs/generated/registry.json"]
  d2_S --> d2_Q["HTTP query coercion"]

Dokumenty repozitáře. Každý druh deklarovaný v share/kinds.yaml jmenuje identitu schématu tvaru <vendor>.<name>/v<n>. Schémata žijí pod share/schemas/majordomus/<kind>/. Většina druhů v Markdownu — pravidla, ADR, dovednosti, prompty, kontextové dokumenty a další (ls share/schemas/majordomus/*/*.proto) — se píše jako zprávy protobuf a jejich JSON Schema se z nich odvozuje; ostatní druhy se píší přímo jako JSON Schema. Hlavička pravidla je například uzavřená zpráva v share/schemas/majordomus/rule/rule.v1.proto, a proto se neznámý klíč front-matteru v pravidle odmítne, místo aby se tiše ponechal.

Generované artefakty mají také schémata, pod share/schemas/generated/. Před zápisem generate zkontroluje každý artefakt na banner původu a každý strukturovaný dokument, který deklaruje kontrakt, proti jeho schématu.

Schopnost: jedna deklarace

Každá operace Rust programu se deklaruje jednou, makrem capability! (apps/majordomus-cli/src/capability/handler.rs). Toto je skutečná deklarace operace, která vysvětluje důkaz jednoho pravidla, z apps/majordomus-cli/src/capability/builtin/rules.rs (popis zkrácen):

capability! {
    id: "rules.show",
    title: "What proves this rule",
    description: "One rule with its full proof: ...",
    input: RuleInput,
    output: RuleDetail,
    stability: Stability::BehaviorallyVerified,
    exposure: Exposure {
        mcp: mcp("majordomus_rule"),
        http: get("/api/v1/rules/rule"),
        cli: Some(CliExposure { path: vec!["rules".into(), "show".into()] }),
    },
    tags: ["rules", "governance", "verification", "evidence"],
    cache: CachePolicy::Disabled,
    handler: show,
},

Registr

Moduly skládají schopnosti pomocí module!; compose_modules! skládá moduly; aplikace sestaví registr pomocí CapabilityRegistry::builder().with_modules(builtin::modules()).with_index(&index). Druhé volání je místo, kde se objevování setkává s rovinou schopností: každý indexovaný objekt se stane schopností Resource (apps/majordomus-cli/src/capability/declarative.rs), čitelnou přes MCP jako majordomus://<kind>/<identity>, takže nový soubor s pravidlem si agent přečte bez jediného řádku v Rustu.

build() validuje celou množinu a sbírá každou chybu místo zastavení u první (apps/majordomus-cli/src/capability/registry.rs): gramatiku id, jmenný prostor shodný s modulem, duplicitní nástroj MCP, duplicitní trasu HTTP, duplicitní cestu příkazu, chybně utvořené vystavení HTTP, neplatnou politiku cache. Registr, který by vystavil dvě operace na jedné trase, nelze sestavit.

Exekutor je jeden. Context::execute (apps/majordomus-cli/src/capability/executor.rs) je jediný volající dispatche registru. Příkazová řádka, HTTP, MCP i Cockpit jdou přes něj, což činí „stejnou operaci na každém povrchu“ vlastností kódu, ne slibem.

Projekce

HTTP

Neexistuje tabulka tras. Router se ptá registru: Router::capability v apps/majordomus-cli/src/http/router.rs volá registry.by_http(method, path), odpoví 405, když sedí jiná metoda, a 404, když nesedí nic, naváže query parametry GET přes vstupní schéma nebo vezme JSON tělo POST a volá Context::execute. Každá HTTP expozice je vynucena pod /api/v1/ přes HttpExposure::PREFIX. Chyby se mapují na 400, 404, 422 a 500 na jednom místě.

Nekapacitní mounty — obsluhovaná domovská stránka, /openapi.json, /swagger, /cockpit, /mcp, proud událostí, /docs/, /rustdoc — jsou deklarovány jednou v zjišťování webových povrchů (apps/majordomus-cli/src/web/; docs/generated/web.json je vypíše), které popisuje docs/WEB.md. Nová operace nepotřebuje vůbec žádný kód HTTP: rules.show nemá v routeru žádný handler, jen generický dispatch.

Ručně se píše obchodní logika za handlerem — apps/majordomus-cli/src/rules/ pro důkaz pravidla — nikdy metadata trasy.

OpenAPI

apps/majordomus-cli/src/http/openapi.rs projde registr a vytvoří dokument OpenAPI 3.1. operationId je id schopnosti, schémata jsou kanonická schémata jako komponenty, příklady jsou případy měření výkonu a rozšíření x-majordomus-* nesou druh a identitu. Je poskytován živě na /openapi.json ze stejného registru, který obsluhuje požadavky, a commitnut jako docs/generated/openapi.json, aby byla změna kontraktu vidět při review. Jedna odpověď zatím není odvozena věrně: dokument připojuje odpověď 422 refused jen k příkazům, ačkoli některé dotazy mohou také odmítnout a router jim přesto odpovídá 422.

OpenAPI je odvozeno z týchž smluv, které obsluhují skutečné požadavky API. Není to druhá dokumentace, kterou je třeba držet v souladu.

Swagger UI

Swagger UI na /swagger je pouze vykreslovač /openapi.json a nic víc (apps/majordomus-cli/src/http/swagger.rs). Není zdrojem pravdy, nedrží žádné definice a nemůže s API nesouhlasit, protože nemá nic vlastního, s čím by nesouhlasil. Jeho assety pro prohlížeč jsou připnuty na jednu verzi a načítají se z CDN — jediná část lokálního povrchu, která nefunguje offline, a modul to říká.

MCP

MCP je projekce téhož registru pro agenty (apps/majordomus-cli/src/mcp/surface.rs):

  • Nástroje jsou každá schopnost, jejíž expozice jmenuje nástroj. inputSchema a outputSchema pocházejí z kanonického schématu; nápověda read-only pochází z druhu. Nápovědy destructive a idempotent zatím nepocházejí z deklarovaného účinku: jsou jednou zapsány v mcp/protocol.rs pro každý nástroj (viz Architektonický dluh).
  • Zdroje jsou každá schopnost, jejíž expozice jmenuje zdroj, plus každý indexovaný objekt jako majordomus://<kind>/<identity>, čtené stejným řešením objektů, jaké používá HTTP endpoint objektů.
  • Volání nástroje se vyřeší pomocí registry.by_mcp_tool a spustí Context::execute.
  • Instrukce, které klient čte na initialize, jmenují nástroje, jež zapisují do repozitáře, změřené z deklarovaného účinku každé schopnosti, a OpenAPI publikuje stejný účinek jako x-majordomus-effect; every_surface_names_what_writes_the_repository_and_nothing_else v apps/majordomus-cli/tests/shared_units.rs drží obojí na registru.
  • Prompty se neinzerují a šablony zdrojů jsou prázdné — záměrně, ne opomenutím.

Žádný nástroj MCP není psán ručně. majordomus_announce, který vypadá jako zvláštní koordinační nástroj, je běžná schopnost peers.announce. Jediné ručně kódované chování je v mostu MCP (apps/majordomus-cli/src/mcp/bridge.rs), který tento nástroj rozpozná, aby mohl po opětovném připojení přehrát oznámení klienta na nový server.

Příkazová řádka: kontrolovaná druhá deklarace

Tady je model k sobě upřímný. Příkazová řádka není generována z registru. Strom clap v apps/majordomus-cli/src/cli.rs je psán ručně, odesílán ručně psaným matchem a vykreslován textovými funkcemi v každém modulu příkazu. Zdroj to říká: apps/majordomus-cli/src/capability/closure.rs uvádí, že příkazová řádka „je deklarována podruhé, v clap“.

To, co brání tomu, aby se ta druhá deklarace rozešla, je, že se kontroluje v obou směrech:

  1. Od deklarace k přítomnosti. Schopnost, jejíž CliExposure pojmenovává cestu, která ve stromu clap neexistuje nebo existuje, ale nelze ji spustit, selže v closure.rs a v testu projekce.
  2. Přítomné k deklarovanému. Každý příkaz clap, který nevykresluje schopnost, musí figurovat v cli::LOCAL (apps/majordomus-cli/src/cli/local.rs) s typovaným důvodem — vykresluje schopnost, zapisuje repozitář, je alias, je lokální pro relaci, nebo spravuje proces. quality::parity kontroluje seznam proti stromu oběma směry a scripts/ci/projection-check selže u příkazu bez důvodu.
  3. Stejný executor. Příkaz, který vykresluje schopnost, volá ctx.execute(id, input); jeho vlastní kód je jen prezentace (report_text, show_text v apps/majordomus-cli/src/commands/rules.rs) a --format json vypíše hodnotu schopnosti beze změny.

V praxi se cesta příkazu píše třikrát: ve strukturách clap, v CliExposure schopnosti a jako doslovná slova, která modul příkazu předá registry.by_cli, aby našel svou schopnost. Výše uvedené kontroly drží tyto tři v souladu; neudělají z nich jedno. Ne každý spustitelný příkaz je projekcí schopnosti — mnoho z nich jsou položky LOCAL, které vykreslují sdílenou doménovou logiku, zapisují do repozitáře, aliasují jiný příkaz nebo spravují proces. Rozdělení změřte, nevěřte zde napsanému číslu:

$ jq '[.. | objects | select(.executable? == true)] | length' docs/generated/cli.json
$ jq '[.capabilities[] | select(.exposure.cli)] | length' docs/generated/registry.json

Vedle ručně vykreslených příkazů existuje generický a je odvozený. majordomus-cli run <capability-id> [--input JSON] (apps/majordomus-cli/src/commands/executions.rs) provede jakoukoli registrovanou schopnost tímtéž executorem a vypíše její hodnotu — protějšek runneru Cockpitu v příkazové řádce. Každá schopnost je tedy dosažitelná z příkazové řádky; vyhrazený příkaz s vlastními slovy a lidským rendererem existuje jen tam, kde pro něj byl napsán příkaz clap. Indexované objekty se čtou stejně, přes entity kinds a entity show (schopnosti entity.kinds a entity.show, také přes HTTP a MCP), nebo přes run objects.list.

Cockpit není další aplikace, databáze ani doménový model. Co se stane, když se přidá schopnost

Poctivý vývojářský postup na výchozí větvi dnes:

  1. Doménové chování napište do vlastního modulu pod apps/majordomus-cli/src/.
  2. Deklarujte schopnost pomocí capability! v modulu pod apps/majordomus-cli/src/capability/builtin/, se vstupními a výstupními typy odvozujícími JsonSchema a vstupem implementujícím BenchmarkCases. Pokud je modul nový, přidejte jej do seznamu pub mod a do builtin::modules() — jediný ruční krok skládání.
  3. HTTP, OpenAPI, Swagger UI, MCP a spouštěč Cockpitu se objeví bez dalšího kódu, pro každé vystavení, které deklarace jmenuje; spouštěč potřebuje vystavení přes HTTP a run <id> k němu z příkazové řádky dojde tak či onak.
  4. Je-li schopnost vystavena na příkazové řádce, přidejte variantu clap, dispečujte ji přes ctx.execute, napište textový renderer a přidejte spustitelný příklad. Closure a parity selhávají capabilities validate, projekční test a projection-check, dokud se deklarace a strom neshodují; samotný build uspěje.
  5. Spusťte just derive (scripts/derive: generate, data webu, znovu generate, pak .gitattributes), což přepíše registr, OpenAPI, reference, inventář měření a data webu; samotné majordomus generate data webu nepřepíše. Commitněte je se změnou. Pre-commit hook odmítne commit, jehož data webu jsou zastaralá, a — je-li spustitelný soubor sestaven — takový, jehož projekce registru jsou zastaralé.
  6. Testy. Generické testy projekcí pokrývají novou schopnost automaticky. Vlastní pin test modulu vypisuje jeho schopnosti a jejich vystavení, takže přidání jedné do existujícího modulu znamená rozšířit tu tabulku; poté přidejte behaviorální případ pro to, co dělá.
  7. Tvrzení a důkazy. Je-li schopnost veřejnou zárukou, přidejte do docs/CLAIMS.yaml tvrzení s jeho testem a detailní stránku pod docs/claims/; běh testu zaznamenejte pomocí majordomus-cli evidence record.
  8. Verze. Veřejná plocha se změnila, takže majordomus-cli release analyze nyní dluží bump; release bump jej zapíše (viz Publikace a verze).

Nic se neregistruje zvlášť v HTTP, OpenAPI, Swaggeru, MCP, Cockpitu ani referenci. Příkazová řádka je zbývající druhá deklarace a je kontrolovaná. Cíl nulové registrace — nová kanonická entita, která dosáhne každého relevantního povrchu bez kroku na povrch — je splněn pro každý povrch kromě příkazové řádky a skládání modulů.

Rust engine pravidel (apps/majordomus-cli/src/rules/mod.rs) to redukuje na jeden stav z RuleState, nejsilnější první: proven, inputs_unchanged, stale, gated, failing, not_run, reviewed, unrunnable, dangling, unproven. Visící cesta činí pravidlo dangling — převažuje nad vším; jinak selhávající test činí pravidlo failing; jinak je jeho stav nejslabší z testů, které mohou nést důkaz. Za prošlé se počítají jen první tři. Nález se vznáší pro visící důkaz nebo pro blokující pravidlo, které je nedokázané, selhává nebo nejde spustit; not_run, gated a reviewed záměrně nálezy nejsou, protože popisují absenci záznamu, ne vadu.

scripts/ci/rule-proof-check je kontrola: visící (dangling) důkaz selhává a pravidlo jakékoli třídy, které nejmenuje žádný validátor, žádný test a žádné reviewed_because, selhává — třída není výjimka. Jediná výjimka je vendorované pravidlo označené principle. Drží ho ratchet, jehož základní stav, .ai/repo/rule-proof-baseline.txt, je prázdný.

Abyste viděli, kde repozitář stojí — ne abyste věřili slovu tohoto dokumentu:

V době psaní ten report říká, že každé blokující pravidlo buď jmenuje důkaz, který se vyřeší a je navázán na kontrolu, nebo deklaruje reviewed_because a vynucuje ho člověk (rules report --class blocking uvádí které), a že v ledgeru je zaznamenáno málo běhů, takže většina pravidel stojí na not_run místo proven. To je správné čtení důkazů: kontroly běží v CI při každé změně a CI zaznamenává své běhy do artefaktu na běh (scripts/ci/evidence-collect), ale nic je zatím nepřenáší do sledovaného ledgeru (ADR 0080, navrženo). „Satisfied“ v reportu znamená žádný nález — nic nevisí a žádné blokující pravidlo není nedokázané, selhávající ani nespustitelné; zahrnuje reviewovaná pravidla a poradní pravidla, která žádný důkaz nejmenují. Neznamená, že zaznamenaný běh prošel. Zelený odznak kdekoli v Majordomu musí být projekcí zaznamenaného provedení; kde žádné zaznamenáno není, povrchy říkají not run, gated nebo reviewed — nikdy proven.

Hooky poskytovatele (pro Claude Code v .claude/hooks/) volají majordomus capture session při startu, compactu a ukončení. Životní cyklus úlohy je start s povinným rozsahem, check, které rozesílá doktríny na ni vázané, a finish s výsledkem a, pokud to profil vyžaduje, ověřovacím příkazem, jehož exit kód se zaznamená. Dokončení, které selže v doktríně, je odmítnuto s exitem 10 a seznamem nesplněného.

Kontext pro relaci

Kontext se kompiluje na několika místech a každé je deterministické. Kromě tří níže lib/session_context.sh skládá pracovní kontext otevřené epizody při každém čtení.

majordomus context (lib/context.sh) sestavuje seřazené sekce — git, peery, úlohu, profil, kontextové dokumenty, otevřené otázky, kandidáty znalostí, rozhodnutí, uvažování, checkpoint, předávku, integraci, relevantní soubory, historii, prompt — řízené přepínači profilu a vtěsnané do řádkového rozpočtu politiky. Sekce se zahazují od nejméně spolehlivé — historie, integrace, soubory, dokumenty, znalosti, uvažování, rozhodnutí, pak těla checkpointu a předávky, která před zahozením zkrátí na řádek s ukazatelem, pak peery — a git, úloha, profil a otevřené otázky se nezahazují nikdy. Každé zahození je uvedeno pod EXCLUDED; pokud je výstup stále nad rozpočtem, příkaz skončí exitem 10 místo tichého zkrácení.

majordomus context resolve <path> (lib/context_docs.sh) skládá kontextové dokumenty, které platí pro cestu: každý Markdown soubor context/v1 pod .ai/, jehož rozsah ji pokrývá — přesný adresář, obsahující podstrom nebo explicitní seznam cest — seřazené podle hloubky, pak deklarovaného pořadí, pak cesty, s odstraněnými nahrazenými dokumenty a otiskem nad řetězcem. Každý dokument přidává k svým předkům; nejbližší je nenahrazuje.

devcontext.compile je kompilátor v Rustu pro seřazenou pracovní množinu úlohy (apps/majordomus-cli/src/devcontext/). Prochází složený graf objektů od úlohy po typovaných hranách s pevnými dopřednými a zpětnými vahami, řadí podle úrovně autority — úloha, governance, zdroj, rozhodnutí, znalost, historie — poté podle relevance, poté podle URI a utrácí tokenový rozpočet metodou first fit, přičemž pojmenuje každou přeskočenou položku a její cenu. Jeho jediné odvozování je záměr: slova úlohy porovnaná s titulkem, popisem, identitou a tagy objektu, omezená pod přímým semínkem a pod většinou jednotlivých deklarovaných hran (devcontext/select.rs); stále může předstihnout deklarovaný vztah dosažený slabou nebo vícekrokovou hranou a úroveň autority se řadí před relevancí. Příkaz shellu context jej zatím nepoužívá.

Kontext se generuje, protože musí být znovu sestavitelný. Kontext, který existuje jen uvnitř dřívějšího promptu, se ztratí spolu s ním; kontext zkompilovaný ze stavu repozitáře může příští pracovník zkompilovat znovu a vysvětlit ho položku po položce.

Předávka

majordomus handover bere tělo na stdin se sekcemi, které politika vyžaduje — Objective, Current State, Next Action — nebo ho odvodí pomocí --derive. Tělo je autorské; front matter je odvozený: repozitář, worktree, větev, head, stav pracovního stromu, změněné soubory, časová razítka. Tělo, které nese identitní pole, je odmítnuto, takže worker nemůže tvrdit head, na kterém není.

handover --resolve najde nejrelevantnější záznam: nejprve stejný worktree a větev, pak stejnou větev, nikdy v celém repozitáři. Označí vztah k aktuálnímu HEAD jako exact, advanced, diverged nebo jiný kontext a vypíše verdikt čerstvosti podle prahů z politiky, přičemž zastaralý záznam označí jako historii. Briefing relace používá stejný verdikt a necituje další akci zastaralé předávky, protože pokyn, který platil před několika dny, je kontext, ne rozkaz.

Nástěnka peerů, překryv a mesh

Tři věci se snadno pletou: kdo jiný právě teď v tomto repozitáři pracuje, zda jeho práce koliduje s mou a které instance Majordomu existují v síti.

Nástěnka: co dělají peeři

Sdílený server každého checkoutu drží v paměti nástěnku peerů (apps/majordomus-cli/src/peers.rs). Klient MCP, který se připojí, se stane peerem s id pozice, jménem klienta, transportem, časem připojení a poslední aktivitou. Pomocí majordomus_announce uvede záměr a rozsah, volitelně pod názvem claimu, a nové oznámení pod stejným názvem tento claim nahradí. Nástěnka se neperzistuje: odešlý peer, který něco oznámil, je uchován jako nepřipojený, až do RETAINED odešlých slotů (apps/majordomus-cli/src/peers.rs), a ten, který nikdy nic neoznámil, zmizí.

majordomus_peers sbírá nástěnku v rámci repozitáře (ADR 0044): čte nástěnku tohoto checkoutu z paměti a ptá se serveru každého sesterského worktree přes HTTP, jedním skokem, a každého peera označí checkoutem, z něhož pochází. complete: false znamená, že nástěnku nešlo přečíst, a boards říká které a proč — krátká nástěnka není důkazem, že tam nikdo není.

Mesh: kdo existuje

Mesh odpovídá na jinou otázku: které uzly Majordomus existují a lze je zastihnout (docs/MESH.md, apps/majordomus-cli/src/mesh/). Uzel má identitu Ed25519 vedenou na uživatele; instance je jeden běh procesu. Poskytovatelé objevování posílají jednu podepsanou, omezenou obálku přes UDP multicast, UDP broadcast nebo HTTP rendezvous endpoint a deklarace může jmenovat statické seedy spolupráce. Registr drží uzly podle identity s presence TTL a retenčním oknem; důvěra je deny-unknown; uzly označuje a rozhoduje, které se smějí propojit a replikovat žurnál, a nedává žádná práva provádění.

Repozitář bez deklarace meshe, nebo s deklarací enabled: false, neotevře žádný objevovací socket a kostra, ze které nový repozitář začíná, žádný nedodává. Vlastní deklarace tohoto repozitáře, .ai/repo/mesh/majordomus.yaml, je zapnutá: multicast na lokálním segmentu, rendezvous huby na soukromé síti vlastníka a tailnetu a důvěryhodné klíče, které vypisuje (docs/MESH.md, „Mesh tohoto repozitáře“). Neexistuje poskytovatel Tailscale ani mDNS; ADR 0050 je uvádí jako budoucí poskytovatele a rendezvous koncový bod dosažitelný přes tailnet je podporovaný způsob, jak spojit stroje. Tok dat je stejný jako u každého jiného povrchu: schopnosti mesh.status a mesh.nodes, obsluhované přes HTTP a MCP a vykreslené na /cockpit/mesh.

Nástěnka se promítá do meshe. Nástěnka stále sbírá checkouty jednoho stroje přes soubory zápůjček a to zůstává pohledem místním ke stroji. Nad objevováním kooperace propojuje runtimy jednoho repozitáře — jeden server na checkout, na tomto stroji nebo jiném — přes ověřená spojení (ADR 0067): při každém tepu se relace nástěnky runtime stávají relacemi meshe a jejich oznámení poradními nároky, v jednom podepsaném žurnálu, který každý propojený runtime replikuje a sloučí stejně. Takže nástěnka peerů a nároky se replikují napříč runtimy; spojení potřebuje povolený mesh a důvěryhodný klíč. Žurnál je podepsaná posloupnost na proud s hodinami Lamport (apps/majordomus-cli/src/mesh/journal.rs) nesoucí události relací, nároků, předávek a review a jeho stav je čisté sloučení (mesh::state::fold): oznámení nástěnky se stane poradním nárokem meshe, zatímco nárok převzatý přes mesh.claim je výhradní a při konfliktu se odmítne. Při rozdělení sítě mohou nárokovat obě strany; sloučení vybere nejnižší hodiny Lamport, pak proud, pak posloupnost a poraženého označí conflicted — nároky nejsou linearizovatelné a docs/MESH.md to říká. Registr uzlů a tabulka spojení žijí v paměti a umírají s procesem; soubor identity a žurnál přetrvávají a znovu načtený žurnál obnoví události, ale ne čerstvost. Stabilita modulu je experimentální. Mesh agenty neorchestruje.

Verze se píše jednou

Verze se píše na jednom místě, v [package] version manifestu crate, a zapisuje ji jeden příkaz, majordomus-cli release bump (apps/majordomus-cli/src/release/version.rs), který také udržuje v souladu vlastní položku lockfilu a čte obojí zpět. Shellový nástroj žádnou verzi neuvádí: čte share/version.txt, generovanou projekci manifestu, která se dodává vedle něj (ADR 0085), a release::version::diagnose odmítne verzi napsanou ručně kdekoli, kde žijí soubory nástroje — kontrola version-authored-once. Minimální zvýšení se měří, ne volí: release analyze porovnává veřejný povrch schopností — id, expozice a schémata, s kompatibilitou vstupu a výstupu posuzovanou v opačných směrech — s posledním release (ADR 0051). Conventional commity jsou důkaz, ne autorita. Stejná analýza je GET /api/v1/release/analysis, nástroj MCP a /cockpit/release. Po zvýšení just derive přepíše share/version.txt, každé razítko generátoru, changelog, docs/INSTALL.md a data verze webu.

Tag spustí workflow releasu: sestaví matici platforem z docs/generated/distribution-matrix.json, publikuje, zapíše záznam releasu pod .ai/repo/releases/ ze skutečných otisků artefaktů, otevře s ním pull request a po dosažení záznamu na výchozí větvi otestuje veřejný instalátor smoke testem.

Co doctor kontroluje

majordomus doctor je jen pro čtení a dispečuje každou doktrínu, která je na něj navázána (lib/doctor.sh). Mezi nimi: vendorovaný balík pravidel proti hashům manifestu; řetěz zapojení doktríny od validátoru přes dispečink a propagaci selhání po test, tvrzení a CI; instrukční soubory poskytovatelů proti jejich generačním razítkům (bez razítka nebo ručně upravené selže); zapojení každého vynucovacího záznamu v politice, včetně odvozovací kontroly v pre-commitu; integrita schémat, rozložení, rozpočty, retence, DAG pravidel, ADR, dovednosti a prompty. Rustové health.report přidává porovnání commitnutého registru s vykreslením v procesu.

Doctor odhaluje, neopravuje. Regenerace je majordomus generate a just derive; oprava ručně upravené projekce poskytovatele je majordomus update --diff <target> a poté --force — prosté update odmítne přepsat ruční úpravu. Generátor se neopravuje sám jen proto, že existuje: regenerace běží bez dozoru pouze ve workflow verzí a releasů, které otevírají pull requesty, a nic neopravuje na místě.

Kruhový dogfooding

Majordomus je supervizován Majordomem. Pravidla, která zakazují ručně vedené registry, jsou pravidla ve vlastním .ai/ tohoto repozitáře; důkazní engine, který říká, zda jsou vynucována, čte kontroly tohoto repozitáře; generátory, které píšou referenci, jsou kontrolovány kontrolami, které tato pravidla jmenují; ledger důkazů může zaznamenat běhy testů, které dokazují determinismus generátorů (dnes jich žádný nedrží: jq -r '.executions[].test' .ai/repo/evidence/ledger.json); a Cockpit vykresluje tento důkaz ze stejného registru, který dokazuje. Když se generátor rozbije, kontrola, kterou jmenuje pravidlo o generátorech, selže v CI a samo pravidlo se čte failing až poté, co je ten běh zaznamenán. Smyčka je silná jen jako její nejslabší zaznamenaný článek — dnes zaznamenávání provádění — a proto je ten článek níže jmenován.

Architektonický dluh

Kde repozitář ještě není modelem, který tento dokument popisuje, měřeno na výchozí větvi. Ne všechny povrchy tyto mezery samy zveřejňují; jsou zde vypsány, aby je čtenář nemusel hledat.

Deklarováno dvakrát nebo registrováno ručně

  • Příkazový řádek je druhá deklarace v clap, kontrolovaná uzavřením a paritou, ale negenerovaná; cesta příkazu se také opakuje jako slova, která jeho modul předává by_cli, a pomocná funkce, která to dělá, je zkopírována do několika modulů příkazů. Textové renderery a spustitelné příklady se píší ručně.
  • Přidání modulu schopností upraví seznam pub mod a jediné volání compose_modules!.
  • Oblasti Cockpitu, statické trasy a dispatcher jsou psány ručně a testy je drží shodné, nejsou odvozeny; komentář modulu v cockpit/nav.rs pojmenovává méně oblastí, než servíruje.
  • Seznam cílů příkazové řádky majordomus generate je druhý výčet vedle vlastního výčtu generátoru a chybí mu jeden z jeho cílů, který proto běží jen pod all.
  • Nástroj shellu drží vlastní dispatch tabulku vedle share/commands.yaml a rules, skills, evidence, knowledge a bench existují v obou programech s různými významy.
  • Dva seznamy povolených, share/allow/commands.txt a share/allow/events.txt, jsou psané ručně; žádný generátor je zatím neodvozuje.
  • Můstek MCP má pro nástroj announce zvláštní případ při přehrání po opětovném připojení.
  • docs/HARDCODING_LEDGER.yaml uvádí místa, kde je fakt zapsán dvakrát a která byla založena, s příkazem, který každé reprodukuje; několik otevřených položek zůstává a několik duplikací pojmenovaných v této sekci tam zatím není. Tabulka povrchů v docs/WEB.md je jednou z nich svým duchem: psaná ručně a nekontrolovaná žádným testem.

Odvozeno, ale ne věrně

  • Anotace MCP nástrojů: nápovědy destructive a idempotent jsou stejné pro každý nástroj, včetně těch, které zapisují do repozitáře; jen nápověda read-only se řídí deklarací.
  • OpenAPI připojuje odpověď 422 refused pouze k příkazům, ačkoli některé dotazy odmítají.
  • Diagram pipeline na stránce architektury webu je pevná posloupnost zapsaná v generátoru a vynechává vlastní generační fáze spustitelného souboru.
  • Vztah doktríny k principu je obyčejné depends_on; žádné typované pole neexistuje. Odkazy pravidlo-tvrzení existují jen u vendorovaných doktrín; tvrzení na pravidla nezpět neodkazují.
  • Členové souboru kolekce (tvrzení, příkazy, taxonomie případů užití) se indexují bez kontroly schématem na člena, jíž prochází každý jiný objekt.

Není zpřístupněno všude

  • Žádné stránky Cockpitu podle druhu pro pravidla, doktríny, ADR nebo tvrzení — obsluhuje je generická stránka objektu. Žádná stránka plánu v Cockpitu a přehled ukazuje preflight, ale ne snapshot prostředí.
  • Nástěnka peerů nemá vlastní příkaz — čte ji run peers.list — a pro oznamování je potřeba relace MCP.
  • Příkazy životního cyklu v shellu (start, check, finish, handover, context) nejsou schopnosti, takže nemají projekci HTTP ani MCP; continuity.state je jejich čtecí model.
  • Hooky relace jsou adaptovány jen pro Claude Code; ostatní poskytovatelé své deklarují a jsou neadaptovaní (share/providers.yaml, lib/capture.sh).
  • Prostředky Swagger UI pocházejí z CDN.

Bez důkazů

  • Běhy se do registru zapisují jen pomocí evidence record; CI spouští každou kontrolu, ale své běhy zpět nezapisuje, takže většina pravidel a tvrzení se čte jako not_run místo proven a web publikuje deklarované a podporované počty vedle sebe, aby to řekl.
  • Deklarativní pravidla nejmenují žádný důkaz a stojí na unproven; jsou poradní, takže nejsou zjištěními. Revidovaná pravidla vynucuje člověk a nepočítají se jako strojově vynucená.

Nevynucováno, jak je zdokumentováno

  • project.derived-files-regenerated říká, že scripts/derive-check běží v CI a ve workflow Pages; běží jen ve workflow zvýšení verze a release, zatímco kontrola pull requestu spouští své poloviny odděleně. Polovina pre-commit porovnává hash vstupu a porovnání registru přeskočí, není-li sestaven spustitelný soubor.
  • Sonda obsluhy nasazení je uvnitř jobu nasazení jen poradní; jakmile uvidí commit, publikovaná dokumentace a rustdoc se ověří a job selže, stejně jako při chybě sestavení GitHub Pages, a kontrola pages-live při dokončení posoudí, zda je publikace aktuální.
  • project.no-counts-in-prose je mechanizováno pro vždy načítaný kontext poskytovatele (doctor) a pás důkazů na domovské stránce (homepage-check); u dokumentů se vynucuje revizí.
  • evidence.record zapisuje commitnutý ledger, ale deklaruje efekt process_state, takže seznam zapisovatelů do repozitáře odvozený z efektů (instrukce MCP, x-majordomus-effect) ho vynechává.

Nesestaveno, nebo sestaveno částečně

  • Poskytovatelé discovery Tailscale a mDNS; NAT traversal a spoje širokého dosahu. Spolupráce mezi stroji existuje přes rendezvous endpointy a důvěryhodné klíče, je experimentální a její provoz na více strojích se opírá o zaznamenaný ruční běh (docs/MESH.md).
  • Rustová strana životního cyklu relace je čtecí model; přechod je navržen.
  • Záznam záměru je částečně adoptován (ADR 0070): .ai/repo/project/intents/ drží záznamy, které čtou intent validate a intent preflight; úloha se k nim váže při start a je z nich briefována (ADR 0111) a žádná politika dokončení je nespotřebovává.
  • Verzi lze deklarovat dříve, než je vydána: verze crate a nejnovější záznam o release jsou samostatné skutečnosti; navigační lišta uvádí release a changelog zobrazuje nevydanou verzi nad ním.
  • Mnohá ADR, která kód už dodržuje, zůstávají proposed, protože přijetí je aktem člověka.

Majordomus není sbírka příkazů, dashboardů a integrací agentů. Je to model nativní pro repozitář, z něhož se tyto povrchy odvozují.

Příkazová řádka, HTTP API, MCP, OpenAPI, Swagger UI, Cockpit a dokumentace mají být projekcemi jedné typované reality repozitáře — a tam, kde je některé z nich stále psáno ručně, ho k té realitě drží kontrola a tento dokument jej jmenuje.

Pravidla a doktríny nejsou cenné proto, že jsou napsané. Cennými se stanou, když je jejich vztah k validátorům, kontrolám, provedením a důkazům strojově zkoumatelný — a když povrchy říkají not run místo zeleného odznaku, dokud není zaznamenán běh.

Nástěnka peerů a mesh nejsou orchestrace agentů. Činí workery, jejich přítomnost a jejich claimy dostatečně viditelnými, aby o nich mohli uvažovat lidé a koordinační mechanismy.

Generování a odvozování jsou způsob, jímž se Majordomus snaží zabránit tomu, aby repozitář pomalu nashromáždil sedm neslučitelných popisů sebe sama.
