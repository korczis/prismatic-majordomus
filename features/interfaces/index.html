One registry over the command line, HTTP, OpenAPI, Swagger UI and MCP

Every agent, script and person reads the same repository through the interface it already speaks, and none of the interfaces is maintained by hand.

Surfaces

What it does

The first majordomus mcp in a repository binds one shared server on the loopback interface and logs every surface it serves: the home page, this documentation, the crate's rustdoc, the Cockpit, the Swagger UI, the OpenAPI document, the capability routes and MCP over HTTP. Every later client attaches to it instead of starting another, and the server ends when its last client leaves. The client configurations at the repository root — one per provider that reads one, as docs/generated/providers.md lists them — name one launcher, so opening the repository in any of them is enough.

What the server answers is the registry: a tool, a resource, a route or a command exists because a declaration exists, and the same declaration is what the reference and the website render. A surface — the documentation mount, the crate's rustdoc, a generated report, the Swagger UI — is discovered from the thing that produces it, or from the source that says it exists, and resolved once into a topology the router, the home page, the publication and the validator all read.

What it does not do

Most of what is served reads. Every capability carries its effect in the registry: a read, a change to the answering runtime's own state (the peer board, the mesh journal, the evidence ledger), or a change to the repository. The ones that write the repository are continuity.publish, continuity.resume, continuity.sync, executions.start, intents.propose, mesh.enrol, plan.transition, reasoning.record and recover.orphans; the initialize instructions every client reads name them from the registry, and case 3363 refuses this page when its list and the registry's differ, because a sentence that promises a read-only surface is exactly the sentence an agent acts on. There is no authentication and no remote binding by default; the server is for the clients on this machine. When it is bound beyond loopback, its reads answer whoever reaches it, and every capability that changes something is refused to a remote caller unless a linked node signed the input. It does not run a model and it does not route work to one.

Executions executions behaviorally verified

Running a capability of this registry as work that can be watched: started, followed event by event over the live channel, read back afterwards, and asked to stop. One plane per checkout: `majordomus run` executes in its own process and reports the execution to the server already serving the checkout, so that server lists it beside its own; with no server it says that nothing else can see the run. In memory; an execution does not outlive the server that holds it.

Using it

From the executable's command line

The synopsis of each, as the executable's own help prints it.

  • majordomus scope [OPTIONS] [PATHS]

    The repository scope: what a worker reads and what it never reads; with paths, whether each is in or out and why

  • majordomus run [OPTIONS] <CAPABILITY>

    Run a capability as an execution and follow it: its steps, its progress and its output as they happen

  • majordomus executions list [OPTIONS]

    Every execution the server remembers, newest first

  • majordomus executions show [OPTIONS] <ID>

    One execution in full: its state, its steps, its diagnostics and what it produced

  • majordomus executions events [OPTIONS] <ID>

    One execution's retained events, oldest first

  • majordomus executions cancel [OPTIONS] <ID>

    Ask an execution to stop

  • majordomus executions protocol [OPTIONS]

    The live channel's contract: where it is, what it writes, and the schema of each message

  • majordomus entity kinds [OPTIONS]

    Every kind of the layer, the route of its index, and every route collision there is

  • majordomus entity show [OPTIONS] <ADDRESS>

    One entity: its route, what it references, what references it, where it is served
