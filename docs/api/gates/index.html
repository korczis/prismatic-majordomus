HTTP API: gates

Completion as a state the repository decides rather than a claim a worker makes: the validation gates this repository declares in its CI model, which of them a task's own change set selects, what each one last reported, whether that verdict still describes the tree it was taken over, and therefore whether the task may be called finished. A gate that has never reported is `queued` and not `pass`, a run whose files have changed since is `stale` and refuses exactly as a failure does, and a gate the change cannot affect is `exempt` rather than unknown.

GET /api/v1/gates gates.model

The CI model

Every validation gate this repository declares — the job that runs it, the command it runs, what it proves, whether every plan selects it and whether its runner can be had on demand at all — with the path classes that decide which change selects which gate, and, derived from those classes, the pathspecs each gate's evidence is taken over.

GET /api/v1/gates/completion gates.completion

Whether this task may be called finished

The active task's own change set — from the commit it started at to the working tree, uncommitted files included — put through the CI model: which gates it selects and why, what each one last reported and over which files, which verdicts have gone stale because the tree moved underneath them, which required gates have never reported at all, and which obligations the change implies whether or not the task declared them. `finishable` is false only when a required gate is known to be failing, stale or blocked by one that is; absence of a verdict is reported as unverified rather than silently accepted. The done invariant is the questions of share/completion.yaml, in its order, each answered from the source it names; `stage` is the stage of the work those answers fold to, and `complete` is true only when every question passes or is exempt — finishable and complete are two different words.

  • query
  • behaviorally_verified
  • benchmark required
  • cache disabled
  • MCP tool majordomus_completion
  • MCP resource {"name": "completion", "uri": "majordomus://gates/completion"}

GET /api/v1/gates/policy gates.policy

The completion policy

The one definition of done: the stages of the work in order, every question a task must answer before it may be called finished, the stage each question belongs to and the source its answer is taken from — an obligation of share/obligations.yaml, a gate of the CI model, the change set, the repository's convergence or the closing readings. Read from share/completion.yaml, the file `gates.completion` takes its questions from. A token the policy names and the vocabulary lacks is reported as a problem, and a gate question this repository's CI model never answers is listed by name.

GET /api/v1/gates/state gates.state

How each gate last went

Every gate the CI model declares with the standing of its last recorded run in this checkout, whichever task recorded it: `pass` or `fail` over the files as they stand now, `stale` when those files have changed since the run, `queued` when no run has ever reported — listed again under `never_reported`, because a missing verdict is the case an absent reader renders green — and `unknown` when a run exists and cannot be checked against this tree. Each run carries the commit it was taken at and whether that is the commit checked out now. Read offline from this checkout's own record; what it did not consult, the forge's CI runs, is named under `unreached` rather than left out.

Completion

object 
use majordomus_cli::gates::Completion;

// the document every surface reads, as `gates.completion` answers with it. The property
// that matters is the one asserted here: a gate that never reported leaves the task
// finishable and *unverified*, which is a different thing from a task that passed.
let c: Completion = serde_json::from_value(serde_json::json!({
    "present": true,
    "model": ".ai/repo/ci/gates.yaml",
    "plan": { "mode": "affected", "reason": "1 path in 1 class", "changed": ["docs/CLI.md"],
              "classes": [], "unclassified": [], "selected": {}, "excluded": {} },
    "finishable": true,
    "unverified": ["reference-check"],
    "tallies": { "queued": 1 },
    "gates": [],
    "obligations": [],
    "questions": [],
    "policy": "share/completion.yaml",
    "stage": { "id": "gates", "title": "Gates", "state": "pending", "complete": false,
               "owing": ["ci"], "stages": [] },
    "complete": false
}))
.unwrap();
assert!(c.finishable, "absence of a verdict does not refuse");
assert_eq!(c.unverified, ["reference-check"], "and it is never silently accepted");
assert!(c.blocking.is_empty());
// finishable is not complete: the stage the answers fold to still owes the ci question
assert!(!c.complete);
assert_eq!(c.stage.id, "gates");
assert_eq!(c.stage.owing, ["ci"]);

Whether the active task may be called finished, and everything the answer rests on.

finishable is the field a caller acts on and the one thing no surface may recompute: the shell tool's check and finish read it, the HTTP API serves it, the Cockpit renders it, and all of them are reading this one execution.

propertytyperequireddescription

True when a task record was found in this checkout.
task ActiveTask | null → ActiveTask no
The task, as its record declares it.
model string yes
The CI model this was judged against.
plan GatePlan → GatePlan yes
Affected or full, and why.
finishable boolean yes
False when a required gate is known to be failing, stale, or blocked by one that is. Absence of a verdict does not make this false — it makes unverified non-empty.
blocking array of string no
The required gates whose status refuses completion.
unverified array of string no
The required gates that have never reported, or cannot be judged here. A task finished over these is finished unverified, and the record says so.
tallies map of integer (uint) yes
How many gates stand in each status, by word.
gates array of Gate → Gate yes
Every gate of the model, what refuses first.
obligations array of ImpliedObligation → ImpliedObligation yes
Which obligations the change set implies, and whether the task promised them. The judgement of a declared one is obligations.closure's, not this module's.
questions array of DoneQuestion → DoneQuestion yes
The done invariant: the questions a task must answer before anybody may call it finished, each with the source that answered it and the evidence it read. Composed from the obligation closure, the gates, the change set, the repository's convergence and the closing readings; a question nothing here reaches is unknown and names the command that would answer it. Exactly the questions of the completion policy, in its order, each with the stage the policy places it in.
policy string | null no
The completion policy the questions were taken from, as the distribution names it. Absent when no policy could be read; a finding then says why, the one question asked is whether it can be, and nothing is complete.
stage LifecycleStage → LifecycleStage yes
Where the task stands in the lifecycle, folded from the answers in the policy's stage order: the first stage blocked, else the first stage pending, else the last. Derived on every reading and never written down by anybody.
complete boolean yes
True only when a task is present and every question of the policy passes or is exempt. The one field that may be read as "done": it is the stage fold's word, and no surface computes it a second time from the parts.
findings array of string no
What could not be established, each as one line. Never empty when something was skipped: a gap is reported rather than left to be inferred.

CompletionPolicyReport

object
The completion policy, as gates.policy serves it: the stages, the questions and the source each is answered from, with what the policy resolves to in this repository. The policy is flattened into the report, so a reader sees the keys the file carries with the derived fields beside them.

use majordomus_cli::capability::builtin::gates::CompletionPolicyReport;
use majordomus_cli::gates::CompletionPolicy;

let policy = CompletionPolicy::parse(
    "version: 1\nstages:\n  - id: a\n    title: Alpha\n    summary: s\nquestions:\n  - id: q\n    stage: a\n    question: Is it?\n    source: gate:site-check\n    remediation: run it\n",
    "share/completion.yaml",
)
.unwrap();
let report = CompletionPolicyReport {
    outline: policy.outline(),
    problems: policy.validate(&[]),
    unanswered_gates: policy.unanswered_gates(&[]),
    policy,
};
assert_eq!(report.outline, "- Alpha: q\n");
assert_eq!(report.unanswered_gates, ["q:site-check"]);
let json = serde_json::to_value(&report).unwrap();
assert_eq!(json["stages"][0]["id"], "a", "the policy's own keys, flattened");
assert!(json.get("problems").is_none(), "a coherent distribution writes no problems");

The format version the file states.
source string yes
Where it was read from.
stages array of StageDecl → StageDecl yes
The lifecycle, in order.
questions array of QuestionDecl → QuestionDecl yes
Every question, in declaration order.
outline string yes
The definition of done in a dozen lines: one per stage that asks anything, its questions after a colon.

GateModelReport

object
The CI model this repository declares: what may refuse a change, and what selects each.

Two things about this report are worth knowing before reading one. count is measured from gates rather than written down, so the two can never disagree the way a hand-maintained total does. And unreadable is how a reader tells "this repository declares no CI model" from "the call failed": a repository of the layer is not obliged to declare gates, so the empty model is an answer, and it says why it is empty.

use majordomus_cli::capability::builtin::gates::GateModelReport;
use serde_json::json;

// the shape every surface serves: `unreadable` is skipped when the model was read
let r: GateModelReport = serde_json::from_value(json!({
    "version": 1,
    "source": ".ai/repo/ci/gates.yaml",
    "count": 0,
    "on_demand": [],
    "gates": [],
    "classes": [],
})).unwrap();
assert_eq!(r.count, r.gates.len(), "the total is measured, never declared");
assert!(r.unreadable.is_none(), "read, and it declares nothing");

// and the other empty answer, which a reader must not confuse with that one
let absent: GateModelReport = serde_json::from_value(json!({
    "version": 0,
    "source": ".ai/repo/ci/gates.yaml",
    "count": 0,
    "on_demand": [],
    "gates": [],
    "classes": [],
    "unreadable": "no such file",
})).unwrap();
assert_eq!(absent.unreadable.as_deref(), Some("no such file"));

GateStatus

"pass" | "fail" | "stale" | "blocked" | "queued" | "exempt" | "unknown" 
use majordomus_cli::gates::GateStatus;

// the three answers a reader is entitled to, and they are different answers
assert!(GateStatus::Fail.refuses(), "a run that failed refuses");
assert!(GateStatus::Queued.unverified(), "asked and unanswered is a debt");
assert!(!GateStatus::Exempt.refuses() && !GateStatus::Exempt.unverified());

// and the one that is neither: a run whose tree has moved proves nothing about this one
assert!(GateStatus::Stale.refuses());
assert_eq!(GateStatus::Stale.as_str(), "stale");

What is known about one gate. Every word is one this repository's design tokens already carry (share/design/tokens.yaml, status.states), so a surface renders it without being taught a sixth vocabulary and the design gate does not refuse it.

  • passIt ran over these inputs and succeeded. The only word that discharges anything.
  • failIt ran over these inputs and failed. Completion is refused.
  • staleIt ran, and the files that select it have changed since; what it proved is about a tree that no longer exists. Completion is refused, because the alternative is treating a claim about the past as a claim about the present.
  • blockedSomething it cannot run without has not passed, so its own silence means nothing.
  • queuedThe plan selects it and no run has ever reported. Not unknown: the question was asked and no answer came, which is a debt somebody owes, and not pass, which is the mistake this word exists to make impossible.
  • exemptThe plan does not select it: nothing the task changed can make it true or false.
  • unknownIt cannot be judged here at all — no model, no git, a ledger that would not read. An honest gap, and never a pass.
