# Shared Contract: Worktree Cleanup, Integration, and Repository Hygiene

All phase prompts in this pack inherit this contract.

## 1. Repository-first discovery

Before changing anything, inspect the actual repository and its canonical instructions.

Read and respect, where present:

- `AGENTS.md` and nested agent instructions,
- repository README hierarchy,
- `.ai/**`,
- `.majordomus/**`,
- rules,
- doctrines,
- schemas,
- ADRs,
- session/handover conventions,
- canonical CLI and `just` workflows,
- CI/gates,
- worktree tooling,
- Git hooks,
- GitHub Pages/site documentation,
- API/OpenAPI/MCP/Cockpit architecture.

Do not assume filenames or paths when the repository can tell you.

## 2. Hard safety invariant

Never delete, reset, clean, prune, drop, or overwrite potentially valuable work until it has been classified and proven recoverable.

Potentially valuable work includes:

- tracked modifications,
- staged modifications,
- untracked files,
- ignored files that may contain intentional local work,
- worktree-only files,
- stash entries,
- local-only branches,
- remote-only branches,
- dangling commits,
- commits reachable only from reflogs,
- merge/rebase conflict state,
- detached HEAD worktrees,
- patches generated by unfinished tooling,
- generated artifacts that may encode unavailable source data.

Use evidence, not intuition.

## 3. Preserve before destructive operations

Before any destructive operation, create a recovery boundary appropriate to repository policy. Examples include:

- a namespaced safety tag,
- a safety branch,
- a bundle,
- patch files,
- copied untracked material into an explicitly temporary recovery area,
- a machine-readable inventory containing object IDs,
- a Git bundle covering all relevant refs.

Prefer repository-local/inferred conventions if they already exist.

Do not commit secrets, caches, credentials, local environment files, or huge binary junk merely to preserve them. Preserve safely outside versioned history when necessary.

## 4. Canonical topology invariant

Unless repository instructions explicitly supersede it, converge toward:

```text
repo root:      ~/dev/prismatic-majordomus
worktree root:  ~/dev/prismatic-majordomus-wt
feature branch: feature/improve-cli
worktree path:  ~/dev/prismatic-majordomus-wt/feature/improve-cli
```

The exact absolute path must be inferred from the current repository root rather than hardcoded.

Rules:

- worktree root is the sibling `<repo-basename>-wt`,
- relative worktree path equals branch name where filesystem-safe,
- one active feature branch maps to one canonical worktree,
- `master`/default integration branch remains in the primary repository root unless existing policy says otherwise,
- duplicate worktrees for the same branch are forbidden,
- detached worktrees require explicit classification,
- ad-hoc worktree roots are legacy state to migrate or remove,
- worktree metadata must match real filesystem state.

## 5. Never integrate blindly

Do not merge branches merely because they exist.

Every branch must be classified into at least one semantic state:

- already merged,
- equivalent/superseded,
- independent and ready,
- dependent on another feature,
- partially overlapping,
- abandoned but containing unique work,
- experimental and intentionally retained,
- stale with no unique commits,
- conflict-heavy and requiring reconstruction,
- unknown and blocked from deletion.

Use commit graph and diff evidence.

## 6. Integration must be serialized

Build a dependency DAG first.

Integrate in a deterministic order chosen from evidence, generally:

1. shared foundations,
2. low-level refactors,
3. domain changes,
4. cross-surface adapters,
5. docs/generated artifacts,
6. cleanup/enforcement.

After each integration step:

- re-run relevant tests,
- re-check generated drift,
- re-check worktree/branch graph,
- commit a coherent unit,
- preserve a rollback point.

Do not create one gigantic octopus merge of unrelated feature branches.

## 7. Rebase policy

For local feature branches, prefer rebasing onto the verified latest integration base when repository policy and branch sharing permit it.

Do not rewrite shared/public history blindly.

Before rewriting a branch:

- inspect upstream tracking,
- inspect remote existence,
- inspect whether others may depend on it,
- inspect branch protection/repository policy,
- create recoverability evidence.

If history rewrite is unsafe, merge or reconstruct deliberately.

## 8. `master` protection

Treat the integration branch as production-grade even if branch protections are absent.

Before updating `master` or equivalent:

- fetch/prune remotes,
- verify local base against `origin/master`,
- ensure primary worktree is clean,
- ensure no unrelated local-only commits are hidden on master,
- run required gates,
- integrate one verified unit at a time,
- push only after validating resulting history.

Do not use `git push --force` on the integration branch.

## 9. No stash graveyard

Audit every stash before dropping anything.

Classify each stash as:

- duplicate of committed work,
- superseded,
- unique and must be restored/integrated,
- local secret/config and must be preserved outside Git,
- unknown and must remain.

Only drop stashes with evidence.

## 10. No hidden Git archaeology left behind

Audit:

- `git worktree list --porcelain`,
- local branches,
- remote-tracking branches,
- tracking relationships,
- tags relevant to cleanup,
- stashes,
- reflogs,
- dangling/unreachable objects,
- in-progress rebase/merge/cherry-pick state,
- lock files,
- prune candidates,
- `.git/worktrees/**` metadata.

Do not manually edit Git internals unless ordinary Git commands cannot repair state and you have proven the recovery path.

## 11. Repository clutter is not just Git clutter

Audit repository-local clutter such as:

- root-level temporary files,
- obsolete scripts,
- duplicate generated outputs,
- stale reports,
- abandoned patch files,
- old worktree manifests,
- duplicate session/context directories,
- orphaned `.ai` or `.majordomus` legacy structures,
- caches accidentally versioned,
- build outputs in wrong locations,
- obsolete docs indexes,
- dead compatibility shims,
- duplicated source-of-truth metadata.

Do not delete merely because a file looks ugly. Determine ownership and canonical replacement first.

## 12. Majordomus architectural principles

Any permanent solution must be:

- single-source-of-truth,
- inferred where possible,
- derived where possible,
- generated where appropriate,
- typed,
- schema-backed where repository conventions support it,
- deterministic,
- data-driven,
- extensible,
- testable,
- documented,
- enforceable,
- discoverable,
- free from consumer-specific duplicate registries.

If worktree state becomes a product surface, the model should conceptually be:

```text
Git + repository policy
        ↓
canonical typed worktree/branch inventory
        ↓
validation / lifecycle operations
        ↓
CLI
API / OpenAPI
MCP
Cockpit
Docs
completion / environment UX where relevant
```

Not six copies of `git worktree list` parsing.

## 13. Do not invent synthetic features

Only add permanent tooling that directly prevents recurrence or materially improves repository control.

Avoid architecture astronautics.

Useful permanent capabilities may include:

- `worktree list/status/doctor/plan`,
- canonical JSON inventory,
- lifecycle validation,
- deterministic branch↔path checks,
- stale/merged candidate detection,
- safe cleanup plan generation,
- explicit execution of an already-reviewed cleanup plan,
- Cockpit visibility if the backend already supports analogous surfaces.

Do not add ornamental dashboards with no operational value.

## 14. Tests before claims

Do not claim cleanup is complete because `git status` is clean in one directory.

Test:

- all active worktrees,
- integration branch,
- relevant workspace packages,
- docs generation,
- schemas,
- API/OpenAPI,
- MCP,
- Cockpit if changed,
- repository validation gates,
- generated artifact drift,
- worktree topology invariants.

Use repository-native commands.

## 15. Evidence-driven final report

Every phase must leave concise evidence:

- what was found,
- what changed,
- what was preserved,
- object IDs/branches involved,
- commands/tests executed,
- remaining blockers,
- next safe step.

Use the repository's canonical handover/session mechanism if one exists. Do not invent a parallel session system.
