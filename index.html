v0.1.0 · portable shell · no runtime · no model calls

Your AI workers are brilliant. Nobody is managing them.

Every fresh session re-reads the repository, reasons at maximum, works on whatever it likes, and says "done" when it feels like it. Majordomus is the layer that decides what a worker is told, declares which paths its work may touch, and refuses to accept "done" until a contract says so.

A lightweight supervisory control layer for AI-assisted work.

01 / the problem

A session grades its own homework

An AI session is the only witness to its own work. Nothing outside the conversation states what it was allowed to do or checks what it did.

  1. 1loads whatever context it likes
  2. 2interprets whichever rulebook it found
  3. 3chooses its own scope
  4. 4changes files
  5. 5declares itself done
  6. Who independently checks that any of it was acceptable?

The environments this tool was distilled from had the failure at scale:

  • instruction files for two AI tools in the same repository sharing 0–9 % of their content: not duplicates, disjoint rule sets
  • an always-loaded operating contract oscillating between 0 and about 1,100 lines across roughly 200 hand edits, until a hard budget with a failing check pinned it
  • seventeen independent cases of a check documented as blocking, present on disk, executable, and invoked by nothing
  • full worktree isolation still producing about 3,200 concurrently modified files and 67 duplicated patches across forty worktrees, with nine ever merged
  • 10 GB of session notes standing in for a database, recovered by a hand-written runbook

Better prompts do not fix any of this. The evidence, with its derivation →

02 / the core model

Majordomus supervises how work is executed

Majordomus does not replace a worker and never invokes a model. It decides what a worker is told, what it may touch, and whether its claim of being done can be believed.

The worker does not get to define its own successful completion.

Majordomus does not stop a worker from touching a file while it runs. It declares the scope up front, detects a file outside it at check and at finish, and refuses to accept the work as completed — nothing is written to the record until every line of the contract passes. Refused acceptance, not runtime prevention, is the contract.

The same team, before and after one directory

With Majordomus

  • ✓one policy, projected into every tool's instruction file
  • ✓named profiles instead of vibes: effort, verbosity, context, verification
  • ✓one active task per checkout, scope declared before the first edit
  • ✓durable state and handovers the next session can trust against git
  • ✓"done" is a contract, evaluated line by line, refused when unmet

04 / drop-in

One directory, one pointer

One directory in your repository holds the policy, the profiles, and the durable state. Nothing is compiled, served, or running in the background.

Requirements: bash 3.2 or newer, git, sha256sum or shasum. Nothing is installed into your project except .ai/ and the instruction files the policy names; .ai/local/ is ignored and never leaves the checkout.

05 / how it works

A task is bounded by start and by finish or handover

  1. step 1 majordomus start

    begin a scoped task under a profile

  2. step 2 majordomus context

    what the next worker needs to know now, within budget

  3. step 3 majordomus checkpoint

    record compact progress inside the active task

  4. step 4 majordomus check

    is the current task consistent with policy, scope, state?

  5. step 5 majordomus handover

    write an append-only continuation record (body on stdin)

  6. step 6 majordomus finish

    evaluate the finish contract; refuse if unmet

11 responsibilities sit behind the 6 commands of that lifecycle — what Majordomus supervises →. Outcomes are a closed vocabulary: completed, partial, blocked, no_match, failed. State read back is labelled different_context, exact, advanced, diverged against git.

06 / guaranteed · advisory · planned

What is real, what is projected, what is not built

A supervisory tool that overstates itself is the thing it was built to prevent. Every row names its source, implementation and test, and the build fails if a path does not exist.

guaranteed97

Deterministic and blocking. Implemented, and a behavioural test proves it.

  • ·The canonical policy is parsed and rejected if it contains an unknown key
  • ·Every profile is parsed, its unknown keys rejected, and the default profile proven to exist
  • ·Every enforcement the policy declares is reconciled against what actually runs
  • ·Exit codes are a contract, and no code means "warn and continue"

advisory6

Projected into the worker's instructions. Whether a worker honours it is not observable from outside. Documentation, not enforcement.

  • ·A decision record without a task, a head and a reason is reported, and does not block
  • ·Capability class, reasoning effort, output verbosity, context and verification are five independent axes
  • ·A profile names a capability class rather than a vendor model
  • ·A profile declares which context a worker should load and no more

07 / what it is not

Not another runtime

  • not a model, and it never invokes one
  • not an agent framework, orchestrator, or runtime
  • not a prompt library or a memory system
  • not a daemon, database, queue, or hosted service; the Rust executable's mcp and serve are read-only processes a client or a person starts and owns, one shared server per repository on the loopback interface that ends when its last client leaves (docs/MCP.md)
  • not a slice of any other platform; there is no shared code
