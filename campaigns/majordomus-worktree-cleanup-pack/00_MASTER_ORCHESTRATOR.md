# Master Orchestrator: Merge, Normalize, and Clean All Worktrees Safely

You are operating inside `prismatic-majordomus` with a large context window.

This is a complete repository campaign. Do not treat it as a one-command cleanup.

## Mission

Bring the repository from its current potentially fragmented state to a verified, integrated, clean, deterministic worktree/branch topology with permanent enforcement.

You MUST first read:

1. `CONTRACT.md`
2. every file under `phases/` in numeric order
3. `RECOVERY.md`
4. the repository's own canonical instructions and governance material

Then execute the phases in order.

Do not ask me to choose obvious implementation details. Infer them from repository evidence.

Do not stop after producing an audit if implementation is possible.

Do not destroy uncertain work.

## Desired end state

The campaign should converge toward all of the following unless repository policy proves a better equivalent:

- one canonical primary repository root,
- one canonical sibling `-wt` worktree root inferred from repository path,
- deterministic branch-to-worktree mapping,
- no duplicate/ad-hoc worktrees,
- no stale worktree metadata,
- all useful feature work classified,
- all merge-worthy work integrated in dependency order,
- all integration conflicts resolved semantically rather than mechanically,
- all required tests passing after each integration unit,
- merged/superseded branches pruned safely,
- stashes audited,
- dangling/reflog-only work audited,
- root/repository clutter cleaned where ownership is proven,
- worktree lifecycle policy enforced through canonical Majordomus mechanisms,
- relevant docs/tooling/schemas updated,
- remote state synchronized without force-pushing the integration branch,
- final repository state demonstrably recoverable and explainable.

## Operating method

### A. Establish one campaign ledger

Use the repository's canonical session/handover mechanism if it exists.

Record a machine-readable ledger containing at least:

- branch name,
- worktree path,
- HEAD OID,
- upstream,
- ahead/behind versus integration branch,
- ahead/behind versus upstream,
- dirty state,
- untracked state,
- stash associations if inferable,
- merge-base,
- unique commits,
- semantic classification,
- dependency classification,
- preservation proof,
- intended action,
- integration result,
- cleanup result.

Do not build a manually maintained duplicate registry as permanent product state. The ledger is campaign evidence, not a new source of truth.

### B. Use checkpoints

Before destructive phases, create explicit recovery checkpoints according to the contract.

After each major integration batch, verify the checkpoint and current graph.

### C. Execute phases sequentially

Run:

1. forensic inventory,
2. preservation,
3. topology normalization,
4. integration DAG construction,
5. branch rebase/repair,
6. serialized integration,
7. repository clutter cleanup,
8. Git state pruning,
9. lifecycle enforcement,
10. cross-surface exposure/documentation,
11. final proof and handover.

Do not skip directly to `git worktree prune`.

### D. Resolve ambiguity by evidence

When two branches overlap:

- compare merge bases,
- compare patch IDs where useful,
- inspect renamed/moved files,
- inspect tests/docs generated by each,
- determine whether one supersedes the other,
- reconstruct intent from commits/session/handover/issues if available.

Do not keep both just to avoid deciding.

### E. Prefer coherent history

Do not integrate hundreds of tiny conflict-fix commits if a cleaner reconstruction is possible and safe.

But do not rewrite shared history without evidence and recovery protection.

### F. Push only verified state

Do not push intermediate broken integration states to `origin/master`.

Push feature branch rewrites only if repository policy allows and use lease protection when force-updating a feature branch is necessary.

Never force-push the integration branch.
