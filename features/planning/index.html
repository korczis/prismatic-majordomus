Milestones and issues as data; status derived, never stored

An issue records what happened to it and the engine derives whether it is blocked, ready, active, verifying or done from the dependency graph, so the roadmap cannot disagree with the plan.

status
✓feature status: stable
domain
Coordination

What it does

majordomus plan validate refuses a cycle, an edge that resolves to nothing and a record that breaks its schema; plan next answers which issues may be executed now; plan roadmap draws the milestone graph the website renders. A branch created for an issue is named after it, so the worktree topology can read the issue back from the branch, and an issue is done only with the evidence its contract requires. Above the branch the same edge is read in both directions and stored nowhere: the trace capability module derives an issue's branches and commits from git, scripts/traceability joins the pull requests GitHub holds, and a commit no execution contract accounts for is reported as unattributed rather than quietly left out.

What it does not do

It does not talk to GitHub on its own: the projection of issues and milestones is rendered offline and applied only when a person runs the sync with a token. Nothing here estimates effort or schedules dates.

Why it exists

Operational moments from the Why catalogue that name one of this feature's mechanisms. Nothing here was assigned: a moment appears because it names a rule, a command, a capability or a claim this feature also names.

  • →read three roadmaps for one project and believed none of them
  • →found finished work on a branch that nobody ever merged
  • →found a substantial change that no issue, ticket or plan ever asked for
  • →closed an issue whose acceptance criteria nothing had actually checked
  • →was asked how far the milestone had got and had to go and ask four people
  • →could not reproduce a result because nothing recorded the state it came from

How it works

The capability modules of the executable this feature names, each with the capabilities it composes. The interfaces each one reaches are listed under Interfaces below: they are projections of one declaration, not separate registrations.

Traceability trace behaviorally verified

Which branches and commits realised an issue, and which issue and milestone a commit served — derived from git and from the canonical project model on every call, stored nowhere. A branch names an issue when one of its path components is an issue id; a commit belongs to the issue whose branches hold it; a commit no such branch holds is reported as unattributed rather than left out, because work with no execution contract is what a traceability report exists to make visible. Pull requests are a GitHub fact and this executable makes no network call: `scripts/traceability` reads them and joins them to this answer over the branch name.

  • What contract this commit served query
  • What realised this issue query
  • The whole work graph above the branch query

The plan and its derivations plan behaviorally verified

The milestone and issue model of this repository, and everything derived from it that nobody authored: the status of each record, the dependency graphs above and below the milestone boundary, the topological execution waves, the roadmap order, the milestone being executed and the one issue to take next. Status is never stored — a record says what happened to it and the status follows from that and from the state of its dependencies — so no file can contradict the graph. This capability reads; writing a lifecycle marker into a record is `plan.transition`, which declares that it writes the repository.

  • The issues, filtered by what the graph derived query
  • The whole derived plan query
  • The one issue to take now query
  • One milestone or issue, with everything derived about it query
  • The milestones in derived order query
  • Where the plan stands query
  • Move one issue through the lifecycle command
  • What the model refuses query
  • What may run at the same time query

Executable development scopes devtask behaviorally verified

An issue and a milestone read as work to be done rather than as metadata: what a person authored, where the plan graph puts it, what happened to it locally, where its external projection stands, and whether a worker may start it — with the origin of every value on the value. Nothing here is a second project model: the records are the canonical ones, the status and the graph are `plan`'s, the branches and commits are `trace`'s, the readiness vocabulary refines three canonical statuses without replacing any, and the projection onto GitHub stays `scripts/github-sync`'s. Nothing here writes anything, which is what makes a user-authored GitHub value safe from it.

  • One issue as an executable development task query
  • One milestone as an executable dependency graph query

Intent intents behaviorally verified

What must become true above the milestones that realise it: each intent's statement, invariants and satisfaction criteria, its stage derived from the plan's milestone status, and each criterion's state derived from the evidence ledger. Nothing is stored and nothing transitions; an intent added under the project model is answered by all of these without a registration anywhere.

  • Which work carries which criterion, and why each issue exists query
  • Every intent, with its derived stage query
  • Which intent a piece of work serves query
  • One intent, with everything derived about it query
  • What the intent model refuses query

Intent realization intent_realization behaviorally verified

Which work realises which intent: every task of this checkout's ledger with the episodes, providers and handovers that carried it, every closed session record and every claim on the peer board, joined through the plan to the intents they serve, each link marked declared, observed, derived or inferred; each intent's unmet criteria with the issues serving them; and the drift between closed work and current evidence. Derived on every read and stored nowhere, so an intent outlives every session and provider that worked on it.

  • Why an intent stands where it stands query
  • Which work realises which intent, and what each still lacks query

  • ○declared status: guaranteed ○recorded evidence: not run A cycle, a self-dependency and a dependency on an issue that does not exist are each refused by name test/cases/42_dag_waves.sh

Using it

The commands that run it

  • majordomus plan begin

    The milestone and issue model — validate it, read it, and move one issue through it.

From the executable's command line

The synopsis of each, as the executable's own help prints it.

  • majordomus devtask issue [OPTIONS] <ID>

    One issue as an executable development task, every field carrying where it came from

  • majordomus devtask milestone [OPTIONS] <ID>

    One milestone as an executable dependency graph: ready, blocked, parallelizable, critical blockers, cycles

  • majordomus intent list [OPTIONS]

    Every intent, with the stage derived from its milestones and its evidence

  • majordomus intent show [OPTIONS] <ID>

    One intent in full: each milestone's derived status and each criterion's evidence state

  • majordomus intent validate [OPTIONS]

    Every finding over the intents; exit 10 when any is a failure

  • majordomus intent coverage [OPTIONS]

    Which work carries which criterion, and the reason every issue exists

  • majordomus intent preflight [OPTIONS]

    Which intent the work on an issue, or on some paths, serves; exit 10 when it serves none

  • majordomus intent realization [OPTIONS]

    Which work realises which intent — tasks, episodes, providers, handovers, peer claims — each link with its provenance, and each intent's unmet criteria and drift; exit 10 when an intent whose milestones are all DONE is contradicted by its evidence

  • majordomus intent explain [OPTIONS] <ID>

    Why an intent stands where it stands: its stage, each criterion, the work realising it
