## 87. Evidence is indexed by subject and judged at the presented revision

### Context

ADR 0041 made a claim's proof a recorded execution. The join it built is by path: a claim in
`docs/CLAIMS.yaml` names a test file, `TestId` turns that path into an identity
(`suite:<case>`, `crate:<binary>`), and the tracked ledger `.ai/repo/evidence/ledger.json`
keeps the latest execution of each identity and nothing older. `majordomus evidence show`
judges every claim against that ledger at the working tree. How many claims reach each state
is what `majordomus evidence show --format json | jq .totals` prints; this record copies none
of it.

That join answers one question about one kind of subject, and every other surface that wants
to say "verified" has no way to ask it:

- **Nothing ties a site widget to a subject.** A homepage panel, a feature page, a command's
  example and an MCP tool's page describe behaviour, and none of them names the claim, rule or
  test that would prove it. Where a page shows proof at all, the word was placed by hand.
- **The site cannot ask whether a claim is proven at the commit it shows.** `evidence show`
  judges the working tree of whoever runs it. The site is built from one commit, which
  `site/data/build.json` names, and no command judges that commit by the ledger committed in
  it.
- **CI throws its runs away.** The suite and the crate tests run on every merge to master and
  print exactly what `evidence record` consumes, and nothing of those runs reaches the ledger
  (ADR 0080's context measures this).
- **A skip reads `failing`.** `Outcome::proves()` holds for a pass only, and both judgements
  map every execution that did not prove to `failing`, so a test that declined to run is
  reported as counter-evidence. In the other direction, the suite runner writes `ok` for a
  case that declines by exiting zero, which records it as a pass; PR #629 corrects that
  (ADR 0080, decision 5).
- **The rules module holds a second copy of the freshness derivation.** `rules/mod.rs` has its
  own `changed_since` and its own mapping from an execution to a state, beside the one in
  `evidence/mod.rs`. Both read the same ledger and must agree on what a commit's diff is, and
  only review holds them together.
- **The entry preflight proposed in PR #578 adds another.** Its `verification.tests` check
  counts a recorded run as current by a filter of its own: a clean recorded tree, a diff from
  the run's commit that touches only the ledger, and a matching digest. It has no containment
  test, so a run recorded on a commit that HEAD does not contain can pass it. Its
  `verification.enforcement` check recounts `rules::report` instead of reading the corpus
  verdict.
- **ADR 0068 and ADR 0080 disagree about where CI evidence goes.** ADR 0068, "CI evidence is
  kept where the run happened, and published with the commit it proves" (proposed, PR #577),
  keeps a run's evidence as the run's artifact, publishes it to the site as a dataset, and says
  that CI's evidence is not committed into the tracked ledger. ADR 0080, "A CI run reaches the
  tracked ledger through a recording branch, never through the run that produced it"
  (proposed, PR #629), commits a trunk run's executions into the tracked ledger through a
  recording pull request. ADR 0080 does not cite ADR 0068, and neither says which one a
  surface reads when they differ.
- **As PR #577 is written, a run record is published as a verdict.** Its collector records the
  run's executions first and derives the report after, so the transcript the site publishes as
  `current` is a verdict over the run's own rows, recorded from a checkout nobody measured.

Another proposal, ADR 0071, "A feature exists only when its delivery is computed and every
dimension passes" (proposed, PR #600), declares delivery dimensions that read test evidence and
holds its own implementation of whether one commit contains another.

This record decides the model every one of those surfaces reads, before any of it is built, so
that each slice of the work is held to one definition rather than to its own.

### Decision

Evidence is indexed by **subject** (a claim, a rule, a feature, a command, a capability, an MCP
tool, a use case), and every surface judges a subject at the **revision it presents**, through
one authority, one freshness function and one aggregation. E is the commit an execution was
recorded on, T the tree its run measured, P the presented revision and Q the presented tree.

#### 1. One authority

A verdict (`ProofState`) is derived only from the tracked ledger
`.ai/repo/evidence/ledger.json`. This adopts ADR 0080. Two things feed the ledger:

- **the recording branch**: a trunk run, after a merge and on a schedule, records its
  executions with `evidence record --origin ci` against the commit it ran and opens a pull
  request that changes only the ledger, from a branch named for that commit. At most one such
  pull request is open; a newer recording replaces it. It passes the same required checks as
  any other pull request;
- **deliberate, committed local recordings.**

**The recording stops at a ledger-only commit.** A trunk commit whose diff from its first
parent is only `.ai/repo/evidence/ledger.json` is not recorded, whether a merge or the
schedule started its run: the recording job ends before it runs a test. Decision 4 judges
every execution in the ledger the same at that commit as at its parent, because the ledger path
is outside `changed'`, so a diff that touches only the ledger still proves. Recording it would
change nothing but the commits the ledger names, and that change would open the next recording
pull request, whose merge would start the next run, without end, each round costing one full
suite run. Landing a recording pull request is such a commit, however it is merged: its diff
from the trunk it lands on is the ledger alone. The schedule still records a trunk whose newest
commit is not ledger-only, which is what it exists for: a merge whose recording never opened or
never landed.

**This amends ADR 0068 sentence by sentence.** The paragraphs of its Decision section, as
written on PR #577's branch, are in order the artifact (¶1), the run reference (¶2), the
publication (¶3), the dispatch refresh (¶4) and the offline run link (¶5).

- ¶1, "It records the executions through `majordomus evidence record --origin ci` and derives
  the report through `majordomus evidence show`." **Amended**: the collector derives the report
  first, with `evidence show` over the tracked ledger as committed at the run's commit, and only
  then records the run's executions. The report is the tracked ledger's verdict at that commit.
- ¶1, "The tracked ledger stays what ADR 41 made it, the evidence of whoever records into the
  tree. CI's evidence is not committed into it." **Superseded by ADR 0080**: a trunk run's
  executions reach the tracked ledger through its recording pull request, and the validating
  run never commits them itself.
- ¶3, "Evidence of the published commit is `current`." **Amended**: `current` takes this
  record's definition (decision 3). Until the site publication is typed, `scripts/pages
  evidence` publishes `current` only when the run is of the published commit, every job that
  ran tests measured a clean tree, the report was derived on a clean checkout of that commit,
  and nothing was absent, refused or failed. Otherwise it publishes `stale` (an ancestor's run,
  or a run that recorded a failure) or `unknown` (the run cannot confirm the report), naming
  each reason. The rule can only withhold `current`; it never changes the report.
- ¶4, "That publication finds evidence of its own commit and says `current`." **Amended** the
  same way: the dispatched publication says `current` only when that definition holds.
- **Standing, by sentence**:
  - in ¶1, "CI evidence is an artifact of the run that produced it."; the sentence naming the
    `evidence` job and the reports it gives the collector; the coverage summary and the
    manifest; and the ninety-day retention;
  - ¶2 whole;
  - in ¶3, every sentence but the amended one: the nearest evidence; the dataset as an
    uncommitted input of one deployment; an ancestor's evidence published as stale, with the
    commits and the changed files between; no evidence published as unavailable, with the
    reason; none of the three blocking publishing; and the one thing ruled out;
  - in ¶4, every sentence but the amended one;
  - ¶5 whole.

**What a run's executions are**, stated once: a validating run's executions decide no verdict in
that run's artifact or on the site, where they are a run record (counted, linked and kept). A
trunk run's executions become verdicts only when its recording pull request lands them in the
tracked ledger (ADR 0080).

#### 2. Supplementary records never strengthen a verdict

- **Run records** are written once per `evidence record` call and kept in the CI artifact, on
  gh-pages under `evidence/<sha>/`, and locally under `.ai/local/evidence/runs/`, bounded at the
  newest 50.
- **Coverage records** are the other kind, carried inside a run record. Both kinds carry their
  own commit and tree.
- ADR 0041 rejected a full execution history in favour of the latest execution per test. That
  is amended only outside the tracked ledger: the ledger still keeps the latest execution per
  test, and history lives only in run records.
- **Local rows** are written only with `evidence record --ledger local`, to
  `.ai/local/evidence/ledger.json`, and are advisory: a surface shows them with their origin
  and decides nothing from them.
- `evidence record` keeps writing the tracked ledger by default, as case 124 holds.

**The monotone rule.** Take a supplementary record of the same test, measured on a clean tree at
a commit R that contains E and is contained in the presented revision. If its outcome is fail,
timeout or error, it caps the verdict at `stale`, with a detail naming the record (its origin,
its identity and R). A supplementary record withholds `proven`; it never decides a verdict,
which is why the cap is `stale` and not `failing`.

The rule has two sources:

- the working copy of the tracked ledger when a commit is presented (decision 5): every
  execution it holds that the ledger committed in the presented commit does not;
- run records.

So no surface shows a verdict stronger than the authority it reads for the revision it presents,
a clean failing run it can see withholds `proven`, and every difference names its record.
`evidence show` and `evidence show --presented HEAD` judge different revisions (the working
tree, and HEAD as committed): the first can read `failing` where the second reads `stale`, and
neither reads verified.

**Publication states** are site-level words, not proof states, and each is already filed as a
status token of the design system. A publication carries exactly one, decided at publication
time from what it can observe: `build.json`, the run records it read and the conclusion of P's
CI run. The first matching row wins.

<div class="overflow-x-auto" tabindex="0">

| # | Observed at publication | State |
|---|---|---|
| 1 | `build.json.dirty` is not `false` | `dirty` |
| 2 | a run record read, P's own or an ancestor's, caps at least one verdict shown through the monotone rule | `stale` |
| 3 | P's own run record is read, and every tree it carries was measured clean | `current` |
| 4 | P's own run record is not read, and P's CI run has not concluded | `pending` |
| 5 | anything else: P's run concluded without a run record (its `evidence` job skipped, cancelled or failed), P's record carries a dirty or unknown tree, the record is unreachable (the artifact expired and no gh-pages copy exists), or no CI run of P is found | `unknown`, naming which |

</div>


- A state and its causes are separate: whatever row matched, every record that capped a
  verdict is listed beside it, so a dirty build that a record also contradicts reads `dirty`
  and still names that record.
- A record of an ancestor only can cap a verdict (row 2) and nothing else. It never makes a
  publication `current`: without P's own record the state is `pending` or `unknown`, with the
  ancestor's record listed by its commit and the commits between. The interim rule of decision
  1 publishes an ancestor's run as `stale` only because there the transcript itself is the
  ancestor's.
- `pending` is the one state a later publication of the same P is expected to replace, when
  P's run concludes (ADR 0068's dispatch refresh, ¶4).

#### 4. Freshness is one function

`changed'` is the set of paths changed from E to the presented side, minus the ledger path. The
first matching row wins.

<div class="overflow-x-auto" tabindex="0">

| # | Condition | State |
|---|---|---|
| 1 | no test | `no_test` |
| 2 | no runner drives the path | `unrunnable` |
| 3 | nothing recorded | `not_run` |
| 4 | skip | `not_run`, with the reason |
| 5 | fail, timeout or error | `failing` |
| 6 | pass; git cannot compare | `stale` |
| 7 | pass; E not contained | `stale` |
| 8 | pass; contained; the test's digest moved; no input changed | `stale` |
| 9 | pass; contained; a declared input changed | `stale` |
| 10 | pass; contained; `changed'` empty; recorded tree clean; presented tree clean | `proven` |
| 11 | as row 10, but the recorded tree is dirty or unknown | `inputs_unchanged` |
| 12 | as row 10, but the presented tree is dirty or unknown | `inputs_unchanged` |
| 13 | pass; contained; `changed'` non-empty; inputs known and none changed | `inputs_unchanged` |
| 14 | pass; contained; `changed'` non-empty; the route names no inputs | `stale` |

</div>


Only row 10 renders "verified", on every surface: a rendered word, a badge and the rules corpus
verdict alike. `rules report` says `proven` only when every blocking rule is `proven`, because
inputs unchanged is not proven (ADR 0041). A diff that touches only the ledger still proves;
that is what lets a recording pull request, a child of E, prove E. A skip is never `proven` and
never `failing`.

A claim's inputs are its source, its implementation and its test source; a rule's are its test
source and its definition; any other route's are its test source and the implementation paths
derived for it, or none. A rule is judged by this same function. The working-tree diff stays
`evidence::changed_since`, and the rules module's copy is removed.

The entry preflight of PR #578 is the one known exception, named in decision 3, until its
follow-up slice lands: its tests check can call a run current when E is not contained in HEAD,
and its enforcement check recounts the rules.

#### 5. The presented revision

- By default the presented revision is the working tree.
- `--presented <rev>` must name the checked-out commit. It is judged by the ledger committed in
  it. The presented tree is measured, ignoring the ledger, and a tree given on the command line
  can only weaken that measurement.
- The working copy of the ledger is not the authority for a presented commit, and it is not
  ignored either. Every execution it holds that the committed ledger does not is a
  supplementary record, read through the monotone rule (decision 2). A clean failing run that
  the checkout holds uncommitted therefore withholds `proven`.
- On the site the presented revision is `build.json.commit`, and `build.json.dirty` caps the
  verdict.
- Judging any other commit is not built.

#### 6. E and T are measured by the run

- The runner measures its commit and its tree at the end of the run, ignoring its own named
  outputs, and carries both beside its report.
- The recorder stamps them. It refuses a report whose commit is not HEAD, and records T as
  `unknown` when there is no measurement.
- A pull-request run's commit is GitHub's merge commit, with `head_sha` beside it. Only a trunk
  run can prove a trunk commit.
- A report states only what ran: a crate binary that ran no test, or a filtered subset, is a
  skip.

#### 7. Containment is one implementation

Whether one commit contains another is decided once, in `git/mod.rs`, beside `git::is_ancestor`,
and shared with the delivery subsystem (ADR 0071). The delivery subsystem imports it once it is
on master and deletes its own copy. Containment that git cannot decide is row 6, never proof.

#### 8. Aggregation is one function

One function combines parts, over each state enum's declared order:

- `failing` if any part fails;
- otherwise the weakest of the parts that can carry proof;
- otherwise the weakest of all parts.

No second ranking is written anywhere. The first step exists because the declared order places
`failing` above `not_run`, so the weakest of a failure and an absence would read as the
absence: a failure is never hidden behind one. Per-state totals always accompany a verdict.

A subject's verdict is computed over its members' own verdicts, never over their raw routes. A
rule member contributes through one declared `RuleState` → `ProofState` mapping:

<div class="overflow-x-auto" tabindex="0">

| `RuleState` | `ProofState` | Carries proof | Why |
|---|---|---|---|
| `proven`, `inputs_unchanged`, `stale`, `failing`, `not_run`, `unrunnable` | the same word | yes (`unrunnable` only when the rule itself judged it) | identical meaning |
| `gated` | `not_run` | yes | a gate refuses violations, but no recorded run proves the behaviour |
| `reviewed` | `no_test` | no | the rule declares that nothing executable expresses it |
| `unproven` | `no_test` | yes | a blocking rule that names nothing is a defect and must weaken its subject |
| `dangling` | `unrunnable` | yes | a named proof that does not exist; the subject also gets a `dangling_member` finding |

</div>


#### 9. The subject index is derived only, in Rust

The index is derived from existing declarations and no list of subjects is authored: claims,
rules, features, commands with their `# majordomus-covers:` and `# majordomus-negative:`
headers, capabilities, MCP names and use-case edges.

<div class="overflow-x-auto" tabindex="0">

| Key | Resolution |
|---|---|
| `claim:<id>` | the claim join of `evidence show` |
| `rule:<id>` | the rule join of `rules report` |
| `feature:<id>` | members: its claims, rules, commands and use cases |
| `command:<path>` | the suite cases whose first `# majordomus-covers:` or `# majordomus-negative:` line names the command, and the crate's CLI examples for a command that has one |
| `capability:<id>` | its command's routes |
| `mcp:<tool>` | the capability the registry names for the tool |
| `use_case:<id>` | its scenario run; members: the commands it runs, the rules it exercises and the claims it evidences, never its owning features |

</div>


- `majordomus generate` writes the index as `site/data/registry/evidence-subjects.json`, in the
  executable's site-data directory. It never writes into `site/data/generated/`, which the shell
  site generator owns and replaces wholesale, so that no directory has two writers.
- The index holds no ledger content and no commit, so `majordomus generate --check` stays
  stable.
- The site only joins to it: `scripts/generate-site-data` joins a panel's route to a key, and a
  subject the index does not have fails generation with the executable's refusal.
- It names the shell derivations it replaces or holds equal: the `tests` of `commands.json` in
  `scripts/generate-site-data`, the header reading of `lib/commands.sh`, and
  `scripts/ci/command-furnished`. A case holds them equal until each reads the artifact. Where
  they differ, the index's first-line rule is the one kept.

#### 10. Subject findings are a separate list

`feature_without_evidence`, `freshness_unknown` and `dangling_member` are findings of a subject's
answer, never of the claim report, whose findings are what `evidence show --check` gates on. They
stay advisory until the gate slice (I1962) makes them refusing and rewrites
`.ai/repo/evidence-baseline.txt` in the same change.

#### 11. The test category is derived from the test identity

`suite:<case>` is end-to-end; `crate:<binary>` from `tests/<binary>.rs` is integration; then
unit, doctest and scenario, the last being a use case's run. `verification.requires` is not
added to `feature/v1`: what a feature requires is what its members name.

#### 12. Coverage is supporting evidence

Coverage never decides a verdict. It is current only for its own commit, with a clean tree, and
on the site only when the presented tree is clean as well. Otherwise it is shown with its commit
and as `stale`.

#### 13. Status-word token keys are hyphenated

The verdict words are filed in the design tokens with hyphens (`inputs-unchanged`, `not-run`,
`no-test`), because the token name pattern refuses underscores. `ProofState::token()` is the one
mapping from the wire word to the token; no template rewrites a word.

#### 14. The public projection is allow-listed

What the site publishes about evidence is a typed projection whose fields are named one by one;
a field not on the list is not published. Text a run printed reaches it only through the one
redactor (I1950), and the published artifact still passes the generator's refusal of machine
paths and credential markers.

#### 15. Surface decisions

- MCP exposes evidence through tool calls only, with no resource templates.
- The required `ci` check does not need the `evidence` job: evidence is refused at publication
  and at finish, not at merge.
- The llvm-cov HTML report is published for the latest deploy only.
- Use-case evidence is not stamped with a commit in the committed catalogue; it is joined to a
  revision only through the deploy-time publication.
- No new shell automation is added (ADR 0069).

#### 16. The recording pull request

A pull request opened with the workflow's own `GITHUB_TOKEN` starts no `pull_request` workflow,
so it would never receive the required checks decision 1 requires of it. The recording pull
request is therefore opened by a token whose events start the required workflow: either the
recording job dispatches `validate.yml` on the recording branch, or it uses a GitHub App token.
The owner decides between them before the CI wiring slice (I1954) lands.

### Consequences

- Until the recording branch runs, the tracked ledger holds only local rows and the site renders
  mostly `not_run`. That is the true state, and it is why the CI wiring precedes the badges.
- ADR 0068 changes only in the sentences decision 1 names. ADR 0041 changes only outside the
  tracked ledger: run records keep history, and the ledger still keeps one execution per test.
- Every rendered "verified" traces to row 10 of one function, and every weaker word that differs
  between surfaces names the record that weakened it.
- A skipped test reads `not_run` with its reason instead of `failing`, and a guaranteed claim
  whose test only skipped is still reported as unsupported.
- The rules corpus verdict proposed in PR #597 reaches `proven` less often: a corpus whose
  blocking rules are merely `inputs_unchanged` reads unproven.
- The delivery subsystem gives up its private containment when it rebases.
- The entry preflight stays an exception until I1965 lands. This record names it so that it is
  not mistaken for the rule.
- The subject index is one more generated artifact. It is declared like every other one, so its
  merge is resolved by the derived merge driver.
- The work is tracked as the milestone `test-evidence`, one issue per slice, I1945 to I1965;
  `majordomus plan` derives what may be worked on and in what order.

### Alternatives rejected

- **Hard-coded badges and links.** A badge written into a template is a claim with no execution
  behind it, and it goes stale the moment the ledger changes.
- **A browser fetch of GitHub Actions.** The published page would depend on the network and on an
  API's limits at read time, it would show a run's own rows as a verdict, and
  `scripts/ci/link-check` decides links offline.
- **Per-surface catalogues of subjects.** Each surface would drift from the others; the command
  to test join already exists more than once in shell (decision 9).
- **A parallel freshness enum.** A second vocabulary for the same states is a second derivation.
  The publication states are kept apart from the proof states for that reason.
- **Commit equality, E = P, as the test for `proven`.** It is unreachable once the record is
  committed: the commit that lands a recording is a child of E, never E. The ledger-only diff
  gives the same guarantee and can be met.
- **Three evidence stores without a read rule.** The tracked ledger, the CI artifact and a local
  ledger would each answer differently, and a reader could not tell which one a surface showed.
- **Recording from the validating run itself.** ADR 0080 rejects it: a pull-request run has no
  business writing to the repository it is judging.
- **Publishing a verdict computed over a CI run's own rows.** That is ADR 0068 as first written:
  the rows were judged against a checkout nobody measured, so the site could say `current` for a
  tree the run did not vouch for.
