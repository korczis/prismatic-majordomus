work-graph-github — Projekce na GitHub je hlídaná, identifikovatelná a procházitelná a sloučený pull request vede zpět k výsledku, kterému sloužil

Projekce nemůže tiše zetlít: kontrola spouští kontrolu driftu při každé změně, která může pohnout modelem nebo adaptérem, a drift je selhání CI s pojmenovaným záznamem. Identita cestuje se záznamem, ne vyčtená z jeho titulku, takže přejmenování titulku na GitHubu nic nepřesune a nevytvoří duplikát, a remote může být fixture, takže se dá bez sítě dokázat, který záznam je který. Slovník sladění rozlišuje stavy, které dosud slučuje, takže `missing` už nestojí za záznam, který nebyl nikdy vytvořen, i za záznam, který člověk smazal, a vzdálená úprava se hlásí jako vzdálená úprava. Nad projekcí pull request pojmenovává úkol, který realizuje, a hrana se odvozuje z gitu a GitHubu, ne z paměti, takže mergnutý commit vede zpět ke kritériím přijetí, která splnil, a výsledek vede vpřed k důkazům, že platí. Odvození, která shell už počítá — ready, blocked, waves, next, status — jsou čitelná přes stejný povrch schopností jako vše ostatní, co tento repozitář ví, ne jen z terminálu.

Problém

Tento repozitář už práci modeluje jednou: milníky jsou výsledky, úkoly jsou prováděcí smlouvy, žádný stav se neukládá a `scripts/github-sync` promítá obojí na GitHub s oblastí označenou hashem, která chrání to, co napsal člověk. Model není vada. Vadou je, že detektor nikdo nespouští: `core-check` spouští `github-sync --plan` a `--render`, nikdy `--check`, takže exit 11 adaptéru se v CI nikdy nespustil. Projekce byla aplikována jednou 2026-09-04 a od té doby ne. Změřeno 2026-09-09 na 867f3a9: 191 zjištění driftu, z toho 172 jsou kanonické úkoly, které na GitHubu nikdy neexistovaly, a 19 jsou těla, jejichž kanonický text se posunul. Všech 8 milníků je synchronizovaných, což je přesně to, co činí hnilobu neviditelnou: povrch, na který se člověk dívá, je povrch, který se stále shoduje. Pod tím adaptér identifikuje vzdálený záznam rozborem jeho názvu na předponu `I0001 — ` a čte vzdálenou stranu přes stránku o 200 položkách, která už drží 19 úkolů a 117 pull requestů, takže mapování se rozbije, když člověk přejmenuje název, a čtení se zkrátí, jakmile běží backfill.

Aktuální stav

Kanonický model tvoří 15 milníků a 184 úkolů, validovaných příkazem `majordomus plan validate` (0 selhání, 4 varování o rozsahu) a vynucovaných `lib/doctor.sh` a `scripts/ci/core-check`. `scripts/github-sync` implementuje plan, check, apply a render s vlastnictvím polí a hashem značky. GitHub drží 8 milníků a 19 úkolů. `--check` končí s 11 při driftu a žádná kontrola jej nevolá. Úkoly a milníky se servírují jako dokumenty přes `objects.get` a žádné z odvození plánu není schopností: `lib/plan.sh` je počítá a spustitelný soubor v Rustu čte `.ai/repo/project/issues/` jen kvůli názvům souborů. Důkazy nesou volitelný řetězec `commit` a žádný pull request, běh kontroly ani větev.

Cílový stav

Přispěvatel přesune úkol, spustí kontroly a CI mu řekne, že projekce zaostává, dřív než recenzent. Člověk přejmenuje úkol na GitHubu a další synchronizace jej aktualizuje místo duplikace. Čtenář se zeptá, který pull request úkol realizoval, nebo kterému výsledku sloužil zmergovaný commit, a jeden příkaz odpoví z odvozených hran. Připravenost plánu lze zjistit přes MCP a HTTP, protože je to schopnost, ne shellová funkce.

Mimo rozsah

  • Nahrazení kanonického modelu, které není tou vadou
  • Import sémantiky GitHubu do kanonických záznamů; GitHub zůstává projekcí
  • Přesun síťových volání do samotného nástroje, což test/cases/08_no_forbidden_constructs.sh zakazuje
  • Klient GraphQL nebo jakákoli abstrakce providera nad rámec jednoho hostitele GitHub, na který tento repozitář publikuje
  • Přiřazení, reakce, nástěnky projektů nebo diskuse

Kritéria přijetí

  • Kontrola spouští kontrolu driftu při každé změně, která může pohnout modelem nebo adaptérem, a nález driftu shodí CI s uvedením záznamu a nápravy
  • Identita jsou kanonická data: přejmenování titulu na GitHubu přesune mapování s ním a nevytvoří duplicitní záznam
  • Smiřování je dokazatelné offline proti fixture remote a fixture je odmítnut při jakékoli mutaci
  • Slovník smiřování rozlišuje never-created, deleted-remotely, edited-remotely, canonically-moved a conflicting a každý stav jmenuje, co by se změnilo, dříve než se cokoli změní
  • Pull request je s úkolem, který realizuje, spojen odvozenou hranou a vztah lze procházet oběma směry
  • Odvození plánu jsou čitelná přes povrch schopností a přidání dalšího nevyžaduje úpravu registru transportů
  • Každé tvrzení, které tento milník činí o GitHubu, je podloženo testem, který běží offline proti fixture

Rizika

  • Zpětné doplnění je mutace směřující ven: aplikace projekce vytvoří zhruba 180 veřejných úkolů v jednom běhu. Musí to být záměrný, potvrzený čin, ne vedlejší efekt zapojení gate.
  • Zapojení kontroly před doplněním způsobí, že CI na masteru zčervená, dokud doplnění nepřistane. Na pořadí záleží a je součástí práce.
