0.11.0· A supervisory control layer for AI-assisted work

AI coding agents do the work. Your repository decides whether it is done.

Majordomus keeps the rules, the task and the paths it may touch, the handover and the definition of done in the repository instead of a chat window. It tells you when two agents claim the same files, and it refuses to call work finished until the repository's own checks pass. Local, portable shell, beside whichever coding agent you use; it never calls a model.

01the problem

Where AI-assisted work actually breaks down

Giving a model a larger context window does not solve this. A larger pile of unstructured information is still a pile.

  5. →opened CLAUDE.md and AGENTS.md and found two different rulebooks for one repository

02how it works

Declare what must hold. Derive everything that repeats it. Refuse what does not.

Nothing here asks a model to behave. The repository states its rules, its lifecycle and what done means as typed files; one executable derives every instruction file, interface and page from them; and the commands that close a task check the result against the contract before anything is recorded.

  1. 1 · Declare

    Policy, rules, profiles, the task lifecycle and the finish contract live under .ai/ as files with schemas. A rule is blocking or advisory, and a blocking rule stops the command instead of advising it.

03what it refuses

The half a model cannot give you

Every transcript below is a run that happened, of a command of the declared lifecycle, that ended by declining to accept the work. None of it is written here: a command that stops refusing stops appearing, and the page cannot be built with nothing on this list.

This is the difference between a tool that tells a worker what to do and one that decides whether what it did counts. A worker can always say it is finished. Here that sentence is a claim the repository evaluates, line by line, against a contract written before the work started — and nothing is recorded while any line of it fails.

06direction

What is shipped, and what this is becoming

The argument above is a doctrine and a design. Parts of it run today; more of it does not. The feature matrix is the shipped half, feature by feature and interface by interface. The unshipped half is named here rather than left for a reader to assume.

  1. Intent capture The statement, and what would settle it. here today: not built
  2. Context Governance preflight, then discovery, then compilation — not retrieval. here today: largely shipped: majordomus context
  3. Plan Ambiguity named, impact derived, strategy chosen against the architecture. here today: not built; the authored work model is
  4. Execute Several workers, different responsibilities, one coordination object. here today: partly: peers, scope claims, worktrees
  5. Verify Against the acceptance criteria, not against the diff. here today: shipped, against the finish contract, not against criteria
  6. Proof An inspectable bundle, not the word success. here today: partly: evidence discharges obligations

Repository intelligence is not a model provider.

Majordomus never invokes a model; it decides what a worker is told, what it may touch, and whether its claim of being done can be believed.

Partly built: the intent record; not built: everything above it

An intent is now a typed record under the project model: a statement, its invariants, the milestones that realise it and the evidence that settles each criterion. Its stage is derived from the plan and each criterion from the evidence ledger, `majordomus-cli intent validate` refuses one whose links do not resolve, and `intent preflight` names the intent an issue serves or the link that is missing. That is the whole of what exists. The session does not load an intent when it starts, completion policy does not yet decide satisfaction, the Cockpit has no intent view, GitHub milestones are not reconciled against intents, and nothing derives a plan from a desired outcome or runs an opposition pass. Every sentence on this page written in the conditional is one of these, and this section will shrink as each one lands.

07get started

Try it on a repository you already have

What init creates is the layer this site is generated from: one directory, tracked, readable without the tool. Everything above this section was derived from this repository's own.

install · one command

Install majordomus in one command

No git, no Rust, no Node, no root. One archive for your machine, its digest verified before anything is unpacked, into $HOME/.local/bin.

1 · paste into a terminal 
curl -fsSL https://majordomus.dev/install.sh | sh

2 · in the repository you want supervised

majordomus init

Writes .ai/ — the policy, the profiles, the rules, the prompts, the workflows — and nothing else.

3 · point your agents at it

majordomus update

Generates CLAUDE.md, AGENTS.md and the other bootstraps from the policy; every worker reads the same contract. Platforms, pinning a version, the security model →
