Rendered from docs/PROFILES.md — the same Markdown GitHub shows.

A profile is one working mode: how much context a task is assembled with, how much effort it is worth, how the worker reports, and what it must produce before it may finish (.ai/repo/profiles/README.md). This document follows a profile from its YAML file through every program that reads it, and marks each link with the code that does the reading and the test that proves it, or says that no test does. It is the audit that milestone a-profile-is-resolved-once-and-enforced is built on (issue I4500). The decision it led to is ADR 0232: one resolver owns the effective profile, and every reader below becomes a consumer of it.

Everything here was measured at d7fd9a36170. A line number is a claim about that commit. When a row's code moves, the row moves with it.

Standing

Each link has one of four standings:

StandingMeaning
proventhe named test fails when the link is removed
advisorythe link exists and acts, but nothing refuses when it is ignored, or no test holds it
duplicateda second reader computes what another reader already computes, and the two can disagree
missingan input or a consumer the model needs, and no code joins them

The path of a profile

.ai/repo/profiles/<name>.yaml           (seeded from share/skeleton/profiles by init/migrate)
  -> validation         doctor: parse, allowlist, name = file, default exists, limits
                        index: JSON schema majordomus.profile/v1, per object
  -> selection          start: --profile, else policy profiles.default   (issue's profile ignored)
  -> task record        current.yaml profile: <name>; ledger task.started {profile}
  -> worker context     context: TASK, PROFILE, toggles; check --explain: the flattened file
  -> enforcement        check: checkpoint freshness (advisory class)
                        finish: verify command, regression test, decision record (blocking)
  -> records            checkpoint, handover, session, session-context: the name only
  -> other readers      reasoning mode, proceed effort, completion gates, plan, Cockpit, site

There is no resolver. Every reader opens the file, or the object the index made of it, by itself.

The trace

Path is the file and line at d7fd9a36170. "Reads" is what it takes from a profile. "Does" is what it does with it. "Consumer" is who sees the result.

The rest of the model:

SurfaceTodayWhat the resolver must keep
File schemamajordomus.profile/v1, additionalProperties: false, seven required keysv1 for additive optional keys (ADR 0232); a rename or a new required key is v2 with a migration
Allowlistshare/allow/profile.txt, generated from the schemaregenerated, never hand-edited
Task recordcurrent.yaml profile: <name>the name, plus the effective profile's fingerprint
Ledgertask.started requires profile (share/events.yaml:29)the name stays; the fingerprint is added
Continuity recordTaskRef.profile: Option<String> (continuity/record.rs:109); none on a mesh handoverunchanged; a resume suggests the name
Policyprofiles.default, profiles.checkpoint_interval_defaultthe default stays an input; the interval default becomes a diagnostic when it disagrees with the default profile

Two axes have no consumer at all. Nothing reads effort_escalation, and output_contract is printed by context (lib/context.sh:228) and nothing checks it. The axes capability, effort, verbosity and presentation are printed, and effort is forwarded by proceed.step. None of them is enforced, and share/profile-limits.yaml leaves them out on purpose.

Surprises against the issue's own record

The issue was written at 51b38035a71. Re-measured at d7fd9a36170:

  • I0201 is delivered (519e783abcb). share/profile-limits.yaml, its doctor reconciliation and the three # majordomus-limit: adapters are on master, and case 4400 proves them. The issue record still carries no completion stamp.
  • apps/majordomus-cli/src/reasoning/mod.rs reads a profile's file directly, and so is a Rust reader the issue does not list. proceed/step.rs reads effort from the index, which is a second.
  • gates/done.rs does not read the profile at all. It asks the regression question of every task, while it cites the profile key.
  • The policy's checkpoint interval and the default profile's are two declarations of one value.

What is not covered yet

  • No test or gate fails when a new reader of a profile appears that is not a row here. The test is a case under test/cases/ that searches lib/, share/ and the crate source for mj_load_profile, mj_pro , profile_files, kind == "profile" and the profiles directory, and compares every hit with the paths of this document's trace tables. test/ is outside I4500's declared scope, so the case belongs to the resolver's first issue. Until then, this table can go stale without anything noticing.
  • docs/claims/profile-axes.md says every axis is advisory. That is stale for the context.* toggles and the verification.* requirements. It is outside this audit's scope (see ADR 0232, Consequences).
