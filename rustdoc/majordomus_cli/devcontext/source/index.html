Source
Expand description

The source ranges a request’s paths reach: where each Rust definition under them lies, offered to the budget as a range rather than as a whole file.

§Why a range, and why here

A worker who is told “the code under apps/x/src/devcontext” has been told nothing it can afford to read: that is five files and six thousand lines. What it can afford is the outline — fn compile, lines 762–936 of mod.rs — and then the one range it needs. So a request whose effective paths reach Rust source is answered with one candidate per definition, each carrying the path, the line span, the symbol, how it was found and what reading it costs, and the budget spends those candidates in the same total order as everything else. The whole-file cost and what the selected ranges cost instead are reported beside them (super::SourceCoverage), so the saving is a measured number in the answer rather than a claim about it.

§What it reads, and what it refuses to

super::select reads no file and walks no tree; this module is the one place the compiler reads source, and it is bounded on every axis:

  • only files git tracks under a requested path, asked for as a literal pathspec so that a path is never interpreted as pathspec magic;
  • only files the repository scope admits (crate::scope::Scope::classify: undeclared, secret, binary and oversized files are out before anything is read);
  • never a symbolic link, and never a file whose real path leaves the repository root;
  • at most MAX_SOURCE_FILES files, MAX_SOURCE_BYTES bytes each and MAX_RANGES_PER_FILE ranges each — whatever is cut is counted in the answer.

Nothing is built and nothing of the analysed project runs: the parser is syn over the bytes read, with no macro expansion, no cfg evaluation and no name resolution. A range is therefore a syntactic definition, observed: it says where an item is written, never what calls it. A file syn cannot parse, and every language it does not cover, is reported as such rather than answered with an empty outline that would read as complete.

§A file, end to end

A file is outlined into its definitions; the compiler names each one by a range of that file under SCHEME, and the budget spends them as KIND entries.

use majordomus_cli::devcontext::source::{outline, KIND, SCHEME};

let text = "pub struct Budget;\n\nimpl Budget {\n    pub fn spend(&self) {}\n}\n";
let defs = outline(text).unwrap();
let uris: Vec<String> = defs
    .iter()
    .map(|d| format!("{SCHEME}src/budget.rs#L{}-L{}", d.first, d.last))
    .collect();
assert_eq!(uris, ["source:src/budget.rs#L1-L1", "source:src/budget.rs#L4-L4"]);
assert_eq!(KIND, "source-range");

// a definition never spans another: the impl block is its methods, not a range of its own
assert_eq!(defs[1].symbol, "Budget::spend");

Constants§

KIND
The kind every range candidate carries.
MAX_RANGES_PER_FILE
The most ranges one file contributes; the rest of its definitions are counted.
MAX_SOURCE_BYTES
The largest file read for ranges. A larger one is reported, not parsed: the parser has a budget like everything else, and the repository scope may already set a lower one.
MAX_SOURCE_FILES
The most files one request reads for ranges. A directory with more is read in the index’s byte order up to the bound, and the rest are counted as truncated.
PARSER
What syn reads, said once so every range and the coverage name the same parser.
SCHEME
The scheme of a range’s identifier: source:<path>#L<first>-L<last>.
