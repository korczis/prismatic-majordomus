Only for a verified region does it keep record ids, and only the leading id of each list line github-sync writes (`- Refs #<n> (<id> — <title>)`, `- <id> — <title> (not on GitHub yet ...)`, `- <id> (its record is in this pull request ...)`, github-sync:406-412), never an id inside a title or on the `**Milestone:**` line, each decided by I2901's plan::is_record_id. The hash contract is github-sync's, reproduced exactly: carriage returns stripped from the decoded body (github-sync:600); the region is the lines strictly between the one begin line and the one end line, each ending in a newline, as pr_region_read (github-sync:457-467) extracts them; hash16 (github-sync:484) is the first 16 hex characters of the sha256 of those bytes, compared with the begin marker's hash as github-sync:611-619 does. The Rust reader is held to a golden body github-sync wrote. plan.delivery adds the edge `projected_region` beside title_or_branch, slug, subject and forge_title, under forge_title's landing rule (plan/delivery.rs:1016-1052): it counts only when the pull request's merge commit or head is in the history read, at that commit's time, and a merge that only plans is judged as forge_title's is. It exists only in the live answer, like the forge's merged titles (plan/delivery.rs:1001-1015); an answer at a commit reads that commit's history only and reports the region source unread with its reason. An edited or malformed region names nothing, and the delivery source that reads the regions names each such pull request by number and state, in github-sync's words."
