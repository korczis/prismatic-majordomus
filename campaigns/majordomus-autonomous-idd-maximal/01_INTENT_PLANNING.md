# PHASE 01 — INTENT REALIZATION, PLANNING, CRITIQUE, MILESTONES

Start from the current typed intent record, criteria, invariants, evidence ledger, `intent validate`, preflight, coverage, issue/milestone links, and gap/critique records. Trace exactly how stages and verdicts are derived. Do not invent a second planning schema. Locate existing milestone dependency/issue model and GitHub reconciliation rules.

Implement an intent realization capability with operations conceptually equivalent to `analyze`, `propose`, `critique`, `materialize`, `reconcile`, `explain`, `start`, `pause`, `resume`, `cancel`, `status`. Names must conform to existing capability declaration patterns. Each operation is typed and safe under retries. Have an LLM propose a graph only as a candidate: no hallucinated existing identifiers, paths or acceptance evidence. Deterministic validation verifies identities, criteria coverage, dependencies, resource scopes, acceptance tests, budget, execution permissions, worktree isolation, and no cycles. An opposition pass must critique assumptions, missing work, unattainable success criteria, duplicate PRs and unsafe operations. A planner revises or records actionable BLOCKED state with diagnostics.

Materialize accepted plans into the existing milestone/issue system, idempotently, with bidirectional provenance and GitHub mapping where currently supported. Repeated planning must reconcile rather than duplicate issues. Model decomposition (parent/child outcomes, bounded tasks) as an extension of canonical metadata only if existing constructs cannot express it. Persist LLM/model/provider and prompt version fingerprints for audit, not private raw prompts in public output. Preserve a stable content hash of the intent criteria and plan proposal.

Derived state pipeline: Intent statement/invariants -> criteria -> evidence requirements -> gap assessment -> candidate plan -> critic verdict -> validated dependency graph -> milestones/issues -> readiness -> execution -> observed evidence -> criterion verdict -> intent satisfaction. Expose `why blocked`, `what changed since proposal`, `why this issue exists`, `what remains to satisfy criterion`, and stale/contradicted evidence. A complete milestone without passing intent criteria must not mark intent satisfied.

Required tests: idempotent plan replay; no empty criterion coverage; malformed links; no hallucinated issue mapping; graph cycles; dependency blocking; plan drift after criterion edit; reconciling external GitHub changes; adversarial critique rejects missing tests; conflicting scopes; stale evidence; zero-work already-satisfied intent. Produce a fixture with a small real code change, 2–3 criteria and 2 linked issues proving bidirectional traceability through CLI/API/MCP/UI projection.

Acceptance: ONE natural-language intent becomes a valid critic-reviewed executable plan and stable canonical work graph with no manual issue transcription and no duplicate issue creation after rerun.
