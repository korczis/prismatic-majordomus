Whether a worktree’s work is already in the trunk, by what git can prove offline.

git branch --merged answers one question: is the branch’s tip an ancestor of the trunk. A branch squash-merged on the forge, carried in a train, or cherry-picked is never an ancestor, and a worktree whose only uncommitted changes are records that landed through another branch is never clean, so neither is offered by worktree cleanup. On 2026-11-16 that left 205 worktrees (about 44 GiB) on this machine whose every byte was already on the trunk; they were found with the two readings below and removed by hand.

Both readings are exact, never heuristic:

  • content_in: merging the branch into the trunk would change nothing. git merge-tree --write-tree <trunk> <rev> writes the merged tree without touching any work tree or ref; when that tree is the trunk’s own tree, the branch adds nothing. A branch with one line the trunk lacks writes a different tree, and a conflict is a “no”.
  • uncommitted_in: every path git status reports holds, in the work tree, exactly what the trunk holds at that path (the same blob and mode, or absent in both).

Neither fetches, and neither writes: merge-tree --write-tree adds the merged tree’s objects to the object store, as any git merge would, and moves no ref.

use majordomus_cli::worktree::landed::{content_in, uncommitted_in};
let dir = tempfile::tempdir().unwrap();
let run = |args: &[&str]| {
    let ok = std::process::Command::new("git")
        .args(["-c", "user.email=t@t", "-c", "user.name=t"])
        .args(args)
        .current_dir(dir.path())
        .env_remove("GIT_DIR")
        .env_remove("GIT_WORK_TREE")
        .status()
        .unwrap()
        .success();
    assert!(ok, "git {args:?}");
};
run(&["init", "-q", "-b", "main"]);
run(&["commit", "-q", "--allow-empty", "-m", "base"]);
run(&["switch", "-q", "-c", "squashed"]);
std::fs::write(dir.path().join("a.txt"), "a\n").unwrap();
run(&["add", "a.txt"]);
run(&["commit", "-q", "-m", "one"]);
run(&["switch", "-q", "main"]);
run(&["merge", "-q", "--squash", "squashed"]);
run(&["commit", "-q", "-m", "squash"]);
// not an ancestor of main, and still entirely in it
assert_eq!(content_in(dir.path(), "squashed", "main"), Some(true));
run(&["switch", "-q", "squashed"]);
std::fs::write(dir.path().join("b.txt"), "b\n").unwrap();
assert_eq!(uncommitted_in(dir.path(), "main"), Some(false), "b.txt is not in main");
std::fs::remove_file(dir.path().join("b.txt")).unwrap();
assert_eq!(uncommitted_in(dir.path(), "main"), Some(true), "nothing uncommitted is left");

Functions§

content_in
Would merging rev into trunk change nothing? Some(true) when the merge writes the trunk’s own tree, Some(false) when it writes another tree, conflicts, or cannot be written at all (a revision git cannot merge, a git older than 2.38 without merge-tree --write-tree): a “no” every time, never a “yes”. None when the trunk itself cannot be resolved or git cannot be run. cwd is any work tree of the repository.
trunk_reference
The ref the trunk is judged by: its remote-tracking branch when it has one (what every other checkout and the forge see), the local trunk otherwise.
uncommitted_in
Does every uncommitted change in this work tree already hold what rev holds at that path, in the index and in the work tree? Some(true) for a clean work tree too. Some(false) when any path differs (a staged version the trunk lacks included), when a conflict is unresolved or an operation (merge, rebase, …) is in progress, for a path that is a symbolic link or a directory git reports whole (a nested repository), and for a path the file system will not describe: none of those is ever judged equal. None when git cannot read the work tree, rev, the index or a file’s content.
