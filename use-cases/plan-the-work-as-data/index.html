Keep the plan as milestones and issues the tool can validate

Declare milestones as outcomes and issues as execution contracts, and let the tool say what is ready and what is blocked.

guaranteed Repository knowledgeintermediatemaintaineragentwrites state

Situation

The plan lives in a tracker nobody reads from the repository, or in a document whose status column is a matter of opinion. What is ready to start and what is blocked is an argument, not a query.

Outcome

Milestones and issues are files under .ai/repo/project/; plan validate refuses a dangling dependency or a cycle, and plan ready and plan blocked are computed from the same records every time.

The scenario

Executed against the real tool, in a repository prepared by plan-model, every time this site is generated. What follows is not a description of what should happen; it is what happened.

given

  • ·a canonical project model with one milestone and two issues, the second depending on the first

when

  1. 1majordomus plan validate
  2. 2majordomus plan ready
  3. 3majordomus plan blocked

then

  • ·status is derived from the records and git, never written into them
  • ·an issue cannot be marked done without the evidence its milestone requires

What the tool did

Evidence of the run this page was generated from: pass, 3 step(s). Output is normalised: the repository's path, timestamps, ids and durations are placeholders; nothing else is edited.

  1. 1 $ majordomus plan validate exit 0

    every record parses, every reference resolves, the dependency graph is acyclic

    plan validate: 1 milestone(s), 2 issue(s), 0 failure(s), 0 warning(s)

  2. 2 $ majordomus plan ready exit 0

Why the tool knows this

The chain from this page to the code: the use case names commands, rules and claims; each rule is dispatched from the registry and each claim names the test that proves it; the scenario above executed the commands. Nothing in this chain is prose about intent.

  • majordomus planThe milestone and issue model — validate it, read it, and move one issue through it.

The rules that make it hold

  • blockingProject model integrityEvery milestone and issue file parses, carries the id its filename claims, and contains no key nobody reads.
  • blockingDependency graph integrityThe issue dependency graph is acyclic, every edge names an issue that exists, and no issue is executing ahead of a dependency that is not done.

Guarantees exercised

  • guaranteedMilestones and issues are canonical repository files, and a key nobody reads is an error
  • guaranteedIssue and milestone status is derived from recorded facts and is stored nowhere
  • guaranteedA cycle, a self-dependency and a dependency on an issue that does not exist are each refused by name
  • guaranteedExecution waves are computed from the graph, and issues in one wave that touch the same paths are reported as serialised
