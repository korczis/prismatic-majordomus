# M05: Real coordination of work, not cosmetic peer presence

Trace canonical intent -> milestone -> issue/task -> session -> worker/agent -> worktree -> exclusive scope claim -> execution -> evidence -> review -> handover -> completion. Identify where current cooperation board is observational vs actually enforcing work allocation. Reuse existing task/intent/plan schemas and execution policies. Build one typed coordination model with stable IDs, causal links, provenance, authorization, status derivation and conflict explanations. No second task database, event queue or frontend assignment table. Preserve existing GitHub synchronization as external projection, not second source of authority.

Support capability-aware eligible peer routing, explicit work acceptance, heartbeat/progress, resume/retry, cancellation, peer departure, claims over overlapping paths/issues, review requests/responses, handover across worktrees/machines and deterministic conflict resolution policy. Never turn receiving a peer message into arbitrary shell execution. Guard mutating work by repo policy and permissions. Delivery should be idempotent or carry dedup/operation IDs and compensation, with honest at-least-once semantics. Fairness/backpressure, bounded queues and expiration must be explicit.

Tests: worker dies mid-task; two agents claim same scope; one client disconnects; overlapping worktrees; request review on peer; same task resumed on new machine; GitHub offline; recovery after replay; zombie task; malicious unauthorized assignment. Gate: UI reflects authoritative events and evidence, no ghost owner, orphan claim or false completion.
