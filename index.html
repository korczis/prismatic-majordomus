Intent-driven development

Stop telling AI what files to edit. Tell it what must become true.

Majordomus is a control plane built on a doctrine: the desired state of the system, the constraints that must stay true and the evidence completion requires belong to the repository, not to a prompt. What follows keeps the two halves apart and marks each one — the part that is enforced here today, and the part that is still only the argument.

Not merely implemented.Not merely tested.Not merely merged.Satisfied.

install · one command

Install majordomus in one command

No git, no Rust, no Node, no root. One archive for your machine, its digest verified before anything is unpacked, into $HOME/.local/bin.

1 · paste into a terminal 
curl -fsSL https://majordomus.dev/install.sh | sh

2 · in the repository you want supervised

majordomus init

Writes .ai/ — the policy, the profiles, the rules, the prompts, the workflows — and nothing else.

3 · point your agents at it

majordomus update

Generates CLAUDE.md, AGENTS.md and the other bootstraps from the policy; every worker reads the same contract. Platforms, pinning a version, the security model →

01 / the problem

Prompt-driven development does not scale with the repository

A developer says: edit this file, add this endpoint, write these tests, update this component. The model follows the immediate instruction. Sometimes it works.

  • ✗It builds a second implementation of something that already exists.
  • ✗It ignores an ADR nobody put in front of it.
  • ✗Documentation claims one thing while the runtime does another.
  • ✗Tests pass while a whole integration surface is broken.
  • ✗The change merges, and nobody can answer a fairly basic question later.
What user intent was this change actually supposed to satisfy?

Context is fragmented across

  • source code
  • tests
  • git history
  • issues
  • milestones
  • ADRs
  • rules
  • doctrines
  • policies
  • session contexts
  • handovers
  • knowledge
  • generated documentation
  • runtime state
  • API schemas
  • deployment state
  • other agents working on the same system

Giving a model a larger context window does not solve this. A larger pile of unstructured information is still a pile.

02 / the core idea

Describe the desired state, not the edit

An intent is a statement about reality: what must become true, what must stay true, and what evidence would settle it. It is deliberately not a list of files to open.

Given the current repository, what must change for the intent to become true?

Intent is the primary artifact

A prompt is not the source of truth. It is one way to communicate an intent to a worker. Neither is an issue, a milestone, a commit, a pull request, an ADR or a test: those are projections, constraints, evidence or consequences around it.

04 / context before code

Context is compiled, not merely retrieved

The goal is not to pour the repository into the model. It is to compile the smallest useful representation of reality the work needs. Ordered by authority, carrying its provenance, and fitted to a line budget that names every exclusion: that part runs today. Deduplication against what a worker already holds, and detecting when two sources disagree, are the parts the model still wants.

Dumping twenty Markdown files into a context window is not architecture. It is littering with GPUs.

05 / governance is executable

The rules that apply to a piece of work are resolved before it starts, from the policy and the profile, and a blocking rule stops the command rather than advising it. 06 / provenance

Every significant change should be explainable

An intent should carry its origin, its governance, its constraints, its realisation, its verification and the interfaces it reached. That is what turns development history into something you can ask a question of — and it is the shape of the record, not one this repository writes yet.

Instead of

Why does this code exist?

fix stuff

An answerable history says

This subsystem exists because an intent required automatic worker bootstrap. It was introduced in these commits, under this doctrine, verified by this test, exposed on these interfaces, and its verification status is current. Commit to issue, this repository already answers; the intent above them is what is missing.

07 / issues are a projection

The tracker stops pretending to be the semantic model

Issues stay useful. Milestones stay useful. In this model they become projections of intent rather than the place intent is kept. Commit to issue is already traceable in both directions here; the intent above them is not, which is why the questions below are still unanswerable.

  • ?implementation with no active intent behind it
  • ?intent with no implementation
  • ?an issue marked complete while its acceptance criteria fail
  • ?a commit not linked to the intent it serves
  • ?a milestone claiming completion while dependent intents are unresolved

None of these are questions a tracker can answer, and none of them are questions this repository can answer today. They are the reason the intent object is worth building.

08 / claims must match reality

Automatic. Supported. Enforced. Generated. Tested.

Repositories accumulate words like these, and they are surprisingly dangerous. A claim is worth having only when something connects it to evidence. Here every claim names the source, the implementation and the test that settle it, and a claim whose evidence no longer resolves fails the build.

Each is an entry naming the source, the implementation and the test that settle it. A claim whose evidence no longer resolves fails the build before the site can be published.

Then either the implementation changes or the claim does. Reality wins — an unusual policy for software documentation, admittedly.

The shape of the finding, not a finding. Comparing a claim’s wording to the behaviour it describes is still a person’s job here; what the build does enforce is that every claim’s evidence resolves.

09 / opposition

Disagreement is cheap before deployment and expensive after

Before an implementation is accepted, another pass should try to disprove it. No command runs this today; it is the discipline the model asks for, and these are the questions that actually catch the failures.

  • ?Did we misunderstand the intent?
  • ?Does an existing implementation already solve this?
  • ?Is this duplicating another subsystem?
  • ?Which decision constrains it?
  • ?Which edge cases and which surfaces were forgotten?
  • ?Do the tests match the requirement, or only the implementation?
  • ?Can this regress silently later?

10 / done

Completion means intent satisfaction

Code written, tests green, PR merged: all useful, none of them proof of the outcome. A merged pull request whose intent remains false is unfinished work, and the git server is not an oracle.

The contract as the repository's own README works it through — an illustration, not a capture. One line per check, each naming what it proved; a failing line carries the command that reproduces it, and nothing is written until every line passes.

11 / a control loop — mostly not built

An agent does not get to declare success because its patch applied

Close the same stages and you have a control system rather than an assistant: context would observe, the plan would compute the difference, execution would act, verification would measure, and the result would be compared against the intent rather than against the diff — replanning until it is satisfied. Only the last of those runs here today. Majordomus never invokes a model and never writes the code; it decides what a worker is told and whether its claim of being done can be believed, and that comparator is the part of the loop that exists.

Not built: everything the word intent names

There is no intent object, no intent registry and no intent id. An issue here already records its objective, its desired state, its acceptance criteria and the evidence it requires — what is missing is anything above the issue that those roll up to, and any evaluation of those criteria when work is declared done. Nothing derives a plan from a desired outcome, runs an opposition pass, or assembles a proof that an intent was satisfied; the traceability that exists runs from commit to issue, not from either to an intent. Every sentence on this page written in the conditional is one of these. The doctrine came first and the surface follows it: when it exists it will appear on the matrix above like everything else, derived from one declaration, and this section will shrink.

the doctrine

Implementation is subordinate to intent

A change is not complete because code was written, tests passed, a pull request merged or a deployment succeeded. It is complete when all of this holds.

  • 1the originating intent is known
  • 2relevant context has been considered
  • 3applicable governance holds
  • 4the required implementation exists
  • 5affected surfaces are synchronized
  • 6acceptance criteria pass
  • 7claims match implementation
  • 8runtime behaviour is verified where it applies
  • 9evidence enough to demonstrate the outcome exists

Discover once. Reason once. Derive everywhere. Verify against intent.

A repository stops being a collection of partially synchronized artifacts and becomes an inspectable model of what we wanted, what we knew, what we decided, what changed, why it changed, what constrains it, whether it works, and how we know.

Humans define intent. Majordomus keeps the system honest.
