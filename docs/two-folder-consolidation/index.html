Rendered from docs/TWO_FOLDER_CONSOLIDATION.md — the same Markdown GitHub shows.

The phase 1 deliverable of the two-folder-integration milestone (issue I1101, decision ADR 0169). It lists every path Majordomus writes, generates or mutates when a project adopts it, outside .ai/ and .majordomus/. For each path it gives the code that writes it, whether anything records the write, the class it belongs to, and what the two-folder contract does with it.

The inventory was established on 2026-10-16 against d1162668036 in two ways, and a row appears here only when one of them found it:

  • Reading the writers. Every write in bin/majordomus, lib/*.sh, share/mods/claude-code/, site/static/install.sh and apps/majordomus-cli/src/** was read: redirections, mv/cp/mkdir/ln, git config, update-ref, push, std::fs::write, create_dir_all, rename and symlink. Temporary directories that are removed before the command returns are left out, and so are writes that happen only inside the Majordomus source tree (scripts/derive, scripts/ci/*, .just/*).
  • Measuring an adopter. A new git init repository with a README, one source file and one commit was adopted with HOME and the XDG directories pointed at an empty directory. It ran init, update, capture install, start, check, finish, doctor, context, handover, serve ensure/stop, worktree create, update again, generate --check, generate, completion install and continuity publish. After each step it recorded every changed path outside the two namespaces, every file in .git/ except objects, git config --local, every file under HOME, and every sibling directory. The same run was repeated with init --personal.

The default part of the measurement is a test, not a memory: case test/cases/3113_the_adoption_footprint_is_inventoried.sh adopts a new repository with init, update and capture install. It then requires the set of paths outside the two namespaces to equal the list in the default adoption, requires this document to name each of them, and requires a personal adoption to leave git status empty while its exclude block names every path it wrote. A writer that starts leaving a new path behind fails the case until this document records it.

This replaces the first reading of 2026-09-06 (948dbd93, still in history as 95d9a773c7f). What changed since that reading lists what it got wrong or what has moved since.

Classes

Every row carries one class. The class says why the path exists, and the contract decides on that reason:

ClassMeaning
canonicalOnce written, it is the person's file. Majordomus seeds it and then does not own it. Rewriting it would overwrite somebody's work.
derivedComputed from this repository's own .ai/ content. It is committed, regenerable and stamped or bannered, and it is never read back as input.
generatedLaid down from the tool's distribution (share/). It is byte-identical in every repository at one version and follows the tool, not the repository.
cacheRecomputable state with no meaning of its own. Deleting it costs time and nothing else.
runtimeState of one clone, one machine or one process. It never travels through git as content, though it may live in git's own directory or refs.
accidentalWritten in an adopter although it serves no purpose there: a projection of Majordomus's own source tree, or output that landed at the repository root for want of a namespace.

The fate column uses three words. Bridge means the path stays where it is because a consumer outside Majordomus reads it there, and the ownership ledger records it (I1109). Move means it goes into .ai/ or .majordomus/. Stop means it stops being written in an adopter.

7. What changed since the first reading

These corrections are measured against 948dbd93:

  • Completion and environment exist. majordomus completion install writes a managed block in the shell's startup file, and majordomus env describes the checkout. The first reading said there was neither.
  • There is now one uninstall path: completion install --remove. Nothing else is reversible.
  • capture install writes more than hooks. It writes two Claude Code mods under .claude/skills/, and removes them when their policy key is turned off. generate writes editor skills under .claude/skills/ and .agents/skills/ and a .zed/tasks.json. None of these were in the first reading.
  • share/allow/commands.txt and share/allow/events.txt now say what they are. Both carry an AUTHORED FILE — no generator derives it yet banner. They are still authored files in a generated directory.
  • A personal adoption exists, and it is the one adoption that already keeps a record of what it wrote (section 1).
  • Still true: init refuses a second run with exit 15 (test/cases/01_init.sh); nothing reverses init, update or capture install; share/events.yaml has no init event; README.md:476 still says every generated file comes out of the one executable, which scripts/generate-site-data still contradicts.

8. Defects this inventory found, recorded and not fixed here

This phase changes no path. Each defect below belongs to the phase named:

  • generate in an adopter writes Majordomus's own docs/INSTALL.md, site/static/install.sh and site registry (section 3) → I1112 / I1116.
  • The Rust provider renderer overwrites a hand-edited AGENTS.md in file mode, and migrate runs update --force (lib/migrate.sh:220), which does the same → I1111 / I1114.
  • update writes $MJ_ROOT/$target without the ../ and absolute-path guard mj_norm_path (lib/common.sh:694-707) → I1102.
  • A stale .zed/tasks.json is never removed → I1110.
  • Worktree creation turns on extensions.worktreeConfig in the shared .git/config and says so only in its JSON → I1109.
  • refs/offload/* sits outside refs/majordomus/ → I1104.
  • The SessionEnd commit bypasses the repository's commit hooks by construction → I1109 records it; whether it stays default is a policy decision, not this inventory's.

9. Ordered slices

These are the milestone's issues, in the order the inventory supports:

  1. I1102 / I1104: the namespaces as a typed contract. .ai/, .majordomus/ and refs/majordomus/ are the namespaces. .ai/.gitignore takes the boundary lines out of the root .gitignore.
  2. I1109: the ownership ledger, grown out of the personal exclude block, covering files, clone configuration, refs and history mutations, each with the hash it was written with.
  3. I1108 / I1110: init as a reconciler in the shape the editors plan already has: desired, actual, conflict, orphan. A second run changes nothing.
  4. I1112: the root reduced to bridges. The .claude/hooks/ shims move under .majordomus/, and the accidental rows of section 3 stop.
  5. I1111: uninstall, using the stamp comparison for refusal and the completion block's --remove as the pattern.
  6. I1116: this repository's own footprint, moved through the reconciler, with a dry run first.

10. Risks

  • An inventory that a writer outruns is worse than none. It authorises what it no longer describes. That is why the default adoption is a test (case 3113), not only a table. The optional commands of sections 3 to 5 are held by this reading alone until the ledger records them.
  • The shell tool and the Rust executable are two implementations of one product. The adoption lifecycle lives in the shell one, and generate lives in the Rust one. Both write the root provider files, and only the shell one refuses a hand edit. Any slice that moves a writer across that boundary has to leave one writer, not two.
